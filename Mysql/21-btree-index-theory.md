# 21 - B+ 树索引原理

## 1. 为什么是 B+ 树

| 候选 | 问题 |
|---|---|
| 哈希表 | 只支持等值，无范围/排序；InnoDB 有自适应哈希（AHI）做内部加速，不暴露给用户 |
| 二叉/红黑树 | 树高随数据线性增长，磁盘 IO 次数太多 |
| B 树 | 数据存所有节点，单节点存键少 → 树更高；叶子无链表，范围查询中序遍历回溯 |
| B+ 树 | **数据全在叶子 + 非节点只存键 + 叶子双向链表**：树矮（3 层 2000 万行）、范围扫描顺链走 |

## 2. 结构与规模估算

- 页 16KB，InnoDB 索引键+指针约 12~13 字节 → 非叶子节点一个页可存约 1200 个键
- 假设行 1KB：叶子页存 16 行
- **3 层树容量：1200 × 1200 × 16 ≈ 2000 万行**
- 结论：一次主键查询 ≤ 3 次 IO（根节点常驻内存后仅 1~2 次）；千万级单表主键查询依然极快——这就是"5000 万行再考虑分表"的底气

## 3. 聚簇索引（主键索引）

```
叶子节点存完整行数据。表本身就是主键的 B+ 树。
```

- `SELECT * FROM t WHERE id = 5` → 沿主键树到叶子直接得行
- **为什么主键要自增**：顺序追加到最右叶子，无页分裂；UUID 随机插入 → 页分裂 + 碎片 + 缓存失效（见 16/19）
- 主键越小，所有二级索引越小（见 4）

## 4. 二级索引（回表）

```
二级索引：叶子存 (索引列值, 主键值)
查询流程：二级索引树找主键 → 回聚簇索引树取整行
```

- `SELECT * FROM user WHERE username='alice'`：username 索引树 → 得 id → 回主键树 → 得行
- 回表代价 = 再一次树查找，多行匹配时乘以行数 → **覆盖索引**消除回表（见 22）
- 间接规则：主键尽量小（BIGINT 而非长 VARCHAR），二级索引每个叶子都带主键

## 5. 页分裂与页合并

- 插入顺序键：填满一页开新页（顺序追加）
- 插入随机键：中间插入 → 当前页分裂（搬移一半数据）→ 碎片与性能抖动
- 删除使页利用率低于阈值（MERGE_THRESHOLD 默认 50%）→ 与相邻页合并

这也解释了：
- 唯一索引 ID 尽量趋势递增
- 批量导入前 `ORDER BY 主键` 可显著提速
- 高频删除的表要 `OPTIMIZE TABLE`/重建回收碎片

## 6. 一个索引一棵树

每个索引都是独立 B+ 树 → **索引不是越多越好**：
- 空间：每索引一整棵树
- 写放大：INSERT/UPDATE/DELETE 都要维护所有相关索引
- 建议：单表索引 ≤ 5~6 个，优先联合索引合并单列索引

## 常见坑

1. UUID 做主键导致页分裂与索引膨胀
2. 长 VARCHAR 主键让所有二级索引膨胀
3. 索引数量失控，写入慢
4. 以为"B+树 3 层"在超大表仍成立——行很宽（大字段）时叶子行数骤降，树高 4+，IO 翻倍 → 大字段拆表

## Checklist

- [ ] 主键自增 BIGINT 或雪花（趋势递增）
- [ ] 索引数量克制，优先联合索引
- [ ] 能口算 3 层树 ≈ 2000 万行的估算过程
