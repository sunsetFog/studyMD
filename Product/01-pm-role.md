# 01 · 产品经理到底在干什么

## 1. 一句话定义

> PM 是**对产品的商业结果负责**的人：决定做什么、不做什么、为什么做、按什么顺序做，并推动团队把它交付出去。

不是「画原型的」、不是「传话筒」、不是「给开发提需求的」。核心产出是**决策**，不是文档。

## 2. PM 的四项职责

```
① 定方向：这个产品/功能为谁、解决什么问题、凭什么赢
② 定范围：这一版做哪些、不做哪些（砍需求比加需求更重要）
③ 定标准：做成什么样算好（验收标准、质量基线、指标）
④ 推落地：协调设计/开发/测试/运营，让东西真的上线并被用起来
```

## 3. PM 不做什么（边界感）

| 不该 PM 做的 | 谁来做 |
|---|---|
| 决定技术方案、表结构、选型 | 技术负责人 |
| 决定视觉细节、动效 | 设计师 |
| 决定测试用例与自动化策略 | QA |
| 替用户拍脑袋说「用户肯定想要」 | 用户研究/数据 |

PM 的权威来自**信息充分 + 逻辑清晰 + 对结果负责**，而不是职级。

## 4. 能力模型（T 型）

```
        通用素养：沟通、结构化思考、同理心、数据感
                        |
   深度：需求洞察 + 方案设计 + 项目推动 + 数据闭环
                        |
        领域知识：所在行业的业务流程与用户心智
```

| 能力 | 具体表现 | 提升方式 |
|---|---|---|
| 用户洞察 | 能从访谈里听出真实动机 | 每月 3 次用户访谈 |
| 结构化 | 能把一团乱麻拆成树状结构 | 练习 MECE、画思维导图 |
| 取舍判断 | 敢砍需求并说明理由 | 每次评审后复盘决策 |
| 数据感 | 会定义指标、会看异常 | 自己搭一次埋点+看板 |
| 推动力 | 无人授权下也能把事推成 | 主动同步进度、暴露风险 |

## 5. PM 的分类

| 类型 | 关注点 | 典型产出 |
|---|---|---|
| 用户/体验型 | 交互、留存、NPS | 原型、体验优化方案 |
| 商业/增长型 | 收入、转化、成本 | 变现策略、增长实验 |
| 数据/策略型 | 模型、策略、效率 | 策略文档、实验报告 |
| 平台/B 端型 | 流程、效率、稳定 | 业务流程方案、接口定义 |
| AI 产品型 ★ | 能力边界、质量、成本 | Prompt 规格、evals 集、降级策略 |

## 6. 与开发协作的正确姿势 ★

开发者（你）最应该从 PM 身上拿到什么：

1. **明确的问题定义**：用户在什么场景下卡住了（不是「我要一个 AI 助手」）
2. **可验收的标准**：什么算做对了，含边界与异常
3. **优先级与 deadline 的理由**：为什么是现在做
4. **决策授权范围**：哪些细节我可以自己定

反过来，开发者应该主动给 PM 什么：

1. **技术可行性边界**：这个模型现在做不到 / 做得到但要花多大代价
2. **成本与性能数据**：一次调用多少钱、多慢、在什么量级会出问题
3. **替代方案**：更便宜/更稳的实现路径

> ★ AI 时代最大的变化：**技术可行性是模糊的**。PM 问「能不能做」，正确答案是「能做到 70 分，90 分需要 X 成本，且不稳定」。你必须给出**概率与成本**，而不是简单的能/不能。

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 需求传话筒 | 用户说要什么就记什么 | 追问 5 个 Why，还原场景 |
| PRD 写了没人看 | 文档 50 页，开发只读结论 | 结论前置 + 原型 + 验收标准 |
| 拍脑袋决策 | 「我觉得用户会喜欢」 | 任何判断都要有证据或标注假设 |
| 只管上线不管结果 | 上线即结束 | 上线前就定好观测指标 |
| 频繁改需求 | 开发中途改方向 | 变更走评估：影响/成本/是否本版 |

## 8. Checklist

- [ ] 能一句话说清这个产品为谁解决什么问题
- [ ] 知道这一版不做什么，并能说明理由
- [ ] 每个需求都对应一个用户场景，不是凭空的功能
- [ ] 上线前已定义好「成功长什么样」的指标
- [ ] 与开发的协作有明确的决策授权边界
