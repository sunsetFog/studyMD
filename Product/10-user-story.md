# 10 · 用户故事与验收标准

## 1. 用户故事（User Story）的句式

```
作为【角色】，我希望【做什么】，以便【获得什么价值】。

例：
作为【电商运营】，我希望【一次生成 5 条文案】，以便【快速挑选合适的上架】。
```

三个组成部分：**Card（卡片：一句话描述）+ Conversation（对话：讨论细节）+ Confirmation（确认：验收标准）**。

> 常见误读：用户故事不是需求文档，而是**引发对话的承诺**。细节在讨论里，不在卡片上。

## 2. INVEST 原则（好故事的标准）

| 字母 | 含义 | 说明 |
|---|---|---|
| **I** Independent | 独立 | 可单独交付，不依赖其他故事 |
| **N** Negotiable | 可协商 | 不是合同，细节可讨论 |
| **V** Valuable | 有价值 | 对用户/业务有明确价值 |
| **E** Estimable | 可估算 | 团队能估出工作量 |
| **S** Small | 小 | 一个迭代内能完成（一般 ≤ 3 人日） |
| **T** Testable | 可测试 | 有明确的验收标准 |

不合格例子：「作为用户，我希望系统性能好」——不 Valuable（太泛）、不 Estimable、不 Testable。

## 3. 故事拆分（Splitting）

**纵向切分**（按用户价值切，而非按技术层切）：

```
❌ 横向切：做数据库 → 做后端接口 → 做前端页面（切完每个都不能交付价值）
✅ 纵向切：
   故事1：能生成一条文案（最薄的全链路）
   故事2：能生成多条并挑选
   故事3：能保存为模板
   故事4：能批量导出
```

### 拆分技巧

| 方法 | 例子 |
|---|---|
| 按流程步骤拆 | 搜索 → 筛选 → 对比 → 下单 |
| 按业务规则拆 | 先支持普通用户，再支持 VIP 规则 |
| 按数据边界拆 | 先支持 1 条，再支持 10 条，再支持无限 |
| 按接口/渠道拆 | 先 Web，再移动端 |
| 按操作拆 | 先支持创建，再支持编辑/删除 |
| 按质量属性拆 | 先能用，再优化性能/体验 |

## 4. 验收标准（Acceptance Criteria）

### 写法：Given-When-Then

```gherkin
Feature: 批量生成文案
  场景：正常生成
    Given 用户输入了商品信息且剩余额度 ≥ 5
    When  点击「生成 5 条」
    Then  展示 5 条结果
    And   每条结果可单独复制

  场景：额度不足
    Given 用户剩余额度为 2
    When  用户选择生成 5 条
    Then  提示「剩余额度不足，最多可生成 2 条」
    And   不调用生成接口

  场景：生成超时
    Given 模型响应超过 30 秒
    When  用户在等待页
    Then  展示中断按钮
    And   中断后保留已生成的结果
```

### AC 的常见写法对比

| 弱 | 强 |
|---|---|
| 「响应要快」 | 「首字延迟 ≤ 1.5s（P95）」 |
| 「结果要准确」 | 「结构化字段解析成功率 ≥ 98%」 |
| 「界面友好」 | 「错误提示包含原因 + 下一步操作」 |
| 「支持批量」 | 「单次最多 10 条，超过提示上限」 |

## 5. 故事点估算

| 方法 | 说明 |
|---|---|
| 斐波那契数列 | 1/2/3/5/8/13，越大越不确定 |
| 计划扑克 | 各自出牌，差异大则讨论后重出 |
| T-shirt size | S/M/L/XL，粗估用 |

**估算的是规模（复杂度+工作量+不确定性），不是时间**。速度由团队历史吞吐（velocity）换算。

> 只估相对值：「这个比那个大一倍」比「这需要 5 天」准确得多。

## 6. DoD（完成的定义）

团队共同约定「Done」意味着什么：

```markdown
- [ ] 代码已合并并通过 Code Review
- [ ] 单元测试覆盖率 ≥ 60%，关键路径有测试
- [ ] 通过 QA 验收（AC 全绿）
- [ ] 埋点已上报并验证
- [ ] 无新增 P0/P1 缺陷
- [ ] 文档/配置已更新
- [ ] 已在预发环境验证
```

★ AI 功能的 DoD 补充项：

- [ ] evals 集通过率达标（见 36 篇）
- [ ] 单次成本在预算内
- [ ] 降级路径已验证
- [ ] prompt 已版本化并入库

## 7. 故事地图（Story Map）

```
                ┌──────────── 发布 v1 ────────────┬──── v2 ────┐
用户活动：       找商品          下单           售后
                  │              │              │
任务：         搜索  筛选      加购  支付      退货  咨询
                  │    │         │    │         │     │
故事：         键搜  价格筛选  购物车 微信支付  申请  AI客服
                                               ↑
                                           Walking Skeleton（骨架先通）
```

作用：**横轴是用户旅程，纵轴是优先级**，一眼看出每个版本的完整性。

## 8. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 故事写成任务 | 「设计数据库表」 | 用用户视角句式，有用户价值 |
| 故事太大 | 一个故事做两周 | 按 INVEST 拆到 ≤ 3 人日 |
| 没有 AC | 做完说不清完成没有 | 无 AC 不进迭代 |
| AC 只写正常路径 | 异常全靠临时发挥 | 每个故事至少 2 条异常 AC |
| 估算变承诺 | 估 3 点被当成 3 天 | 估算只用于相对排序 |
| 故事横向切 | 前后端各做一半 | 纵向切通全链路 |
| DoD 不统一 | 有人觉得「写完代码」就算完成 | 团队公示 DoD 清单 |

## 9. Checklist

- [ ] 故事用「作为…我希望…以便…」句式
- [ ] 通过 INVEST 六项检查
- [ ] 每条故事有 ≥ 3 条 AC（含异常）
- [ ] 大故事已纵向拆分
- [ ] DoD 团队共识且公示（AI 项目含 evals/成本/降级）
