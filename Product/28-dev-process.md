# 28 · 产品研发全流程：从想法到上线

## 1. 全景流程

```
① 想法/机会      （需求池、用户反馈、战略）
      ↓
② 评估与立项      （价值、可行性、成本；决定做不做）
      ↓
③ 需求定义        （调研、画像、PRD、原型、AC）
      ↓
④ 方案评审        （产品 + 设计 + 开发 + 测试 对齐）
      ↓
⑤ 设计            （交互稿 → 视觉稿 → 设计评审）
      ↓
⑥ 开发            （技术方案 → 编码 → 自测 → 联调）
      ↓
⑦ 测试            （用例 → 功能测试 → 回归 → 性能/兼容）
      ↓
⑧ 验收            （PM/设计验收，UAT）
      ↓
⑨ 发布            （灰度 → 放量 → 全量）
      ↓
⑩ 运营与迭代      （数据监控 → 用户反馈 → 下一轮）
```

## 2. 各阶段的关键产出与角色

| 阶段 | 主责 | 产出 | 参与 |
|---|---|---|---|
| 立项 | PM + 负责人 | 立项文档（目标、范围、指标、资源） | 全员 |
| 需求 | PM | PRD + 原型 + AC | 设计、开发、测试 |
| 设计 | 设计师 | 交互稿、视觉稿、切图/规范 | PM、开发 |
| 技术方案 | 开发负责人 | 技术方案、接口定义、排期 | PM、测试 |
| 开发 | 开发 | 代码、自测报告 | — |
| 测试 | QA | 测试用例、缺陷、测试报告 | 开发 |
| 验收 | PM/设计 | 验收结论 | 全员 |
| 发布 | 开发 + 运维 | 发布计划、回滚方案 | PM、QA |
| 运营 | 运营/PM | 数据报告、迭代计划 | 全员 |

## 3. 需求评审（最关键的对齐点）

```
会前：PRD + 原型提前 1 天发出，参会者必须读过
会中：
  ① PM 讲背景、目标、指标（5min）
  ② 过功能点与流程
  ③ 过边界与异常（★ 重点）
  ④ 开发评估可行性与工时风险
  ⑤ 测试确认可测性
  ⑥ 当场决策：通过 / 修改后再审 / 砍掉
会后：24h 出纪要（决策 + 待办 + 负责人 + 时间）
```

**评审不通过的常见原因**：目标不清、边界缺失、方案没考虑技术约束、范围过大。

## 4. 技术方案评审（开发主导）

内容：
- 系统/数据模型变更
- 接口定义（含字段与错误码）
- 依赖与风险（第三方、模型 API）
- 性能与容量（QPS、数据量、成本）
- 兼容与迁移方案
- 灰度与回滚方案

★ AI 项目必须增加：
- 模型选型与 fallback 链路
- Prompt 设计与版本管理
- 成本估算（单次/日均）
- 降级与限流策略
- 输出格式校验与容错

## 5. 测试与质量

| 测试类型 | 谁做 | 说明 |
|---|---|---|
| 单元测试 | 开发 | 核心逻辑 |
| 接口测试 | 开发/QA | 契约测试 |
| 功能测试 | QA | 按 AC |
| 回归测试 | QA | 自动化优先 |
| 性能/压力 | QA/开发 | 关键路径 |
| 兼容测试 | QA | 浏览器/设备 |
| 安全测试 | 安全 | 越权、注入、数据泄露 |
| ★ AI 效果测试 | 开发 + PM | Evals 集 + 人工抽检 |

**缺陷分级**：

| 级别 | 定义 | 处理 |
|---|---|---|
| P0/致命 | 崩溃、数据丢失、不可用 | 立即修，阻塞发布 |
| P1/严重 | 主流程受阻、无替代方案 | 本迭代必修 |
| P2/一般 | 次要功能异常、有替代 | 排期修 |
| P3/建议 | 体验瑕疵 | 择机 |

## 6. 发布策略

| 策略 | 说明 | 适用 |
|---|---|---|
| 全量发布 | 一次全上 | 低风险小改动 |
| 灰度（按比例） | 1% → 5% → 20% → 100% | 常规 |
| 按用户分群 | 内部 → 种子用户 → 全量 | 大改动 |
| 金丝雀 | 少量服务器先上 | 服务端/基础设施 |
| 特性开关（Feature Flag） | 代码上线但功能关闭 | ★ 强烈推荐 |
| 影子流量（Shadow） | 新逻辑跑但不返回结果 | ★ AI 模型替换验证 |
| 蓝绿/滚动 | 基础设施层面 | 运维 |

**发布必配**：监控告警 + 回滚方案 + 回滚演练 + 值班人员。

## 7. 上线后（最容易被跳过的一步）

```
① 数据监控（首日/首周）：核心指标、错误率、性能、成本
② 用户反馈收集（客服、评论、社群）
③ 缺陷跟进与热修
④ 效果复盘：是否达成立项时定的指标
⑤ 迭代计划：下一轮做什么
```

**上线不是结束，是验证的开始**。立项时定的指标就是复盘的依据。

## 8. 流程的常见病与对策

| 病 | 现象 | 对策 |
|---|---|---|
| 流程过重 | 小改动也要走全套 | 分级：大需求走完整流程，小改动走快速通道 |
| 流程过轻 | 口头需求直接开发 | 至少要有 PRD 简版 + AC |
| 文档没人看 | 写了等于没写 | 结论前置，控制篇幅 |
| 评审走过场 | 会上没人提问 | 会前强制阅读，会上点名提问 |
| 测试时间被压缩 | 开发延期挤压测试 | 排期预留测试时间，不可压缩 |
| 上线无监控 | 出问题靠用户投诉 | 发布清单含监控与告警 |
| 无复盘 | 同样问题反复 | 每个版本做 30 分钟复盘 |

## 9. ★ AI 项目的流程补丁

| 环节 | 补丁 |
|---|---|
| 立项 | 增加「可行性验证（spike）」阶段，先跑通效果再立项 |
| 需求 | PRD 含输出规格、示例集、质量基线、降级方案、成本预算 |
| 开发 | Prompt 版本化入库，与代码分离管理 |
| 测试 | 建 Evals 测试集（≥ 50-100 条），每次改动跑回归 |
| 发布 | 影子流量对比新旧模型/prompt，再灰度 |
| 上线 | 监控质量指标（采纳率、👎率）与成本，不只是技术指标 |
| 复盘 | 加入 bad case 复盘与 prompt 迭代 |

## 10. Checklist

- [ ] 每个需求有明确的目标指标（立项时定，上线后复盘）
- [ ] 需求评审有 PRD + 原型 + AC，24h 内出纪要
- [ ] 技术方案含依赖、性能、回滚
- [ ] 发布有灰度、监控、回滚方案
- [ ] 上线后 1 周内做数据与反馈回顾
- [ ] AI 项目含 spike、evals 回归、影子流量、成本监控
