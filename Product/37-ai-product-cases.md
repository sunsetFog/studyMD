# 37 · AI 产品案例拆解：可复用的模式

## 案例一：AI 客服问答（RAG 型）

| 维度 | 内容 |
|---|---|
| **Job** | 当用户有问题时，我要立刻得到准确答案，而不是等人工或翻文档 |
| **容错度** | 中（答错了有代价，但有人工兜底） |
| **范式** | 对话 + 引用来源 + 转人工 |
| **关键技术** | RAG（知识库检索）+ 拒答机制 + 意图路由 |
| **北极星** | 问题解决率（无需转人工且用户未再追问） |
| **质量基线** | 答案有依据率 ≥ 95%，拒答率 5-15% |
| **成本** | 单次 ¥0.01-0.05，靠缓存与小模型路由降本 |
| **体验要点** | 引用可点击、不确定时提示、可一键转人工 |

**可复用模式**：
```
知识库质量 > 模型能力（垃圾进垃圾出）
拒答比编造好（宁可说不知道）
转人工通道是信任基础
「未解决问题」是最有价值的训练与改进来源
```

## 案例二：AI 写作助手（生成型）

| 维度 | 内容 |
|---|---|
| **Job** | 当我面对空白页时，我要一个可以改的起点，省去从零开始 |
| **容错度** | 高（用户会改，本来就是草稿） |
| **范式** | 生成式创作 + Copilot（就地改写） |
| **关键技术** | prompt 模板库 + 风格控制 + 局部重写 |
| **北极星** | 用户采纳并保存的成稿数 |
| **质量基线** | 采纳率 ≥ 60%，平均编辑幅度 ≤ 30% |
| **成本** | 单次 ¥0.02-0.1，注意长文成本 |
| **体验要点** | 多个候选、流式输出、局部重写、版本管理 |

**可复用模式**：
```
给「起点」而不是「成品」（降低期望压力）
多候选 + 可编辑 = 用户掌控感
模板库降低冷启动门槛
风格/语调自定义是付费点
```

## 案例三：AI 代码助手（Copilot 型）

| 维度 | 内容 |
|---|---|
| **Job** | 写代码时，我要少敲重复代码、更快找到答案 |
| **容错度** | 低（代码要能跑）但**验证成本低**（跑一下就知道） |
| **范式** | Copilot（IDE 内内联建议）+ 对话 |
| **关键技术** | 上下文工程（当前文件/项目/依赖）+ 补全时机 |
| **北极星** | 采纳的建议行数 / 采纳率 |
| **质量基线** | 建议采纳率 25-35%（行业水平） |
| **体验要点** | 建议不打断、可 Tab 接受、可部分接受 |

**可复用模式**：
```
★ 「验证成本低」的场景最适合 AI（错了马上能发现）
内联呈现优于弹窗（不打断心流）
上下文质量决定效果（取哪些文件很关键）
接受率是最重要的线上指标
```

## 案例四：AI 文档/会议摘要（提效型）

| 维度 | 内容 |
|---|---|
| **Job** | 面对长内容，我要 30 秒知道重点和跟我相关的部分 |
| **容错度** | 中（遗漏要点是主要问题） |
| **范式** | 嵌入式增强（在文档旁一键生成） |
| **关键技术** | 分块 + 长上下文 + 结构化输出（要点/待办/决议） |
| **北极星** | 使用摘要后完成阅读/决策的比例 |
| **质量基线** | 要点召回率（人工评估）≥ 85% |
| **体验要点** | 结构化呈现、可展开原文对照、可复制 |

**可复用模式**：
```
输出结构化（要点列表 > 段落）
与原文对照（便于验证，建立信任）
「待办事项」「决议」比「摘要」更有价值
长内容要分块处理并注意成本
```

## 案例五：AI 数据分析助手（Agent 型）

| 维度 | 内容 |
|---|---|
| **Job** | 我不懂 SQL，但我要从数据里得到答案 |
| **容错度** | 低（数字错了会误导决策）但可验证（展示 SQL） |
| **范式** | 对话 + Agent（生成 SQL → 执行 → 解释） |
| **关键技术** | Text-to-SQL + schema 注入 + 结果校验 + 展示 SQL |
| **北极星** | 用户得到可用答案的会话比例 |
| **质量基线** | SQL 可执行率 ≥ 90%，结果正确性 ≥ 85% |
| **体验要点** | 展示生成的 SQL（可审计）、展示数据表格、支持追问 |

**可复用模式**：
```
★ 展示中间产物（SQL）是建立信任的关键
让 AI 做「翻译」而非「结论」（用户自己解读数据）
限制范围（只读权限、限行数、超时）是安全底线
错误时展示 SQL 让用户能修正
```

## 案例六：AI 图片/设计生成（创作型）

| 维度 | 内容 |
|---|---|
| **Job** | 我要快速得到一张能用的图，不用找设计师 |
| **容错度** | 高（不满意就再生成） |
| **范式** | 生成式创作（参数 + 多候选） |
| **关键技术** | 文生图模型 + 风格预设 + 后处理 |
| **北极星** | 被下载/使用的图片数 |
| **体验要点** | 多候选并行生成、参数可视化、局部重绘、历史版本 |
| **成本** | 单次较高（¥0.1-1），免费额度要严格限制 |

**可复用模式**：
```
参数可视化比让用户写 prompt 更友好
并行生成 4 张让用户选（提高满意度）
局部重绘/inpainting 是高频刚需
成本是核心约束（限次 + 风控）
```

## 跨案例的可复用规律

| 规律 | 说明 |
|---|---|
| **验证成本决定可行性** | 用户能快速验证结果对错 → AI 容易成功（代码、摘要） |
| **给起点而非成品** | 降低期望、提高采纳 |
| **可编辑性是刚需** | 不可编辑的结果用户不敢用 |
| **结构化优于自由文本** | 便于验证、便于程序处理 |
| **展示过程建立信任** | 引用、SQL、中间步骤 |
| **拒答优于编造** | 尤其在有依据要求的场景 |
| **上下文工程 > 模型选择** | 给对的信息比换模型更见效 |
| **采纳率是最好的质量指标** | 反映真实价值 |
| **成本决定商业模式** | 单位经济必须为正 |
| **人工兜底是信任基础** | 尤其 B 端与高风险场景 |

## 失败案例的常见共性

```
① 拿着技术找场景（用户没有这个 Job）
② 与通用 ChatGPT 无差异（没有领域数据与工作流优势）
③ 期望管理失败（demo 太完美，上线失望）
④ 成本失控（免费额度被薅 / 重度用户亏损）
⑤ 质量不稳定（无 evals，悄悄退化）
⑥ 没有人工兜底（出错就崩）
⑦ 冷启动做不好（用户不知道输什么）
⑧ 合规问题（上线后被叫停）
```

## Checklist（做 AI 功能前对照）

- [ ] 明确了这个功能的 Job 与容错度
- [ ] 选对了交互范式（对话/Copilot/Agent/嵌入式）
- [ ] 做过 spike，有真实样本的质量数据
- [ ] 定义了质量基线与线上指标（采纳率等）
- [ ] 建了 evals 集，每次改动回归
- [ ] 算过成本，单位经济为正
- [ ] 有人工兜底与降级方案
- [ ] 与「直接用 ChatGPT」相比有明确差异优势
