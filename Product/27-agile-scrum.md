# 27 · 敏捷与 Scrum：迭代怎么跑起来

## 1. 敏捷的价值观（四个宣言）

```
个体与互动        > 流程与工具
可工作的软件      > 详尽的文档
客户合作          > 合同谈判
响应变化          > 遵循计划
```

注意：右侧也有价值，只是左边更重要。**敏捷不是「没有文档、没有计划」**。

## 2. Scrum 三大角色

| 角色 | 职责 | 常见误区 |
|---|---|---|
| **PO（产品负责人）** | 决定做什么、排序、对价值负责 | 变成「需求传话筒」 |
| **SM（Scrum Master）** | 保障流程、移除障碍、教练 | 变成「项目经理/催进度」 |
| **开发团队** | 跨职能、自组织、交付增量 | 变成「按文档干活的螺丝钉」 |

## 3. Scrum 五大事件

| 事件 | 时长 | 输入 | 输出 |
|---|---|---|---|
| **Sprint 计划会** | 2-4h（2周迭代） | 排好序的 Backlog | Sprint 目标 + 本迭代待办 |
| **每日站会** | 15min | — | 同步 + 暴露障碍 |
| **Sprint 评审** | 1-2h | 完成的增量 | 反馈 + 调整 Backlog |
| **Sprint 回顾** | 1-1.5h | 本迭代过程 | 改进行动项（1-3 条） |
| **Backlog 梳理** | 每周 1h | 粗需求 | 细化、估算、排序后的 Backlog |

### 站会的正确开法

```
✅ 围绕 Sprint 目标：「为了达成目标，我今天做 X，卡在 Y」
❌ 流水账汇报：「昨天写了代码，今天继续写」
```

站会不是汇报会，是**同步与暴露风险**。

## 4. 迭代节奏（Sprint）

```
Sprint 长度：1-4 周（多数 2 周）
  - 短：反馈快，但仪式开销占比高
  - 长：稳定，但风险积累
  ★ AI 项目建议 1-2 周（不确定性高，需快速反馈）
```

### Sprint 的完整性

```
① Sprint 目标（一句话，可衡量）
② 选定需求（团队承诺，非被分配）
③ 迭代内范围锁定（变更走例外流程）
④ 产出潜在可交付增量（DoD 达标）
```

> **迭代内不改需求**是 Sprint 有效的关键。要改就停掉重开 Sprint。

## 5. 看板（Kanban）vs Scrum

| 维度 | Scrum | 看板 |
|---|---|---|
| 节奏 | 固定迭代 | 持续流动 |
| 变更 | 迭代内锁定 | 随时可改（有 WIP 限制时） |
| 度量 | Velocity | 周期时间、吞吐 |
| 适合 | 有明确目标的开发 | 运维、支持、探索性工作 |

### 看板核心：WIP 限制

```
待办 | 进行中(≤3) | 评审中(≤2) | 完成
```

限制在制品数量 → 暴露瓶颈 → 加快流动。**不设 WIP 的看板只是贴纸墙**。

## 6. 度量指标

| 指标 | 说明 | 用途 |
|---|---|---|
| **Velocity** | 每迭代完成的故事点 | 预测产能（不可用来比较团队！） |
| **周期时间** | 从开始到交付的时长 | 反映流程效率 |
| **吞吐量** | 单位时间完成项数 | 产能 |
| **燃尽图** | 剩余工作量趋势 | 进度可视化 |
| **CFD（累积流图）** | 各状态堆积 | 找瓶颈 |
| **变更失败率/交付频率** | DORA 指标 | 工程效能 |

> 反模式：用 Velocity 考核团队 → 团队会 inflated 估算点数（点数通胀）。

## 7. 敏捷的常见反模式

| 反模式 | 表现 | 修正 |
|---|---|---|
| 瀑布式敏捷 | 先写完整 PRD 再「敏捷开发」 | 需求渐进细化 |
| 站会变汇报 | 向 PM/领导汇报 | 团队内部同步 |
| 回顾会不产出 | 只抱怨不改 | 每次产出 1-3 条可行动项并跟踪 |
| Sprint 无目标 | 只是「做这些需求」 | 写清目标与价值 |
| 迭代内插需求 | 天天改 | 锁定范围，紧急走例外 |
| PO 同时是 SM | 自己排需求自己催 | 角色分离 |
| 估算变承诺 | 估点被当 KPI | 估算只用于规划 |
| 只做仪式不改工作方式 | 「我们在跑 Scrum」但决策方式没变 | 敏捷是思维，不是仪式 |

## 8. ★ AI 项目的敏捷调整

| 调整 | 说明 |
|---|---|
| **缩短迭代** | 1-2 周，因为效果不确定，需要快速看到真实输出 |
| **Spike 任务常态化** | 每个不确定需求先做「可行性验证」（1-3 天）再评估 |
| **Demo 必须真实跑** | 评审要现场跑真实输入，不能只放 PPT（AI 效果必须眼见为实） |
| **Evals 进 DoD** | 没有通过测试集不算完成 |
| **Bad case 回顾会** | 每周固定时间过失败案例（类似 bug 复盘） |
| **数据准备单独排期** | RAG 的数据清洗/标注工作量大，要独立估算 |
| **模型变更当发版处理** | 换模型/改 prompt 走完整验证流程 |
| **成本评审** | 迭代评审时看成本指标，避免成本悄悄上涨 |

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 迭代太长 | 一个月才看到东西 | 缩到 1-2 周 |
| 需求没细化就进迭代 | 开发中才发现做不了 | 会前 Refinement 完成 |
| 并行做太多 | 什么都做一半 | WIP 限制 |
| 回顾会无行动 | 问题反复出现 | 行动项进下个迭代 Backlog |
| 燃尽图不更新 | 失去意义 | 每日更新（或看 CFD） |
| AI 项目只看功能完成 | 效果不达标也算完成 | 质量基线进 DoD |
| 忽略技术债 | 越跑越慢 | 固定比例还债 |

## 10. Checklist

- [ ] 每个 Sprint 有一句话目标
- [ ] Backlog 经过 Refinement（有 AC 与估算）
- [ ] 迭代内范围锁定，变更走例外
- [ ] 站会是团队同步而非向上汇报
- [ ] 回顾会产出 1-3 条行动项并跟踪
- [ ] 有 WIP 限制与可视化看板
- [ ] AI 项目：Demo 真实跑、Evals 进 DoD、每周 bad case 复盘
