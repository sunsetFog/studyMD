# 34 · Prompt 产品化：把提示词当成产品资产

## 1. 核心认知：Prompt 是代码，也是产品需求

```
prompt 决定了 AI 产品的 70% 表现
  → 它是「用自然语言写的产品逻辑与业务规则」
  → 它必须：版本化、可测试、可回滚、可协作、可审计
```

反模式：prompt 散落在代码字符串里、散落在某个人的 ChatGPT 对话里、改了不记录。

## 2. Prompt 的层次结构

```
┌─ 系统提示（System Prompt）：角色、目标、规则、风格、约束、输出格式
├─ 领域知识（注入）：RAG 检索结果、术语表、业务规则、示例库
├─ 用户输入（User）：用户实际输入（不可信，需防御）
├─ 上下文（History）：历史对话（需管理长度）
└─ 输出格式约束：JSON Schema / 模板 / 字数限制
```

## 3. 写好系统 Prompt 的结构模板

```markdown
# 角色
你是一个【角色】，服务于【用户群】。

# 目标
你的任务是【具体任务】。

# 输入
你会收到：【输入内容说明】。

# 规则（约束）
1. 必须…
2. 禁止…
3. 当【条件】时，【处理】
4. 如果不能确定，输出「无法确定」而不是编造

# 输出格式
输出必须符合以下 JSON Schema：
{...}
只输出 JSON，不要附加解释。

# 风格
语气【…】，长度【…】，使用【语言】。

# 示例（few-shot）
输入：…  输出：…
输入：…  输出：…
```

## 4. Prompt 工程常用技巧（产品视角）

| 技巧 | 说明 | 何时用 |
|---|---|---|
| **明确角色** | 给角色与受众 | 几乎总是 |
| **给示例（few-shot）** | 3-5 个输入-输出样例 | 需要特定格式/风格时最有效 |
| **结构化输出** | 要求 JSON + Schema | 需要程序解析时 |
| **链式拆解** | 把复杂任务拆成多步 | 复杂任务（先摘要再改写） |
| **思维链（CoT）** | 「请先分析再回答」 | 推理类任务 |
| **自检查** | 「输出前检查是否符合规则 X」 | 格式/合规要求高时 |
| **约束长度与格式** | 明确字数、段落、字段 | 几乎总是 |
| **负面约束** | 明确「不要…」 | 防止常见偏差 |
| **温度参数** | 低温度=稳定，高温度=创意 | 按场景调 |
| **变量化** | 把可变部分做成模板变量 | 工程化必需 |

> 提示：**「给示例」是性价比最高的技巧**。3 个高质量示例常常胜过 300 字的描述。

## 5. Prompt 工程化实践

### 模板化与变量

```python
SYSTEM_PROMPT = """你是{product}的客服助手。
请用{style}的语气回答用户问题。
只依据以下资料回答，资料中没有的请说明无法确定：
---
{context}
---
输出格式：{output_format}
"""
```

好处：可复用、可配置（按场景/租户切换）、便于 A/B 测试。

### 版本化

```
prompts/
├── customer-service/
│   ├── v1.0.0.md        # 初始版本
│   ├── v1.1.0.md        # 增加拒答规则
│   ├── v1.2.0.md        # 优化格式约束
│   └── CHANGELOG.md     # 变更记录：日期、改动、原因、评测结果
```

**每次改 prompt 必须记录**：

```markdown
| 版本 | 日期 | 改动 | 原因 | eval 通过率变化 | 负责人 |
```

### 与代码分离

```
✅ prompt 存配置文件/数据库/专用平台，支持热更新与灰度
❌ prompt 硬编码在代码里（改一次要发一次版）
```

### 灰度与回滚

```
改动流程：
  新 prompt v2 → 离线 eval（对比 v1） → 小流量 5% → 看线上指标 3 天
    → 全量 / 回滚 v1
```

## 6. Prompt 的测试（Evals 驱动）

```
每一次 prompt 改动必须跑测试集：
① 准备测试集（≥ 50 条，覆盖典型 + 边界 + 对抗）
② 定义评分方式（规则校验 / 模型评分 / 人工）
③ 跑新旧版本对比
④ 通过率不下降才允许发布
```

详见 36 篇。

## 7. 防御式 Prompt 设计

| 风险 | 防御 |
|---|---|
| 用户输入注入（Prompt Injection） | 明确区分系统指令与用户输入；对用户输入做标记与转义；不让模型执行用户带来的指令 |
| 输出格式不合法 | 要求严格 JSON + Schema；加后处理校验与自动修复 |
| 超长输入 | 限制长度，截断或分段 |
| 敏感内容输出 | 加安全规则 + 输出过滤 |
| 模型编造 | 明确「不确定时说不确定」；RAG 要求「只依据资料」 |
| 越权回答 | 在系统 prompt 中限定回答范围 |

## 8. Prompt 的协作管理

| 角色 | 职责 |
|---|---|
| PM | 定义业务规则、示例集、验收标准（prompt 里的「需求」部分） |
| 开发 | 工程化、模板化、测试、部署 |
| 运营/领域专家 | 提供示例、审核输出、维护知识库 |
| 所有人 | 改 prompt 走评审 + 记录 |

> ★ 给非技术同事的**可视化 prompt 编辑能力**（如后台可编辑 + 预览）能极大提升迭代速度，但必须配 eval 回归与审批。

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| prompt 散落各处 | 无人知道当前用的是哪个 | 集中管理 + 版本化 |
| 改了不测 | 悄悄变坏 | 强制 eval 回归 |
| 硬编码在代码 | 改一次发一次版 | 外置 + 热更新 |
| prompt 越写越长 | 成本涨、注意力稀释 | 精简、拆分为多步 |
| 只靠描述不给示例 | 效果不稳定 | 补 3-5 个示例 |
| 无变更记录 | 无法追溯为什么变差 | CHANGELOG |
| 用户输入直接拼接 | 注入风险 | 结构化分隔 + 转义 |
| 温度等参数不记录 | 复现不了结果 | 参数随 prompt 一起版本化 |
| 一人独管 prompt | 知识孤岛 | 团队可见可评审 |

## 10. Checklist

- [ ] prompt 集中管理、版本化，有变更记录
- [ ] 使用模板变量，与代码分离，支持热更新
- [ ] 系统 prompt 含角色/目标/规则/输出格式/示例
- [ ] 每次改动跑 eval 测试集对比
- [ ] 发布走小流量灰度，可一键回滚
- [ ] 有 prompt injection 等防御设计
- [ ] 参数（温度、模型、版本）与 prompt 一并记录
- [ ] 非技术同事可在受控环境下参与优化
