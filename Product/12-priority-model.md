# 12 · 优先级模型：怎么决定先做什么

## 1. 为什么需要模型

优先级冲突的本质是**资源有限**。没有模型时，排序靠「谁嗓门大」，团队必然内耗。模型的作用是**把主观判断变成可讨论的量化输入**。

> 注意：模型给出的是**讨论的起点**，不是自动答案。输入是估计值，输出也只作参考。

## 2. RICE（最常用）

```
RICE = (Reach × Impact × Confidence) / Effort
```

| 因子 | 含义 | 取值方式 |
|---|---|---|
| **R**each 触达 | 一个周期里影响多少人 | 实际人数/会话数 |
| **I**mpact 影响 | 对单个用户的影响程度 | 3=巨大，2=高，1=中，0.5=低，0.25=极小 |
| **C**onfidence 信心 | 你对估计的把握 | 100%=高，80%=中，50%=低 |
| **E**ffort 投入 | 人月数 | 开发+设计+测试总工时 |

示例：

| 需求 | Reach | Impact | Conf | Effort | RICE |
|---|---|---|---|---|---|
| 批量生成 | 5000/月 | 2 | 80% | 2 人月 | 4000 |
| 模板库 | 8000/月 | 1 | 90% | 3 人月 | 2400 |
| 导出 PDF | 2000/月 | 3 | 70% | 0.5 人月 | 8400 |

→ 排序：导出 PDF > 批量生成 > 模板库

**优点**：量化、可比较。**缺点**：依赖估计准确性，不适合战略型需求。

## 3. MoSCoW（范围分类）

Must / Should / Could / Won't —— 详见 11 篇。适合**版本范围内**的分类，不适合跨版本排序。

## 4. KANO（满意度分类）

基本型 → 期望型 → 兴奋型。**基本型永远最优先**（缺了它是致命的），即使 RICE 分不高。

```
排序逻辑：
① 所有基本型未达标项（补齐底线）
② 期望型里 RICE 高的（拉开差距）
③ 兴奋型里成本低的（制造惊喜）
```

## 5. WSJF（加权最短作业优先，SAFe）

```
WSJF = 经济性(商业价值 + 时间关键性 + 风险降低/机会创造) / 作业规模
```

适合**大型团队/多条业务线**排产，尤其强调「时间关键性」（有窗口期的机会）。

## 6. 其他实用模型

| 模型 | 适用场景 | 核心思路 |
|---|---|---|
| **价值/成本矩阵** | 快速粗排 | 四象限：高价值低成本先做 |
| **机会分（JTBD）** | 需求挖掘阶段 | 重要性 + (重要性 − 满意度) |
| **二八法则** | 聚焦 | 找出贡献 80% 价值的 20% 功能 |
| **ICE** | 增长实验排序 | (Impact × Confidence) / Ease |
| **技术债 vs 新功能** | 迭代平衡 | 每迭代预留 15-20% 处理债 |

## 7. 优先级分配的比例建议

```
每迭代资源分配（参考）：
├── 新功能/业务价值      50-60%
├── 体验优化            15-20%
├── 技术债/稳定性        15-20%
└── 探索性/实验          10%
```

> 只做新功能的产品会在一年后变得难以维护；只还技术债的产品会被市场抛弃。

## 8. 排序的常见干扰因素（要识别并管理）

| 干扰 | 表现 | 应对 |
|---|---|---|
| HiPPO（最高薪者意见） | 老板一句话插队 | 用数据把影响量化给他看，让他自己权衡 |
| 大客户绑架 | 一个客户要求改路线 | 单独评估，评估「这个需求代表多少人」 |
| 沉没成本 | 做了很久不舍得停 | 只按未来价值决策 |
| 近期偏差 | 刚被投诉的就排最前 | 看频次数据而非单次事件 |
| 技术兴趣 | 团队想做炫的技术 | 回到用户价值与指标 |

## 9. ★ AI 项目的优先级特殊因子

| 因子 | 说明 |
|---|---|
| **成本权重进 Effort** | 除开发工时，还要算持续推理成本（每月多少钱） |
| **不确定性高** | Confidence 要打得低（50-70%），因为 AI 效果难预测 |
| **先做 spike** | 技术不确定性高的需求，先排一个「可行性验证」任务（1-3 天）再评估 |
| **质量基线优先** | 输出质量不达标时，加功能只会放大不满 |
| **模型演进风险** | 强依赖某模型独家能力的需求要谨慎（可能被换代打乱） |
| **数据准备工作** | RAG 类需求的数据清洗工作量常被严重低估（常占 50%+ 工时） |

## 10. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 所有需求都是 P0 | 等于没有优先级 | 强制 P0 ≤ 60% 容量 |
| 模型算完不改 | 机械按分数执行 | 考虑战略、依赖、学习价值 |
| 估计不准 | Reach/Effort 拍脑袋 | 用历史数据校准，定期复盘准确率 |
| 忽略依赖关系 | 高分的做不了（被依赖卡住） | 排序时检查依赖图 |
| 优先级天天变 | 团队无所适从 | 迭代内锁定，变更走流程 |
| 只排需求不排债 | 系统越来越慢 | 固定比例留给技术债 |

## 11. Checklist

- [ ] 有统一的打分模型（推荐 RICE）并在需求池里留痕
- [ ] P0 不超过迭代容量的 60%
- [ ] 基本型（KANO）需求已全部达标或已排入
- [ ] 每迭代预留技术债/稳定性配额
- [ ] AI 需求的 Effort 包含持续推理成本与数据准备工时
- [ ] 高不确定性需求先排可行性验证（spike）
