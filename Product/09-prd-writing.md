# 09 · PRD 撰写：把需求写成可执行的规格

## 1. PRD 的第一性原则

> PRD 的目的不是「记录」，而是**让所有人对「要做什么」达成同一理解**，并且**可验收**。

判断一份 PRD 好不好的唯一标准：**开发读完能不能直接开工，测试读完能不能直接写用例**。

## 2. PRD 的结构（推荐模板）

```markdown
# 【功能名】PRD v1.0

## 0. 一句话结论
为【用户】解决【问题】，本期交付【范围】，成功标准是【指标】。

## 1. 背景与目标
- 问题现状（数据支撑）
- 用户与场景（画像 + JTBD）
- 本次目标（可衡量）
- 不做什么（Not in scope）★ 必写

## 2. 需求详述
### 2.1 用户故事
- 作为【角色】，我希望【动作】，以便【价值】

### 2.2 功能清单
| ID | 功能点 | 优先级(P0/P1/P2) | 说明 |

### 2.3 业务流程
（流程图 / 泳道图）

### 2.4 页面与交互
（原型链接 + 逐页说明）

### 2.5 规则与逻辑
（状态机、计算公式、边界条件）

## 3. 边界与异常 ★
| 场景 | 处理 | 文案 |
|---|---|---|
| 空数据 | 展示引导态 | 「还没有记录，点这里试试」 |
| 超长内容 | 截断 + 展开 | — |
| 请求失败 | 重试 + 兜底 | 「生成失败，已保留你的输入」 |
| 超时 | 中断 + 后台完成提醒 | — |
| 权限不足 | 禁用 + 说明 | — |
| 并发冲突 | 覆盖提示 | — |

## 4. 数据与技术说明（协作项）
- 涉及的数据表/字段变更
- 接口依赖
- 性能要求（QPS、响应时间、数据量）
- 兼容性（浏览器/系统版本）

## 5. 埋点与指标
| 事件 | 触发时机 | 属性 | 用途 |
|---|---|---|---|

## 6. 验收标准（AC）★
- [ ] 场景1：给定…，当…，则…
- [ ] 场景2：…

## 7. 依赖与风险
| 依赖/风险 | 影响 | 应对 | 负责人 |

## 8. 上线计划
- 灰度范围、放量节奏、回滚方案
- 运营/客服同步事项

## 9. 附录
- 竞品参考、术语表、历史讨论链接
```

## 3. 每一节怎么写（要点）

### 背景：用数据说话

```
❌ 「用户反馈希望有批量功能」
✅ 「近 30 天，62% 的用户单日生成次数 ≥ 5 次（埋点：gen_click），
    客服工单中『能不能一次生成多条』出现 41 次。
    目标：单日多次用户的人均耗时从 18min 降到 8min。」
```

### 功能清单：颗粒度到「可估工时」

```
❌ 「优化生成体验」
✅ 「P0 支持一次输入生成 1-10 条结果（默认 3 条）
    P0 生成结果支持单条复制与全选复制
    P1 支持对单条结果『再生成』
    P2 支持结果排序（按时长/质量分）」
```

### 规则与逻辑：写成判定表

```markdown
| 条件 | 结果 |
|---|---|
| 输入为空 | 按钮置灰，不调用 |
| 输入 > 2000 字 | 提示截断，截断后继续 |
| 剩余额度 = 0 | 弹窗引导升级，不允许生成 |
| 生成中再次点击 | 按钮变为「停止」 |
| 生成失败 | 保留输入 + 重试按钮 + 错误码文案 |
```

## 4. 验收标准（AC）写法：Given-When-Then

```gherkin
场景：额度不足时生成
  Given 用户是免费版且当日剩余额度为 0
  When  用户点击「生成」
  Then  不调用模型接口
  And   展示升级引导弹窗
  And   用户输入内容被保留不清空
```

AC 的三条铁律：

1. **可测试**：每条都能被 QA 转成用例
2. **覆盖异常**：正常路径 1 条，异常路径 ≥ 3 条
3. **无歧义**：不出现「尽快」「合理」「适当」这类词

## 5. 优先级标记

| 标记 | 含义 |
|---|---|
| P0 / Must | 本期必须有，缺了不能上线 |
| P1 / Should | 重要，可延到下个小版本 |
| P2 / Could | 有更好，资源紧张就砍 |
| P3 / Won't | 本期明确不做 |

> 每个版本 P0 不超过总工作量的 60%，否则没有缓冲。

## 6. 变更管理

```
变更申请 → 影响评估（工时/风险/范围） → 决策（本版做/下版做/砍） → 更新 PRD + 通知全员
```

PRD 顶部必须有**修订记录**：

```markdown
| 版本 | 日期 | 修改内容 | 原因 | 影响范围 |
```

> 铁律：**任何口头约定的需求变更，都必须回到 PRD 更新**。否则上线时必然扯皮。

## 7. ★ AI 功能的 PRD 额外必写项

| 项 | 说明 | 示例 |
|---|---|---|
| **输入规格** | 允许什么格式、长度限制、是否必填 | 输入 5-500 字，支持粘贴 |
| **输出规格** | 格式（JSON/文本/Markdown）、结构、长度 | 输出合法 JSON，字段：title/summary/tags |
| **示例集** | 3-5 个输入-输出样例（few-shot） | 见附录 |
| **质量基线** | 可接受的准确率/格式合格率 | 格式合规率 ≥ 98%，人工抽检满意度 ≥ 4/5 |
| **失败与降级** | 超时、模型报错、输出不合法怎么办 | 重试 1 次 → 降级小模型 → 兜底模板 |
| **成本预算** | 单次成本上限、日均调用上限 | 单次 ≤ ¥0.03，日成本 ≤ ¥500 |
| **延迟要求** | 首字延迟、总时长 | 首 token ≤ 1.5s，总时长 ≤ 15s |
| **可控性** | 用户能否编辑/重生成/停止 | 支持停止、支持局部重写 |
| **数据安全** | 用户输入是否送第三方、是否留存训练 | 明确告知，提供关闭选项 |
| **Evals 集** | 上线前的测试集与通过线 | 100 条测试集，通过率 ≥ 90% |

## 8. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| PRD 写「优化体验」 | 无法估价无法验收 | 拆成具体可测的功能点 |
| 只写 happy path | 上线后异常频出 | 边界与异常表必写 |
| 原型即 PRD | 逻辑规则全靠猜 | 原型 + 规则表 + AC 三件套 |
| 没有「不做什么」 | 范围无限膨胀 | Not in scope 必写 |
| 写完不改 | 口头变更满天飞 | 强制走变更记录 |
| AC 不可测 | 「响应迅速」 | 写具体数值 |
| AI 功能没写失败降级 | 模型一挂全线崩 | 降级路径写进 PRD |
| 埋点后补 | 上线后发现没数据 | 埋点随 PRD 一起评审 |

## 9. Checklist

- [ ] 顶部一句话结论 + 目标指标
- [ ] 明确写了 Not in scope
- [ ] 功能清单颗粒度可估工时，带 P0/P1/P2
- [ ] 有边界与异常场景表
- [ ] AC 用 Given-When-Then，覆盖异常
- [ ] 埋点方案随 PRD 一起评审
- [ ] AI 功能包含输出规格、质量基线、降级、成本预算
- [ ] 有修订记录表
