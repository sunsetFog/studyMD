# 32 · AI 产品基础：能力边界、可行性与成本

## 1. AI 产品与传统产品的三个根本差异

| 维度 | 传统软件 | AI 产品 |
|---|---|---|
| 行为 | 确定性（同输入必同输出） | **概率性**（同输入可能不同输出） |
| 正确性 | 可以做到 100% | **存在错误率**，只能提升不能消除 |
| 成本 | 边际成本趋近 0 | **每次调用都有成本** |
| 迭代 | 改代码 | 改代码 + 改 prompt + 换模型 + 改数据 |
| 退化 | 一般不退化 | **会漂移**（模型更新、数据变化导致质量变化） |

理解这三点，后面所有的设计决策都由此推导。

## 2. 能力边界：什么适合 AI，什么不适合

### 适合 AI 的特征

```
✅ 输入模糊/多样（自然语言、非结构化）
✅ 输出容忍一定误差（创意、摘要、建议）
✅ 需要「理解」而非「检索」（语义匹配、归纳）
✅ 规则难以穷举（审核、分类、意图识别）
✅ 人工做很贵很慢（写初稿、整理、翻译）
✅ 有人工兜底（结果可被检查修正）
```

### 不适合 AI 的场景

```
❌ 要求 100% 准确且无法人工核对（财务结算、法律判决、医疗诊断结论）
❌ 规则清晰且稳定（用代码写死更可靠更便宜）
❌ 延迟要求极低（< 200ms 的实时控制）
❌ 无数据、无领域知识且需高精度
❌ 错误代价极高且不可逆（自动转账、自动发帖）
❌ 需要可解释的强因果推理
```

### 判断矩阵

```
              误差容忍度
              高          低
AI 价值  高 │ AI 主战场 │ AI 辅助 + 人工审核
         低 │ 可用可不  │ 别用 AI（写代码）
```

## 3. 可行性评估（立项前必做）

### 五问

```
① 现在最好的模型能做到什么水平？（自己先手工跑 20 个真实样本）
② 达到业务需要的水平了吗？差多少？
③ 差的部分靠什么补？（更好的 prompt / RAG / 微调 / 工作流拆分 / 人工）
④ 补上的成本是多少？（时间 + 钱 + 复杂度）
⑤ 如果只能到 80 分，业务上可用吗？
```

### 可行性验证（Spike）的做法

```
时间盒：1-3 天，不超过 1 周
步骤：
  ① 收集 20-50 个真实输入样本（★ 必须真实，不能自己编）
  ② 定义「合格」标准（可判定的）
  ③ 手工跑模型（可以用 Playground，不用写代码）
  ④ 统计合格率、典型失败模式
  ⑤ 尝试 2-3 种改进（prompt / 加上下文 / 拆步骤）
  ⑥ 给出结论：可行 / 有条件可行 / 不可行，以及需要的成本
产出：一份 spike 报告 + 测试结果表 + 建议方案
```

> 铁律：**没有 spike 就不要立项**。很多 AI 项目死在「以为能做」上。

## 4. 成本模型（AI 产品最容易被忽视的部分）

### 成本构成

```
总成本 = 推理成本 + 检索成本 + 存储成本 + 人工审核成本 + 基础设施

推理成本 = 输入 token × 输入单价 + 输出 token × 输出单价
  注意：输入（尤其长上下文）通常比输出便宜，但量大
```

### 计算示例

```
场景：AI 客服问答，日均 10000 次
  单次输入 ≈ 1500 token（含系统 prompt + 检索上下文）
  单次输出 ≈ 400 token
  模型价格（示例）：输入 ¥15/百万 token，输出 ¥75/百万 token

单次成本 = 1500/1e6 × 15 + 400/1e6 × 75 = 0.0225 + 0.03 = ¥0.0525
日成本 = 10000 × 0.0525 = ¥525
月成本 ≈ ¥15,750
```

若定价 ¥99/月，需要 **159 个付费用户才覆盖推理成本**（还没算其他成本）。

### 降本手段（按优先级）

| 手段 | 效果 | 注意 |
|---|---|---|
| 缩短 prompt / 上下文 | 直接减少输入 token | 别牺牲必要信息 |
| 缓存（相同/相似请求） | 命中率 20-40% 时可大幅降本 | 需设计缓存键 |
| 小模型处理简单任务 | 成本降 10-50 倍 | 路由策略要准 |
| 分级路由（意图 → 模型） | 综合最优 | 复杂度上升 |
| 减少输出长度（限字数） | 直接省 | 可能影响体验 |
| 批量/异步处理 | 可用批量 API（通常半价） | 延迟换成本 |
| 结果复用（模板化） | 高频问题走缓存答案 | 需维护 |
| 蒸馏/微调小模型 | 长期最优 | 前期投入大 |

### 成本红线

```
必须设定：
① 单用户日/月成本上限（超过则限流）
② 全局日成本上限（超过则降级到便宜模型或只读模式）
③ 异常检测（单用户调用量突增 → 风控）
④ 成本告警（日成本超过预算 80% 告警）
```

> AI 产品的成本失控案例极多：一个循环调用的 bug 一夜烧掉数万元。**限流与熔断是必选项，不是可选项**。

## 5. 技术路径选择

| 路径 | 适用 | 成本 | 周期 |
|---|---|---|---|
| **纯 Prompt** | 通用任务、模型已具备能力 | 低 | 小时-天 |
| **Prompt + 示例（Few-shot）** | 需要特定格式/风格 | 低 | 天 |
| **RAG（检索增强）** | 需要私有/最新知识 | 中 | 周 |
| **工作流 / 多步拆分** | 复杂任务、需要可靠性 | 中 | 周 |
| **Agent（工具调用）** | 需要外部动作/多步决策 | 中高 | 周-月 |
| **微调（Fine-tune）** | 特定风格/格式、有大量数据 | 高 | 周-月 |
| **自训练模型** | 极特殊需求 | 极高 | 月+ |

**选型原则**：从最轻的方案开始，遇到明确的瓶颈再升级。

```
Prompt → +示例 → +RAG → +工作流/Agent → 微调
      （每升一级，成本与复杂度大幅上升）
```

> 现实经验：**80% 的问题靠 prompt + RAG 就能解决**。微调常常不是必需品，且会锁定模型。

## 6. 模型选型的考量

| 维度 | 说明 |
|---|---|
| 能力 | 在你的任务上的实测表现（不是排行榜分数） |
| 成本 | 输入/输出单价，长上下文价格 |
| 延迟 | 首 token 延迟、总延迟（影响体验） |
| 稳定性 | 可用性、限流策略、是否有 SLA |
| 上下文长度 | 是否满足你的场景 |
| 合规 | 数据存储地、是否用于训练、备案要求（★ 国内必查） |
| 多模态 | 是否需要图像/语音 |
| 可替换性 | 避免深度绑定某家独家能力 |

**建议架构**：通过模型网关/抽象层接入，**永远保留切换能力**。

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 高估模型能力 | 立项时以为能做，做了发现不行 | 强制 spike |
| 低估数据工作 | RAG 效果差是因为知识库脏 | 数据清洗占 50% 工时，单独排期 |
| 无视成本 | 用户越多亏越多 | 成本模型 + 红线 + 告警 |
| 深度绑定一个模型 | 供应商涨价/下线就完蛋 | 抽象层 + 备选 |
| 追求 100% 准确 | 永远达不到，项目拖死 | 定合理基线 + 人工兜底 |
| 一上来就微调 | 成本高、周期长、锁死 | 先试 prompt/RAG |
| 忽略延迟 | 功能对但太慢没人用 | 延迟纳入验收标准 |
| 不考虑合规 | 上线后被叫停 | 立项就查数据合规 |
| 长上下文滥用 | 什么都塞进上下文，成本暴涨 | 用检索而非全量塞入 |

## 8. Checklist

- [ ] 做过 spike，有真实样本的合格率数据
- [ ] 明确了「合格」的质量基线与可接受的错误率
- [ ] 算过单次成本、月成本、单用户毛利
- [ ] 设定了成本红线、限流、降级方案
- [ ] 技术路径从最轻方案起步（prompt → RAG → Agent → 微调）
- [ ] 模型接入有抽象层，可切换
- [ ] 查过数据合规与模型备案要求
- [ ] 延迟指标写进了验收标准
