# 30 · 沟通与协作：把事情说清、把事情推成

## 1. 沟通的核心原则

```
① 结论先行（金字塔原理）
② 对不同的对象说不同的话（受众导向）
③ 有证据，区分事实与判断
④ 明确「需要对方做什么」（行动召唤）
```

## 2. 结论先行（金字塔）

```
❌ 流水账：我们做了调研，访谈了 8 个用户，发现有 3 个问题……（3 分钟后）所以建议做 X
✅ 结论先行：建议做 X。理由有三：① ② ③。数据支撑如下……
```

结构：**结论 → 理由（3 条）→ 证据 → 行动建议**。

| 场景 | 结构 |
|---|---|
| 汇报 | 结论 → 数据 → 建议 → 需要的支持 |
| 提案 | 问题 → 方案 → 收益 → 成本 → 风险 |
| 同步 | 进展 → 风险 → 下一步 → 需要的帮助 |
| 复盘 | 目标 → 结果 → 差异原因 → 改进项 |

## 3. 对不同角色怎么讲

| 对象 | 关心 | 怎么说 |
|---|---|---|
| 老板/决策者 | 结果、风险、资源 | 结论 + 关键数据 + 需要的决策（给选项） |
| 开发 | 为什么做、边界、优先级 | 场景 + AC + 取舍理由 + 技术约束 |
| 设计师 | 用户、场景、体验目标 | 画像 + 旅程 + 体验目标（不给具体设计） |
| 测试 | 边界、异常、验收 | AC + 异常场景清单 |
| 运营/销售 | 卖点、时间、影响 | 价值主张 + 上线时间 + 注意事项 |
| 客户 | 解决什么问题、什么时候 | 价值 + 时间窗（不承诺过细） |

## 4. 需求评审中的沟通技巧

| 技巧 | 说明 |
|---|---|
| 先讲背景 | 不讲背景的评审必然变成审美讨论 |
| 主动暴露风险 | 「这个方案我最没底的是 X」 |
| 区分决策与讨论 | 「这条需要当场决策，那条会后聊」 |
| 记录并复述 | 「我理解你的意思是…，对吗」 |
| 不当场承诺 | 「我确认后今天回复你」 |
| 控制会议 | 发散时拉回：「这个记进需求池，会后评估」 |

## 5. 冲突处理

| 冲突类型 | 处理 |
|---|---|
| 需求优先级争议 | 回到目标与数据，用排序模型说话 |
| 技术可行性争议 | 让开发给方案与成本，PM 判断价值是否匹配成本 |
| 体验 vs 工期 | 明确「最小可接受方案」+ 后续优化计划 |
| 跨部门资源争夺 | 上升到共同目标，请上级按战略决策 |
| 与老板意见不同 | 给数据与选项，让决策者承担决策（不要硬刚也不要盲从） |

**原则**：对事不对人；先确认共同目标（通常都是「产品成功」），再讨论路径。

## 6. 向上汇报

```
频率：周报（进度 + 风险 + 需要的支持）
内容：
  ① 本周关键进展（3 条内）
  ② 指标变化（用数据）
  ③ 风险与阻塞（★ 最重要，越早暴露越好）
  ④ 下周计划
  ⑤ 需要决策/支持的事项（明确写出，别暗示）
```

**汇报的三条铁律**：

1. **坏消息要早说**（越晚说代价越大，且会失去信任）
2. **带方案汇报**（不要只抛问题，给 2-3 个选项 + 你的推荐）
3. **不要粉饰数据**（数据会说话，掩盖会失去信任）

## 7. 文档与同步机制

| 场景 | 形式 | 频率 |
|---|---|---|
| 项目进度 | 看板 + 周报 | 每周 |
| 需求 | PRD（唯一权威来源） | 变更即更新 |
| 决策 | 决策记录（ADR/会议纪要） | 每次决策 |
| 指标 | 看板 + 月报 | 每月 |
| 知识沉淀 | 项目 Wiki | 持续 |

**减少无效会议**：

```
① 有明确议程与目标，否则不开
② 会前发材料，参会者必须预读
③ 控制人数（决策者 + 执行者，旁听可看纪要）
④ 会议必须有产出（决策/待办/负责人/时间）
⑤ 24h 内出纪要
```

## 8. 推动力：没有授权怎么推动

```
① 建立共识：让相关方理解「为什么」，而不只是「做什么」
② 小胜积累：先做成一件小事建立信任
③ 主动同步：不等人问，定期发送进展
④ 降低他人成本：把需求整理好、把材料准备好，让别人容易配合
⑤ 明确责任与时间：每个待办都有人和日期
⑥ 公开透明：进度可视化（看板），让拖延自然暴露
⑦ 升级机制：阻塞超过 X 天自动升级
```

## 9. ★ AI 项目的沟通特殊点

| 点 | 说明 |
|---|---|
| **效果要用 demo 说话** | 文字描述 AI 效果几乎无效，必须现场跑 |
| **不确定性要明说** | 「现在能到 80 分，90 分需要 X 且不确定」——别给确定性幻觉 |
| **成本要提前说** | 决策者往往不知道 AI 有持续成本，要主动量化 |
| **失败要说清原因** | 是 prompt 问题、模型能力问题还是数据问题（不同原因不同解法） |
| **期望管理** | 对内部也要管理期望，避免 demo 效果被当成稳定能力 |
| **跨职能理解鸿沟** | 让非技术同事理解「概率性输出」，用具体案例说明 |

## 10. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 讲半天没结论 | 听众不知道你要什么 | 结论先行，明确行动召唤 |
| 只抛问题不带方案 | 把球踢给上级 | 带 2-3 个选项 + 推荐 |
| 坏消息藏着 | 爆雷时更严重 | 早暴露 |
| 同一件事对不同人说法不同 | 信息混乱 | 单一事实来源（文档） |
| 会议无纪要 | 决策被遗忘/否认 | 24h 内出纪要 |
| 口头承诺不落文档 | 事后扯皮 | 结论必须进文档 |
| 用形容词代替数据 | 「效果还不错」 | 给数字 |
| AI 效果只靠描述 | 期望失真 | 现场 demo + 真实案例 |

## 11. Checklist

- [ ] 重要沟通都是「结论先行 + 3 条理由 + 行动建议」
- [ ] 对不同角色用不同的表达重点
- [ ] 坏消息早说，且带解决方案
- [ ] 会议有议程、有产出、24h 内出纪要
- [ ] 每个待办有负责人与时间
- [ ] AI 项目的效果沟通以 demo 和真实案例为主，明确不确定性
