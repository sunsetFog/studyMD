# 11 · MVP：最快验证假设的最小交付

## 1. MVP 到底是什么

> MVP = 用**最小成本**验证**最关键假设**的版本。

MVP **不是**「功能残缺的正式版」，而是「**只为学习而存在**的版本」。它的成功标准是**学到了东西**，不是用户满意。

常见误解：

| 误解 | 正解 |
|---|---|
| MVP = 精简功能版 | MVP 是实验工具，可以很丑但必须能验证 |
| MVP 要能用就行 | MVP 必须包含「完整的价值闭环」，否则验证无效 |
| MVP 是最终产品的第一版 | 很多 MVP 会被扔掉（如 Wizard of Oz） |

## 2. 四种 MVP 形态（按成本从低到高）

| 形态 | 做法 | 验证什么 |
|---|---|---|
| **假门（Fake Door）** | 做个按钮/落地页，点了显示「敬请期待」 | 需求强度、点击率 |
| **人工后台（Wizard of Oz）** | 前端像 AI，实际人工响应 | 用户是否接受这种交互、愿意付多少钱 |
| **单功能 MVP** | 只做一条最核心路径 | 核心 value 是否成立 |
| **技术原型** | 拼凑现有 API 快速搭出可用品 | 技术可行性 + 体验 |

> ★ AI 产品特别适合「人工后台 MVP」：**先手动用 ChatGPT 给用户产出结果**，验证他是否愿意为这个结果付费，再决定是否开发。成本几乎为零。

## 3. MVP 的设计步骤

```
① 列出你的核心假设（按风险从高到低排序）
     例：假设A 用户愿意用 AI 写周报
         假设B 用户愿意为此付 99 元/月
         假设C 我们能稳定生成合格周报
② 选出风险最高、最影响生死的 1-2 个假设
③ 设计验证它的最小实验（不是最小产品）
④ 设定成功/失败的判定线（先定好止损线）
⑤ 执行并收集数据
⑥ 决策：坚持 / 调整 / 放弃（Pivot）
```

## 4. 范围控制：砍需求的四种刀法

```
① 砍人群：只服务最典型的一类用户（如只做电商运营，不做自媒体）
② 砍场景：只做最高频的一个场景（如只做周报，不做日报月报）
③ 砍路径：只保留最短主路径，边缘功能全砍
④ 砍质量：非核心部分接受手工/粗糙（后台人工处理也算）
```

**判断能不能砍的准则**：砍掉它，核心假设还能验证吗？能 → 砍。

## 5. 功能优先级：莫斯科法则（MoSCoW）

| 级别 | 含义 | 占比建议 |
|---|---|---|
| **M** Must have | 没有就不能上线 | ≤ 60% |
| **S** Should have | 重要但可延后 | 20% |
| **C** Could have | 锦上添花 | 20% |
| **W** Won't have | 本期明确不做 | — |

**W 必须写出来并公开**，否则它会在开发中途悄悄回来。

## 6. Walking Skeleton（骨架先行）

先打通「端到端最薄的一条链路」，哪怕只有一个功能、一个用户、一条数据：

```
用户点按钮 → 后端调用 → 模型返回 → 前端展示 → 埋点上报
```

好处：尽早暴露集成风险（尤其是 AI 产品的延迟、格式、成本问题），而不是最后才发现。

## 7. MVP 之后：迭代节奏

```
        ┌─────────────────────────────┐
        ↓                             │
   构建 → 衡量 → 学习 → （坚持/转向）─┘
   Build  Measure  Learn   Pivot/Persevere
```

每一轮都要有明确的学习目标，不是「继续完善功能」。

## 8. ★ AI 产品的 MVP 特殊策略

| 策略 | 说明 |
|---|---|
| **先人工后自动** | 人工产出验证价值 → 再用模型自动化（避免「自动化一个没人要的东西」） |
| **先窄后宽** | 只做一个垂直场景做到极致（如「写小红书标题」），比做一个「万能写作助手」更容易成功 |
| **不追求通用** | 通用 = 与 ChatGPT 正面竞争 = 没有优势 |
| **手工兜底合法** | MVP 阶段后台人工修正 AI 输出完全可以接受 |
| **验证成本模型** | 早期就要算：单次成本 × 预期频次 vs 定价，毛利能不能为正 |
| **别等模型变强** | 用现在的模型做到可用即可；模型进步是加分项不是前提 |

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| MVP 做成了正式版 | 开发 6 个月才上线 | 用「假设验证」而非「功能完整」定义完成 |
| 砍错了东西 | 砍掉了价值闭环 | 保留完整主路径，砍的是分支 |
| 没定成功线 | 上线后无法判断是否成功 | 上线前写好判定指标与止损线 |
| 怕丑不敢上 | 打磨 3 个月 | 内部/小范围灰度先上 |
| 数据不足就下结论 | 10 个用户说好就 All in | 设定最小样本量与观察周期 |
| 无限期 MVP | 半年还在 MVP | MVP 有明确时限（2-6 周） |
| 只做加法 | 迭代只加功能 | 每次迭代也问「能删掉什么」 |

## 10. Checklist

- [ ] 核心假设按风险排序，MVP 只为验证 Top 1-2 个
- [ ] 上线前已写好判定指标与止损线
- [ ] 砍需求用过四种刀法，保留完整价值闭环
- [ ] MoSCoW 分类完成，W 清单已公开
- [ ] 有明确的时限与下一轮决策点
