# 21 · 数据分析：从数据里得到结论

## 1. 分析的四个层次

| 层次 | 回答 | 方法 | 价值 |
|---|---|---|---|
| 描述性 | 发生了什么 | 报表、看板 | 低 |
| 诊断性 | 为什么发生 | 下钻、对比、归因 | 中 |
| 预测性 | 会发生什么 | 模型、趋势外推 | 高 |
| 处方性 | 该做什么 | 实验、策略优化 | 最高 |

大部分团队停留在第一层（看板）。真正推动决策的是第二层和第四层。

## 2. 分析的标准流程

```
① 明确问题（不是「看看数据」，而是「上周留存为什么掉了 3pp」）
② 提出假设（列出可能原因，按可能性排序）
③ 找数据验证（对比、下钻、分群）
④ 排除/确认（用数据证伪，而不是找数据支持自己的结论）
⑤ 得出结论与建议（做什么，预期效果）
⑥ 跟进验证（做了之后看指标）
```

## 3. 常用分析方法

### ① 对比分析（最基础也最有用）

| 维度 | 用法 |
|---|---|
| 时间对比 | 环比（vs 上周）、同比（vs 去年同期） |
| 分群对比 | 新老用户、渠道、版本、套餐 |
| 横向对比 | 与行业基准、竞品公开数据 |
| A/B 对比 | 实验组 vs 对照组 |

> 绝对值没有意义，对比才有意义。看任何数字先问「和什么比」。

### ② 下钻（Drill-down）

```
留存掉了 3pp
 → 哪个渠道掉的？（渠道 A 掉了 8pp）
   → 哪天进来的用户掉的？（11/3 那批）
     → 那天发生了什么？（发版 + 投放素材变更）
       → 是版本问题还是素材问题？（分版本看：新版留存低 → 版本问题）
```

**维度拆解清单（MEMC）**：用户属性、时间、渠道、版本、地域、设备、行为分层。

### ③ 漏斗分析

```
访问 10000 → 注册 3000 (30%) → 激活 1500 (50%) → 付费 150 (10%)
```

要点：
- 看**转化率**和**流失绝对数**（有时转化率低但流失少，不值得优化）
- 看**中位耗时**（某一步耗时异常说明有卡点）
- 分群看漏斗（新老用户漏斗形态完全不同）
- 漏斗要有时间窗口（如「注册后 7 日内付费」）

### ④ 留存分析（Cohort）

```
        第0天 第1天 第3天 第7天 第30天
11/01    100%   42%   30%   22%    12%
11/08    100%   45%   33%   25%    14%  ← 版本优化后
```

- **留存曲线是否走平**（走平 = 找到 PMF 的信号）
- 分群留存：完成过核心行为的用户 vs 没完成的（差异巨大）
- 见 25 篇详述

### ⑤ 归因分析

| 方法 | 说明 | 问题 |
|---|---|---|
| 末次归因 | 都算给最后一次触点 | 忽略前期铺垫 |
| 首次归因 | 都算给第一次 | 忽略转化推动 |
| 线性归因 | 平均分 | 简单但不精确 |
| 时间衰减 | 越近权重越高 | 常用 |
| 数据驱动（Shapley） | 按边际贡献 | 复杂但准确 |

### ⑥ 分布分析（不要只看平均值）

```
平均响应 3s，看起来还行
 → 看分布：P50=0.8s，P95=12s，P99=30s
 → 5% 的用户体验极差，他们可能正是对流失最敏感的意见领袖
```

**永远看分位数（P50/P90/P95/P99）与分布图**，平均值会被极端值掩盖。

## 4. 统计陷阱（必须知道）

| 陷阱 | 说明 | 应对 |
|---|---|---|
| 辛普森悖论 | 分组都涨，总体反而跌（权重变化） | 分群看 + 看结构变化 |
| 幸存者偏差 | 只看留下的人 | 也要分析流失用户 |
| 相关≠因果 | 冰淇淋销量与溺水数正相关 | 做实验验证因果 |
| 基数太小 | 3 个用户说好 | 设最小样本量 |
| 多重比较 | 测 20 个指标总有 1 个显著 | 预先定主指标 |
| 选择性报告 | 只报好消息 | 预先注册实验 |
| 周期效应 | 周末/月初波动 | 用同比与完整周期 |
| 数据质量 | 埋点漏报、重复上报 | 先验证数据准确性 |

## 5. 数据驱动的边界

> 数据能告诉你「什么」，很难告诉你「为什么」。

- 数据 + 用户访谈 = 完整答案
- 数据适合优化已知方案，不适合发现全新机会（用户不知道没见过的东西）
- 小样本阶段靠定性，规模化后才靠定量
- 重要决策不要只看数据，还要看战略与直觉（数据有滞后性）

## 6. 常用 SQL 分析模式（产品经理够用版）

```sql
-- 1) 留存（按注册日期 cohort）
SELECT r.reg_date,
       DATEDIFF(a.active_date, r.reg_date) AS day_diff,
       COUNT(DISTINCT a.user_id) / COUNT(DISTINCT r.user_id) AS retention
FROM registrations r
LEFT JOIN actives a ON a.user_id = r.user_id
GROUP BY 1, 2;

-- 2) 漏斗
SELECT step, COUNT(DISTINCT user_id) AS uv,
       COUNT(DISTINCT user_id) / LAG(COUNT(DISTINCT user_id)) OVER (ORDER BY step_order) AS conv
FROM funnel_events GROUP BY step;

-- 3) 分位数
SELECT APPROX_PERCENTILE(latency_ms, 0.95) FROM requests WHERE dt = '2026-11-01';

-- 4) 分组对比（新老版本）
SELECT version, AVG(adopted) AS adopt_rate, COUNT(*) AS n
FROM gen_log GROUP BY version;
```

## 7. ★ AI 产品的数据分析特殊点

| 点 | 说明 |
|---|---|
| **质量指标难以自动计算** | 采纳率/满意度需埋点 + 人工抽检结合 |
| **要分析 prompt 日志** | 用户真实输入聚类，发现高频场景与失败模式 |
| **失败样本比成功样本重要** | 建立「bad case 库」，周会过一遍 |
| **成本归因** | 按用户/场景/模型拆分成本，找出亏损大户 |
| **模型版本对比** | 换模型时必须跑同一测试集对比（见 36 篇） |
| **延迟分布** | AI 延迟长尾严重，必须看 P95/P99 |
| **用户行为新形态** | 「反复重生成」「复制后大幅修改」都是质量差的信号 |
| **幻觉检测** | 用规则/模型抽检输出的事实性，统计幻觉率 |

## 8. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 先有结论再找数据 | 选择性解读 | 列假设 → 证伪 |
| 只看总量 | 掩盖结构问题 | 必做分群 |
| 只看平均值 | 长尾问题看不见 | 看分位数 |
| 数据不准就分析 | 结论全错 | 先校验埋点 |
| 指标掉了只汇报 | 没有建议 | 分析必带行动建议 |
| 混淆相关与因果 | 照着相关性改产品 | 用 A/B 验证 |
| 忽视样本量 | 10 个用户下结论 | 设最小样本 |
| AI 不看 bad case | 平均质量好但个案崩 | 建 bad case 库 |

## 9. Checklist

- [ ] 分析前先写清问题与假设
- [ ] 所有结论都有对比基准（时间/分群）
- [ ] 关键指标看分位数而非均值
- [ ] 漏斗、留存、分布三类基础分析能自己做
- [ ] 结论附带行动建议与预期收益
- [ ] AI 产品有 bad case 库与定期复盘机制
