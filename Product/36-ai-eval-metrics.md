# 36 · AI 质量评估：Evals 与线上指标

## 1. 为什么 AI 产品必须做 Evals

```
传统软件：测试通过 = 上线安全（确定性）
AI 产品：改任何东西（prompt/模型/参数/数据）都可能悄悄让质量变化
  → 没有 evals，你不知道自己是在变好还是变坏
```

**Evals（评测集）就是 AI 产品的单元测试 + 回归测试**。

## 2. 三层评估体系

```
① 离线评估（Evals）：上线前，固定测试集，快速、可重复
② 线上评估（行为指标）：真实用户行为，反映真实价值
③ 人工评估（抽检/盲评）：主观质量，金标准但贵
```

| 层 | 速度 | 成本 | 反映 | 用途 |
|---|---|---|---|---|
| 离线 | 分钟 | 低 | 能力 | 每次改动回归 |
| 线上 | 天-周 | 中 | 真实价值 | 长期监控 |
| 人工 | 小时-天 | 高 | 主观质量 | 校准前两者 |

## 3. 构建 Evals 测试集

### 步骤

```
① 收集真实输入（★ 必须来自真实用户/真实场景，不是自己编的）
② 定义「好输出」的标准（可判定）
③ 为每条样本标注期望（期望输出 或 评分标准 或 检查项）
④ 覆盖分类：
     - 典型场景（60%）：最常见的输入
     - 边界场景（20%）：超长、超短、空、多语言、特殊字符
     - 对抗场景（10%）：诱导、注入、越权提问
     - 历史 bad case（10%）：★ 每次线上出问题就加进来
⑤ 持续扩充（evals 是活资产，不是一次性工作）
```

### 规模建议

```
起步：30-50 条（能挡住明显退化）
成长：100-300 条（覆盖主要场景）
成熟：500+ 条 + 分场景子集合
```

### 测试集格式示例

```json
{
  "id": "case-001",
  "category": "typical",
  "input": "帮我写一封延期交付的道歉邮件，客户是XX公司",
  "context": {"tone": "专业", "length": "200字内"},
  "expectations": {
    "must_include": ["道歉", "延期原因", "新的交付时间"],
    "must_not_include": ["推卸责任的表述"],
    "format": "邮件格式，含主题与正文",
    "length_range": [100, 300]
  },
  "reference_output": "……（可选，用于相似度比较）"
}
```

## 4. 评分方法

| 方法 | 说明 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **规则校验** | 正则/JSON Schema/关键词/长度 | 快、稳定、便宜 | 只能查表面 | 格式、必含项 |
| **代码断言** | 自定义检查逻辑 | 灵活 | 要写 | 结构化输出 |
| **字符串相似度** | BLEU/ROUGE/编辑距离 | 简单 | 与质量相关性弱 | 有标准答案时 |
| **Embedding 相似度** | 与参考答案向量比较 | 语义层面的相似 | 阈值难定 | 开放式生成 |
| **模型评分（LLM-as-judge）** | 用强模型按评分标准打分 | ★ 灵活、接近人工 | 有偏差、有成本 | 主观质量 |
| **人工评分** | 人打分 | 金标准 | 慢、贵 | 校准与小样本 |

### LLM-as-Judge 的做法

```
评分 prompt：
  你会收到【任务描述】【输入】【AI 输出】。
  请按以下维度打分（1-5）：
    1. 相关性：是否回答了用户的问题
    2. 准确性：是否有事实错误
    3. 完整性：是否遗漏关键内容
    4. 格式：是否符合要求
    5. 语气：是否符合品牌风格
  输出 JSON：{scores: {...}, reason: "..."}

注意：
  - 评分标准必须具体（锚定评分锚点：什么样算 5 分、3 分、1 分）
  - 与人工打分做一致性校验（至少 50 条）
  - 固定评分模型与温度，结果才可复现
```

## 5. 关键指标定义

### 离线指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 通过率 | 满足所有检查项的样本比例 | 主指标 |
| 格式合规率 | 输出能被正确解析的比例 | 工程可用性 |
| 各维度平均分 | 相关性/准确性/完整性等 | 定位问题 |
| 拒答率 | 模型说「无法确定」的比例 | 过高=过于保守，过低=可能编造 |
| 幻觉率 | 输出中无依据内容的比例 | 信任核心 |
| 延迟 P50/P95 | 响应时间分布 | 体验 |
| 单次成本 | token 成本 | 成本 |

### 线上指标（见 20 篇）

| 指标 | 说明 |
|---|---|
| 采纳率 | 生成后被使用/保存/发送的比例 |
| 编辑幅度 | 用户修改了多少（越少越好） |
| 重生成率 | 用户重新生成的比例（高 = 不满意） |
| 放弃率 | 生成后直接离开/未使用 |
| 👍👎 比例 | 显式反馈 |
| 轮次深度 | 完成任务用了几轮 |
| 投诉率 | 用户投诉/举报 |

> ★ **采纳率 + 编辑幅度** 是最能反映真实价值的线上指标，比任何离线分数都真实。

## 6. 评估流程（改动必走）

```
任何改动（prompt / 模型 / 参数 / 检索策略 / 数据）
   ↓
① 离线 eval：跑测试集，对比通过率与各项分数
   ↓ 不退化
② 人工抽检：盲评 30-50 条（随机顺序，不告知哪版）
   ↓ 不退化
③ 小流量线上（5-10%）：观察 3-7 天行为指标
   ↓ 不退化
④ 全量 + 持续监控（质量 + 成本 + 延迟）
```

## 7. 线上监控与漂移检测

### 需要监控的漂移

| 类型 | 说明 |
|---|---|
| **模型漂移** | 供应商静默更新模型，输出风格/质量变化 |
| **数据漂移** | 知识库内容变化导致 RAG 结果变化 |
| **输入漂移** | 用户行为变化（新用法、新场景） |
| **成本漂移** | 输入变长、重试增多导致成本上升 |

### 监控手段

```
① 每日跑一次「金丝雀集」（20-50 条固定样本），看通过率是否稳定
② 线上指标看板（采纳率、👎率、延迟、成本）设阈值告警
③ 抽样人工审核（每日/每周抽 20 条）
④ 用户反馈聚类（👎 的原因分布）
⑤ 输入日志聚类（发现新场景与新失败模式）
```

## 8. Bad Case 管理

```
流程：
① 收集：线上 👎、投诉、人工发现、内部测试
② 归档：进 bad case 库（输入、输出、问题类型、严重度）
③ 分类：格式问题 / 事实错误 / 遗漏 / 语气 / 拒答 / 安全 / 延迟
④ 定级：P0（严重误导/安全）/ P1（明显错误）/ P2（体验瑕疵）
⑤ 复盘：每周固定时间过 top 问题
⑥ 修复：改 prompt / 补知识库 / 加规则 / 改流程
⑦ 回归：修复的 case 加入 evals 集（★ 防止复发）
```

> **每个 bad case 都应该变成一条 eval 用例**，这是测试集持续增值的机制。

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 没有 evals 就上线 | 改了变坏也不知道 | 上线前必须有测试集 |
| 测试集自己编 | 与真实分布不符 | 用真实输入 |
| 只看通过率 | 不知道哪里差 | 分维度打分 |
| 用 BLEU 评开放式生成 | 分数与实际质量无关 | 用 LLM-as-judge + 人工校准 |
| LLM 评分没校准 | 分数不可信 | 与人工一致性校验 |
| 测试集不更新 | 无法覆盖新问题 | bad case 持续入库 |
| 只看离线不看线上 | 离线好但用户不满 | 线上行为指标 |
| 换模型不回归 | 全线退化 | 换模型 = 大版本，完整回归 |
| 忽略成本与延迟 | 质量涨了成本爆了 | 一并纳入评估 |
| 抽样只看成功 | 失败模式被隐藏 | 专门分析失败样本 |

## 10. Checklist

- [ ] 有 ≥ 50 条的 evals 测试集，来源真实
- [ ] 覆盖典型/边界/对抗/bad case 四类
- [ ] 评分方式明确（规则 + LLM judge + 人工校准）
- [ ] 每次改动（prompt/模型/参数）都跑离线回归
- [ ] 有金丝雀集每日跑，检测漂移
- [ ] 线上监控采纳率、编辑幅度、👎率、延迟、成本
- [ ] bad case 有库、有周复盘、修复后入 evals
- [ ] 换模型走完整回归流程
