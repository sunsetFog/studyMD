# 05 · 需求分析：从一堆声音里挑出真需求

## 1. 需求的来源

| 来源 | 特点 | 可信度 |
|---|---|---|
| 用户反馈/工单 | 真实但片面 | 中高（要看频次） |
| 数据分析 | 客观但不解释原因 | 高 |
| 竞品动作 | 有参考价值但背景不同 | 中 |
| 老板/战略 | 优先级高，需验证 | 视情况 |
| 销售/客户成功 | 贴近客户但偏大单 | 中（注意偏差） |
| 团队自提 | 有洞察但易自嗨 | 需验证 |
| 技术演进 | 新能力带来新可能 | ★ AI 时代重要来源 |

## 2. 真伪需求判断：四问法

```
① 这是谁的需求？（具体画像，不是「所有用户」）
② 频次多高？（每天 / 每月 / 一年一次）
③ 强度多强？（没它会不会很难受，有没有替代方案）
④ 规模多大？（多少人有这个问题）
```

| 组合 | 判断 |
|---|---|
| 高频 + 强痛 + 大规模 | **必做**，核心功能 |
| 高频 + 弱痛 | 体验优化，可做但不优先 |
| 低频 + 强痛 | 有价值但用户难记住你，考虑入口触发 |
| 低频 + 弱痛 + 少数人 | **不做**（伪需求的重灾区） |

## 3. 需求 vs 需要 vs 欲望

| 层次 | 说明 | 例子 |
|---|---|---|
| Need（需要） | 抽象的根本目标 | 「我要准时下班」 |
| Want（欲望） | 用户自己表述的方案 | 「要一个一键生成报表的按钮」 |
| Demand（需求） | 有支付意愿/行动能力的需求 | 愿意为它付费或改变习惯 |

分析的目标：**从 Want 挖到 Need，再给出比用户想的更好的方案**。

## 4. KANO 模型：需求的分层

```
满意度
  ↑
  │   兴奋型（超出预期，做了惊喜，不做不扣分）
  │  ╱
  │ ╱   期望型（做得越好越满意，线性关系）
  │╱
  │    基本型（必须有，没有极度不满，有了也没感觉）
  └─────────────────────────→ 实现程度
```

| 类型 | 例子（AI 写作工具） | 策略 |
|---|---|---|
| 基本型 | 生成不乱码、不丢内容 | 必须达标，不达标别上线 |
| 期望型 | 生成速度、文采质量 | 持续优化，与竞品对标 |
| 兴奋型 | 自动配图、一键多平台适配 | 差异化亮点，做 1-2 个即可 |
| 无差异型 | 换肤、自定义字体 | 不做 |
| 反向型 | 强制社交分享、自动发朋友圈 | 千万别做 |

**KANO 会随时间下降**：今天的兴奋型，半年后就是基本型（如 AI 摘要）。

## 5. 需求优先级四象限（紧急 × 重要）

|  | 紧急 | 不紧急 |
|---|---|---|
| **重要** | 立即做（线上故障、合规要求） | 计划做（核心能力）★ 最重要但最容易被挤掉 |
| **不重要** | 委托/快速做（临时活动支持） | 不做（删掉） |

> 高手的时间应该花在「重要但不紧急」象限。

## 6. 需求池的字段规范

```markdown
| ID | 需求描述 | 来源 | 用户画像 | 场景 | 频次 | 影响面 | 类型 | 状态 | 负责人 |
```

每条需求必须包含：

- **一句话描述**（用户视角，非功能描述）
- **证据**（谁说的/什么数据，附链接）
- **假设**（如果不确定，标注为假设待验证）
- **验收标准**（怎样算完成）

## 7. 需求拆解：从大问题到可执行

```
大问题：用户留存低
  → 为什么？新用户第一次用没产出
    → 为什么？不知道输入什么
      → 解法 A：示例引导（低成本）
      → 解法 B：模板库（中成本）
      → 解法 C：智能预填（高成本）
```

用**逻辑树/MECE** 拆解：相互独立、完全穷尽，避免遗漏和重叠。

## 8. ★ AI 需求的特殊判断

| 判断项 | 说明 |
|---|---|
| **AI 是否必要** | 规则明确、要求 100% 准确 → 别用 AI；模糊、多样、容错高 → AI 合适 |
| **准确率门槛** | 这个场景能接受多少错误率？（90%？99%？）能否人工兜底 |
| **成本可行性** | 单次调用成本 vs 用户愿意付的钱（毛利算得过吗） |
| **延迟容忍度** | 同步等待能接受几秒？能否流式输出缓解 |
| **数据可得性** | RAG 需要的数据你有吗？质量如何 |
| **失败代价** | AI 错了会怎样？（推荐错了无所谓，医疗建议错了要命） |

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 需求池只增不减 | 500 条需求堆积 | 每季度清理，超过 6 个月没做的默认关闭 |
| 谁声音大做谁的 | 大客户绑架路线图 | 按「频次×规模×战略」打分 |
| 把方案当需求 | PRD 直接写「加个按钮」 | 回溯到用户目标再设计方案 |
| 忽略无需求 | 不问「用户为什么不用」 | 专门研究流失与非用户 |
| 需求没有验收标准 | 做完说不清算不算完成 | 写需求时同步写验收 |

## 10. Checklist

- [ ] 每条需求有四问答案（谁/频次/强度/规模）
- [ ] 用 KANO 标过类型，基本型已达标
- [ ] 区分了用户的 Want 和底层 Need
- [ ] AI 需求通过了「必要性 + 准确率 + 成本 + 延迟 + 失败代价」五项检查
- [ ] 需求池定期清理，有明确的关闭机制
