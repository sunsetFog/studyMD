# 51 · 微服务拆分原则与常见坑

## 1. 拆分原则

### ① 基于业务能力（而非技术分层）

| 正确 | 错误 |
|---|---|
| 订单服务（含订单的 API、逻辑、数据） | 订单 API 服务 + 订单逻辑服务 + 订单 DAO 服务 |
| 用户服务 | 用户 Controller 服务、用户 Service 服务 |

> 按技术层拆会导致「改一个需求要改三个服务、发三次版」——典型的分布式单体。

### ② 基于 DDD 限界上下文

- **领域**（Domain）：核心业务（订单、支付）→ 自研、重点投入。
- **支撑域**：业务相关但非核心 → 可外包/简化。
- **通用域**：通用能力（认证、文件、通知）→ 买或开源。

每个限界上下文对应一个（或几个）服务，边界内统一语言（Ubiquitous Language）。

### ③ 单一职责 + 团队自治（康威定律）

一个服务由一个**_two-pizza team_**（5~9 人）负责，能独立开发、测试、部署。

### ④ 数据所有权

谁的数据谁管理，对外只提供 API/事件。

### ⑤ 演进式拆分

不要一次性大重构。用**绞杀者模式**：先拆变化最快/最独立的模块。

## 2. 粒度判断

| 太大（单体味） | 太小（纳米服务） |
|---|---|
| 一个服务覆盖多个业务域 | 一次请求跨 10+ 服务 |
| 改一处要全量回归 | 独立部署价值 < 维护成本 |
| 团队间频繁冲突 | 网络开销大于业务处理 |

经验参考：
- 一个服务代码量 5k~50k 行。
- 单次业务请求跨服务调用 ≤ 3~5 次。
- 服务数量 ≈ 团队数量 × 1~3。

## 3. 常见坑（按类别）

### 拆分类

| 坑 | 现象 | 解决 |
|---|---|---|
| 分布式单体 | 每次上线要发所有服务 | 重新划分边界，减少同步调用 |
| 拆太细 | 调用链巨长、延迟高 | 合并高频同域服务 |
| 共享库滥用 | 改 common 包影响所有服务 | common 只放无业务的工具与契约，升级要向后兼容 |
| 共享 DB | 改表互相影响 | 独立库，接口化 |
| 按技术分层拆 | 无业务语义 | 按领域拆 |

### 通信类

| 坑 | 现象 | 解决 |
|---|---|---|
| 未设超时 | 线程池打满、雪崩 | 每个调用都设 connect/read timeout |
| 未熔断 | 下游挂拖垮上游 | Resilience4j/Sentinel |
| 未重试或无限重试 | 抖动失败 / 打垮下游 | 幂等接口才重试，限制次数与退避 |
| 无幂等 | 重复下单/重复扣款 | 唯一键、状态机、乐观锁 |
| 循环依赖 | 服务 A↔B 互相调用 | 抽取公共服、改事件驱动 |
| 同步调用链过长 | 延迟累加 | 改异步、并行调用、CQRS 读宽表 |
| 接口无版本 | 改动引发上游故障 | `/api/v1/`，向后兼容 |

### 数据类

| 坑 | 现象 | 解决 |
|---|---|---|
| 跨服务 JOIN | 无法写 SQL | 数据冗余、应用层组装、宽表/ES |
| 分布式事务 | 数据不一致 | 最终一致（消息）+ 对账 |
| ID 不用分布式 | 主键冲突 | 雪花/号段 |
| 时间/时区不统一 | 数据错乱 | 统一 UTC 存储，展示层转换 |
| 无数据归档 | 单表爆炸 | 定期归档冷数据 |

### 运维类

| 坑 | 现象 | 解决 |
|---|---|---|
| 无链路追踪 | 排障靠猜 | 统一 traceId + SkyWalking/Zipkin |
| 日志分散 | grep 几十台机器 | ELK/Loki 聚合 |
| 无健康检查/探针 | 流量打到坏实例 | readiness/liveness |
| 配置散落 | 改配置要改 N 个服务 | 配置中心 |
| 无优雅停机 | 发布时报错 | graceful shutdown + preStop |
| 服务过多管理混乱 | 不知道谁依赖谁 | 服务目录、依赖拓扑、CMDB |

### 组织类

| 坑 | 现象 | 解决 |
|---|---|---|
| 没有 DevOps | 微服务上不去 | 先建 CI/CD、监控、自动化 |
| 团队没有 ownership | 出问题互相推 | 明确服务负责人 |
| 文档缺失 | 接口靠问 | API 文档（OpenAPI）+ 契约测试 |

## 4. 微服务清单（落地前自检）

- [ ] 有 CI/CD 流水线（自动构建、测试、部署）？
- [ ] 有容器编排（K8s）？
- [ ] 有集中配置中心？
- [ ] 有服务注册发现与负载均衡？
- [ ] 有统一网关与鉴权？
- [ ] 有熔断限流降级？
- [ ] 有日志聚合 + 链路追踪 + 指标监控告警？
- [ ] 有接口契约与版本管理？
- [ ] 有自动化测试（契约测试、集成测试）？
- [ ] 团队具备 oncall 与排障能力？

> 以上不满足一半，**先别上微服务**。

## 5. 单体 → 微服务迁移步骤

```
1 模块化单体：先按领域划分清晰的包/module 边界，禁止跨模块直接访问
2 抽出公共能力：认证、文件、通知等通用服务
3 优先拆「变化频繁」或「资源特性不同」的模块（如搜索、报表）
4 引入网关，逐步把流量从单体切到新服务（绞杀者）
5 拆分数据库（双写 → 校验 → 切流 → 下线旧表）
6 完善可观测性与自动化
```

## 6. 契约测试（Consumer-Driven Contracts）

```xml
<dependency><groupId>org.springframework.cloud</groupId>
           <artifactId>spring-cloud-contract-verifier</artifactId><scope>test</scope></dependency>
```

生产者定义契约（Groovy/YAML），自动生成测试；消费者用 stub 测试。避免「接口变了上游才知道」。

## 7. 面试速答

- **如何拆分微服务**：按业务能力/DDD 限界上下文，单一职责、数据自治、团队自治，演进式拆分，不要一步到位。
- **微服务最大坑**：分布式事务与一致性、调用链排障困难、运维复杂度、过度拆分导致分布式单体。
- **如何避免雪崩**：超时 + 熔断 + 隔离 + 限流 + 降级 + 监控告警。
- **什么时候拆分**：单体维护成本高、团队规模扩大、需要独立伸缩/独立发布时；但基础设施必须先行。
