# 66 · 单体到微服务演进

## 1. 什么时候该拆

**信号**：
- 代码库庞大，编译/启动/发布慢（> 10 分钟）。
- 多个团队改同一代码库，冲突频繁、互相阻塞。
- 某模块需要独立扩缩容（如搜索、报表吃资源）。
- 某模块变更频率远高于其它（如营销活动）。
- 局部故障导致整体不可用。
- 需要引入不同技术栈。

**不要拆的信号**：
- 团队 < 10 人、业务未定型。
- 没有 CI/CD、监控、容器化基础。
- 拆分只是为了「技术先进」。

## 2. 演进路线

```
阶段 0  单体应用
        ↓ ① 模块化（包/module 边界清晰，禁止跨模块乱调）
阶段 1  模块化单体（Modular Monolith）
        ↓ ② 抽离通用能力（认证、文件、通知、消息）
阶段 2  垂直拆分 1~2 个高价值模块（绞杀者模式）
        ↓ ③ 引入网关 + 注册发现 + 配置中心
阶段 3  全面拆分 + 可观测性 + 熔断限流
        ↓ ④ 数据库拆分（双写 → 校验 → 切流 → 下线）
阶段 4  平台化（DevOps、Mesh、多租户）
```

> **先做模块化单体**：按领域分包/module，用 ArchUnit 做架构约束测试，为后续拆分扫清障碍。

## 3. 绞杀者模式（Strangler Fig）

```
         ┌──────────────┐
请求 ───►│  网关/代理    │──┬──► 单体（旧功能）
         └──────────────┘  └──► 新服务（已迁移功能）
```
1. 在单体前加代理（Nginx/Gateway）。
2. 新功能全部在新服务实现。
3. 逐步把旧功能迁移到新服务，代理按路径切流。
4. 单体剩下的部分逐渐消亡。

优点：低风险、可随时回退、业务不中断。

## 4. 拆分步骤（以订单为例）

### ① 明确边界

- 订单服务的职责：订单创建、状态流转、查询。
- 不属于订单服务：库存扣减（库存服务）、支付（支付服务）、用户（用户服务）。
- 对外提供：API（同步）+ 事件（异步）。

### ② 抽出代码

- 把 `OrderController/Service/Mapper/Entity` 移到新工程。
- 公共类（Result、异常、工具）放到 common 包（**只放无业务的**）。
- 跨模块调用改为 Feign/MQ。

### ③ 数据库拆分（最难）

```
1 新库建表，结构与原库一致
2 双写：应用同时写旧库和新库（新库写入失败要告警）
3 数据迁移脚本补齐历史数据 + 持续追增量（Canal 或定时任务）
4 校验：行数 + 抽样 checksum 对比
5 灰度读：先读旧库，逐步切到新库（开关控制）
6 停写旧库 → 观察 → 删除旧表
```

> 外键、跨库 JOIN、事务是拆分时最大的障碍，要提前识别。

### ④ 切换流量

- 网关按比例切流（1% → 10% → 50% → 100%）。
- 保持回滚开关（出问题立即切回单体）。

## 5. 常见迁移难点

| 难点 | 方案 |
|---|---|
| 共享数据库 | 先拆代码，再拆库；用 API 替代 JOIN |
| 分布式事务 | 本地事务 → 消息最终一致 / Seata |
| 用户会话 | Session → JWT / Redis Session |
| 文件上传 | 集中到对象存储 |
| 定时任务 | 分布式锁 / 独立调度中心（XXL-Job） |
| 全局异常/日志 | 统一 starter |
| 权限 | 抽取认证服务 + 网关鉴权 |
| ID | 自增 → 雪花/号段 |
| 配置 | 配置文件 → 配置中心 |

## 6. 并存期注意事项

| 事项 | 做法 |
|---|---|
| 契约 | 接口要有版本（`/api/v1`），**向后兼容** |
| 数据一致性 | 双写期间要能比对与修复 |
| 监控 | 新旧链路都要埋点 |
| 回滚 | 每个切流步骤都要可回退 |
| 文档 | 记录哪些功能已迁移 |
| 不要并行开发 | 新旧同时改会失控，尽量冻结旧功能 |

## 7. 架构守护（防止腐化）

```java
// ArchUnit：约束分层依赖
@Test
void layerRules() {
    layeredArchitecture()
        .consideringOnly("com.example..")
        .layer("Controller").definedBy("..controller..")
        .layer("Service").definedBy("..service..")
        .layer("Repository").definedBy("..repository..")
        .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
        .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
        .check(classes);
}

@Test void noControllerToRepository() {
    noClasses().that().resideInAPackage("..controller..")
        .should().dependOnClassesThat().resideInAPackage("..repository..").check(classes);
}
```

## 8. 什么时候该「合」

微服务不是终点。发现以下情况应考虑**合并服务**：
- 两个服务每次都一起改一起发。
- 调用链过深（A→B→C→D）只为完成一个功能。
- 服务太小，维护成本大于收益。
- 团队缩编，无人维护。

> 架构是演进的，合与拆都是正常手段。

## 9. 常见坑

| 坑 | 现象 | 解决 |
|---|---|---|
| 一次全量重构 | 长周期、高风险 | 演进式、小步快跑 |
| 先拆库后拆代码 | 应用还是耦合的 | 先拆代码边界，再拆数据 |
| 共享 common 变业务大杂烩 | 改一处全量回归 | common 只放契约与工具 |
| 分布式单体 | 拆了还得一起发 | 重新划分边界 |
| 无回滚方案 | 出事无法回退 | 切流开关 + 旧路径保留 |
| 双写不一致 | 数据对不上 | 校验 + 修复脚本 + 告警 |
| 忽略数据迁移 | 历史数据丢失 | 迁移脚本 + 校验 |
| 团队没准备好 | 微服务变灾难 | 先补基础设施与能力 |

## 10. 面试速答

- **如何演进**：模块化单体 → 抽通用能力 → 绞杀者模式逐个拆分 → 引入网关/注册/配置 → 数据库双写迁移 → 平台化。
- **绞杀者模式**：在旧系统前加代理，新功能在新服务实现，逐步迁移旧功能，最终淘汰单体。
- **最难的部分**：数据库拆分与分布式事务；做法是代码先行、数据双写、校验切流。
- **如何降低风险**：小步、可回退、灰度切流、双写校验、完善监控。
