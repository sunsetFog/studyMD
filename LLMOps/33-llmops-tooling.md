# 33 - 工具链与平台选型：自建 vs 托管

> 本体系前 32 章描述的能力（网关、计量、灰度、evals、护栏、观测）， EACH 都有「自建 or 买」的问题。
> 本篇给选型框架与主流方案地图，避免重复建设，也避免过度依赖单一供应商。

---

## 1. 选型决策框架

### 1.1 四问法

| 问题 | 判断 |
|---|---|
| **这是我们的核心竞争力吗？** | 是（如 prompt 工程、评估方法论）→ 自建或深度定制；否（如 trace 存储）→ 直接买/用开源 |
| **它强依赖我们的数据资产吗？** | 是（计量明细、评估集）→ 数据必须留在自己可控的存储里 |
| **成熟开源/托管方案存在吗？** | 存在且活跃 → 不要自建（观测、网关都有成熟方案） |
| **被锁死的代价多大？** | 数据格式被私有化锁定 → 至少保持导出通道（21 章计量明细自己持有） |

### 1.2 推荐结论（多数团队）

- **自建/掌控**：计量明细存储、评估集、护栏规则、应急开关——这些与业务深度耦合，且是审计与合规的事实源。
- **买/用开源**：trace 可视化、prompt 管理界面、评估执行框架、向量库托管——成熟度高，自建纯属浪费。
- **云厂商中立**：模型层保持多供应商（04 章网关本身就是反锁定设计），工具层尽量选开源可自托管方案。

## 2. 各能力域的方案地图

| 能力域 | 开源自托管 | 托管 SaaS | 选型提示 |
|---|---|---|---|
| **观测/trace** | Langfuse（自托管）、OpenTelemetry + Jaeger/Tempo | LangSmith、Arize Phoenix、Braintrust | Langfuse 自托管 + OTel 混合是常见最优解（20 章） |
| **Prompt 管理** | Langfuse Prompt Management、自建 DB（16 章） | LangSmith Hub、PromptLayer | 自建 DB 简单可靠；平台方案注意导出能力 |
| **评估框架** | promptfoo、DeepEval、OpenAI Evals、Ragas（RAG 专属） | LangSmith Evaluation、Braintrust | 框架只做执行，评估集与校准（25 章）必须自己持有 |
| **模型网关** | LiteLLM Proxy、OneAPI、自建薄层 | OpenRouter、Portkey | Spring 团队建议自建薄网关（集成 Resilience4j/Micrometer 更顺，04 章） |
| **向量库** | Milvus、Qdrant、pgvector | Pinecone、Zilliz、Tencent VectorDB | 小规模 pgvector 起步最省事（复用 PG 运维）；规模大再迁移 |
| **护栏** | NeMo Guardrails、Guardrails-ai、自建规则链 | 供应商审核 API（内容安全类） | 规则与测试集自己持有，执行引擎可外采（27 章） |
| **编排框架** | LangChain/LangGraph、Spring AI、自建编排 | Dify、Coze（低代码平台） | **编排层建议自建薄代码**：框架抽象漏得快（hidden complexity），薄封装 + 直接 SDK 是长期最稳 |
| **知识管道** | 自建 + Airflow/DolphinScheduler、Unstructured（抽取） | 供应商文档解析 API | 19 章管道逻辑（哈希同步/元数据）自己写，抽取环节可外采 |

## 3. 三种典型团队的组合建议

### 3.1 小团队（1-3 人兼职）

```
LiteLLM（网关） + Langfuse SaaS（观测+prompt） + pgvector + promptfoo + 供应商审核 API
自建: 仅计量明细表（一张 Postgres 表起）+ 评估集（Git）
目标: 全部工程化能力一周内跑通
```

### 3.2 中型团队（专职 2-5 人）

```
自建薄网关（Spring，集成限流熔断计量） + Langfuse 自托管
Milvus/Qdrant 托管 + DeepEval/Ragas（评估执行）+ 自建护栏链
自建: 计量明细（ClickHouse）+ 评估集体系 + 灰度分流 + 应急开关
```

### 3.3 大型/合规敏感团队

```
自建为主：网关/观测管道（OTel+自研落库）/评估平台/护栏
外采仅剩: 向量库基础设施、内容审核 API
要求: 所有数据自有存储，SaaS 仅在边界功能使用
```

## 4. 防锁定工程实践

| 实践 | 说明 |
|---|---|
| 数据出口保障 | 选型前验证：计量/trace/评估数据能否完整导出（API/CSV/数据库直连） |
| 标准协议优先 | 网关层统一 OpenAI 兼容协议；OTel 作为 trace 标准，平台层可换 |
| 双写过渡 | 更换平台时新旧并行双写 2-4 周验证（embedding 换模型同款方法，19 章） |
| 成本可见性 | SaaS 工具的账单纳入 06 章预算体系——LLM 平台按 seat/事件计费，规模大了不便宜 |
| 演进留档 | 每季度评审工具链：实际使用率、成本、替代方案成熟度 |

**评估执行框架的特别提示**：框架会过时（生态变化快），但**评估集与 judge 校准集是你十年资产**——框架可换，资产格式必须自持（25 章的 YAML 规范）。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 用 LangChain 全家桶硬写复杂业务 | 抽象漏损、调试地狱、升级破坏 | 薄封装 + 直接 SDK，复杂控制流自建 |
| 观测数据全交给 SaaS | 数据资产失控、迁移成本极高 | 计量明细自持（21 章），SaaS 只做展示层 |
| 评估集绑死在某平台格式 | 换平台 = 重建资产 | 自持标准格式（YAML），导入导出转换 |
| 工具链堆砌（5 个平台各管一段） | 数据分裂、口径打架、维护成本爆炸 | 单平台覆盖多能力 > 多平台各管一段 |
| 网关选 SaaS 后密钥给了第三方 | 多一个泄漏面 | 密钥永远自己持有（32 章） |
| 自建向量库 | 把精力花在运维而非产品 | 托管起步，规模到了再评估 |
| 没算 SaaS 隐性成本 | 平台费超过省下的人力成本 | 纳入预算体系（06 章）季度评审 |

## 6. Checklist

- [ ] 各能力域完成四问法评估，自建/外采清单成文
- [ ] 计量明细、评估集、护栏规则、应急开关四项核心资产自持
- [ ] trace/观测有标准协议（OTel），平台可替换
- [ ] 网关保持多供应商抽象，密钥自持
- [ ] 编排层薄封装，不绑框架全家桶
- [ ] 所选 SaaS 均验证过数据导出通道
- [ ] 更换工具走双写过渡流程
- [ ] SaaS 成本纳入预算体系，季度评审工具链
- [ ] 评估集格式自持（框架可换、资产不换）
