# 24 - 漂移检测：模型 / 输入 / 知识 / 成本

> 漂移 = 「没人改任何东西，但系统行为悄悄变了」。这是 AI 应用与传统后端最大的运维差异：
> 传统服务的依赖是确定的，LLM 应用的「依赖」会自己移动（模型静默更新、用户输入分布变化、知识库过期、价格调整）。
> 本篇把 18 章的模型漂移扩展为四类漂移的系统性检测。

---

## 1. 四类漂移总览

| 漂移类型 | 变的是什么 | 典型表现 | 检测手段 |
|---|---|---|---|
| **模型漂移** | 供应商更新权重/基础设施 | 金丝雀集掉分、输出风格变化、延迟变化 | 固定基准集每日跑（18 章） |
| **输入漂移** | 用户流量分布变化 | 新话题涌入、语言/长度分布偏移、异常流量 | 输入分布统计 + 新颖度检测 |
| **知识漂移** | 知识库内容过期或管道退化 | 答案引用过期内容、检索命中率下降 | 19 章新鲜度监控 + 检索质量趋势 |
| **成本漂移** | 模型行为变啰嗦 / 计价调整 / 流量结构变化 | 单次成本、token 用量变化 | 成本归因拆解（06 章） |

共同思想：**所有检测都建立在「固定基准 + 统计对比」上**——没有不变的基准，就没有「变」可言。

---

## 2. 基准资产：三种探针

| 探针 | 内容 | 用途 | 频率 |
|---|---|---|---|
| **金丝雀集** | 固定输入 + 确认过的标准答案（50-200 条） | 模型/管道质量漂移 | 每日 |
| **基准画像** | 生产输入分布的周快照统计 | 输入漂移 | 每周对比 |
| **基准成本画像** | 各场景单次成本/token 分布基线 | 成本漂移 | 每周对比 |

**金丝雀集是 drift 检测的心脏**：你的代码不变、prompt 版本不变、模型快照锁定，每天跑它——分数动了就说明环境动了。构建方法：

```
1. 从历史 badcase 与核心场景各抽 50 条（覆盖主要功能与边界 case）
2. 每条标注：期望要点 / 禁止内容 / 参考答案
3. 固定 temperature（或固定 seed），版本化存 Git（和 17 章冒烟集可以合并维护，
   但注意：冒烟集拦截变更（CI 用），金丝雀集探测环境（定时跑），用途不同）
4. 每日定时跑 + 分数入库 + 周环比告警（23 章规则）
```

---

## 3. 模型漂移检测

18 章已覆盖模型升级与静默更新，本节补充**漂移信号的精细判别**——同样的分数下降，根因可能完全不同：

| 掉分伴随信号 | 更可能的根因 | 优先排查 |
|---|---|---|
| 仅质量掉分，延迟/长度正常 | 模型权重更新 | 检查供应商 changelog；试锁旧快照对比 |
| 质量掉分 + 延迟上升 | 供应商换底层基础设施/路由 | 问供应商；观察是否自愈 |
| 质量掉分 + 输出变长 | 模型变啰嗦（常见于新版本） | prompt 收紧 max_tokens/格式指令 |
| 质量掉分 + 拒答率上升 | 模型安全策略收紧 | 检查被拒样本，调整 prompt 措辞 |
| 只有部分场景掉分 | 场景依赖的特定能力变化 | 逐场景 evals（18 章 2.2），针对性修 prompt |

**关键纪律：发现漂移先确认「它不是你自己造成的」**——排除本周的 prompt 发布（17 章灰度面板）、知识库变更（19 章同步报告）、流量结构变化，再归因给模型。

---

## 4. 输入漂移检测

### 4.1 监控什么分布

对生产输入做每周快照，与基线画像对比：

| 分布维度 | 统计口径 | 漂移信号举例 |
|---|---|---|
| 输入长度 | P50/P95 tokens | 突增 → 可能被刷长上下文（成本攻击，10 章防刷联动） |
| 语言分布 | 语言占比 | 新语言涌入 → prompt/知识库是否覆盖 |
| 话题新颖度 | 高维聚类后「落在新簇」输入占比 | 新需求涌现（产品机会）或异常流量 |
| 拒答/护栏触发分布 | 分类型占比 | 某类拦截突增 → 攻击或知识缺口 |
| 空检索率 | 检索 0 命中占比 | 用户在问知识库没有的问题 |

### 4.2 输入漂移的两种应对方向

- **坏漂移**（异常流量、注入攻击样本）：接 27 章护栏与 10 章防刷处置。
- **好漂移**（新话题、新需求）：这是产品输入——「20% 输入落入新簇」值得每周人工看一眼，直接转化为知识库补录任务（19 章）与评估集增补（25 章）。

### 4.3 简易新颖度检测实现

```python
# 每周任务：本周输入 embedding 后与基线簇模型对比
clusters = baseline_clustering.predict(week_vectors)
new_ratio = (clusters == -1).mean()        # 落在所有已知簇之外的比例
if new_ratio > baseline_new_ratio * 2:
    report_top_new_topics(week_vectors, top_n=10)   # 报告给产品/知识库负责人
```

不需要多精密——目标是「新东西出现了能知道」，不是学术级 OOD 检测。

## 5. 知识与成本漂移检测

### 5.1 知识漂移（衔接 19 章）

| 信号 | 指标 | 阈值示例 |
|---|---|---|
| 内容过期 | 答案引用的 source_version 滞后天数 P95 | >30 天告警 |
| 检索退化 | 标准查询集命中率/MRR 周环比 | -5% 告警 |
| 管道退化 | 同步失败率、chunk 总数异常 | 19 章规则 |
| 覆盖缺口 | 空检索率趋势 | 持续 >5% 告警 |

### 5.2 成本漂移的归因流程（衔接 06/22 章）

单次成本周环比 +20% 触发告警后，按顺序排除：

```
1. 流量结构变化？（功能 mix 变了 → 高成本功能占比上升，属正常，调整基线口径）
2. prompt 版本变化？（17 章灰度面板，输出变长）
3. 模型/tier 变化？（降级链把流量送到贵模型了？04 章路由统计）
4. 计价调整？（21 章计价表变更历史 + 账单对账）
5. 都不是 → 模型行为变啰嗦 → 输出长度分布确认（回到第 3 节模型漂移）
```

**成本漂移是最常被误报的类别**，因为它的解释变量最多。归因流程固化成 runbook，避免每次都从零推理。

## 6. 漂移响应决策矩阵

| 判定 | 响应 |
|---|---|
| 环境漂移（模型/计价） | 18 章：锁旧快照 / prompt 修正 / 灰度迁移 |
| 输入坏漂移（攻击/滥用） | 27 章护栏收紧 + 10 章防刷 |
| 输入好漂移（新需求） | 知识库补录 + 评估集增补 + 排进迭代 |
| 知识漂移 | 19 章同步修复 + 内容更新 |
| 自身变更引起 | 回滚（17 章）或修复发布 |
| 基线过期 | 更新基准画像/金丝雀集（记录变更原因！） |

最后一条最容易被忽略：**基线资产本身也要有变更管理**——更新金丝雀集必须写 changelog，否则下次漂移时无法判断「是环境变了还是基准变了」。

## 7. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 没有金丝雀集 | 漂移数月后才被用户投诉发现 | 每日定时基准测试（最高优先级建设） |
| 金丝雀集与 CI 冒烟集混用且无用途区分 | 拦截变更的集子被污染，失去基准意义 | 分开维护，各自版本化 |
| 发现漂移直接归因模型 | 排查方向错误，浪费时间 | 先排除自身变更（prompt/KB/流量结构） |
| 成本告警不做归因拆解 | 误报率高，告警失去信誉 | 固化归因流程（5.2） |
| 输入漂移只当噪音处理 | 错失产品信号 + 放过攻击 | 新簇每周人工过目，坏漂移接护栏 |
| 基准画像永不变更 | 三个月后基线失真，正常流量都像漂移 | 季度评审基线，变更留痕 |
| 温度不固定跑金丝雀集 | 采样噪声淹没真实漂移 | 固定参数，多轮取均值 |
| 漂移发现后无响应闭环 | 知道漂了但没人修 | 决策矩阵 + 每类漂移绑定负责人 |

## 8. Checklist

- [ ] 金丝雀集建立（50-200 条，覆盖核心场景与历史 badcase），每日定时跑，固定参数
- [ ] 金丝雀集与 CI 冒烟集分开维护，均版本化并记录变更原因
- [ ] 分数入库 + 周环比告警（-2% 起），伴随信号（延迟/长度/拒答率）联动判别根因
- [ ] 输入分布每周快照：长度/语言/新颖度/空检索率
- [ ] 新话题簇每周人工过目，转化为知识库补录与评估集增补
- [ ] 异常输入分布联动 27 章护栏与 10 章防刷
- [ ] 知识新鲜度 P95 滞后天数与检索命中率监控
- [ ] 成本漂移告警配固化归因 runbook（流量→prompt→tier→计价→模型）
- [ ] 基准画像季度评审更新，变更留痕
- [ ] 每类漂移有明确负责人与响应动作映射
