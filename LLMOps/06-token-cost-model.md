# 06 · Token 与成本模型：先把账算明白

## 1. 成本是 AI 应用运维的第一性问题

```
传统软件：部署完成后边际成本 ≈ 0
AI 应用：每次调用都花钱，且与使用量线性相关
  → 用户越多成本越高（与传统 SaaS 相反）
  → 成本失控 = 商业模式不成立
```

运维视角的三件事：**算得清（计量）、看得见（看板）、控得住（熔断）**。本篇讲「算得清」。

## 2. Token 基础

| 概念 | 说明 |
|---|---|
| Token | 模型的计费与处理单位，约等于 0.7-1.5 个汉字或 0.75 个英文单词 |
| 输入 token | 你发给模型的内容（系统 prompt + 上下文 + 检索结果 + 用户输入） |
| 输出 token | 模型生成的内容（**通常比输入贵 3-5 倍**） |
| 计费 | 费用 = 输入 token × 输入单价 + 输出 token × 输出单价 |

关键认知：

```
① 大多数场景下输入占大头（长上下文/检索结果/历史对话）
② 多轮对话中，历史消息每轮都要重新计费（成本随轮次线性增长）
③ 系统提示（长 prompt）是固定成本，调用次数多时是大头
```

## 3. 单次成本计算（公式 + 示例）

```
单次成本 = (输入 token / 1e6 × 输入单价) + (输出 token / 1e6 × 输出单价)
```

示例：客服问答场景（人民币单价示例）

```
组成：
  系统 prompt         800 token
  检索上下文（RAG）    1500 token
  历史对话（最近3轮）  1200 token
  用户输入             100 token
  → 输入合计          3600 token
  输出                 500 token

单价（示例）：输入 ¥15/1M，输出 ¥75/1M

单次成本 = 3600/1e6 × 15 + 500/1e6 × 75
         = ¥0.054 + ¥0.0375 = ¥0.0915
```

## 4. 从单次到月度：三个维度推演

```
日成本 = Σ(各场景调用次数 × 单次成本)
月成本 = 日成本 × 30 × 波动系数（通常 1.2-1.5）
单用户月成本 = 该用户全部调用成本之和
```

**必做的三个推演表**：

### ① 场景成本表

| 场景 | 日均调用 | 单次成本 | 日成本 |
|---|---|---|---|
| 客服问答 | 10000 | ¥0.09 | ¥900 |
| 文档摘要 | 500 | ¥0.30 | ¥150 |
| 报表生成 | 100 | ¥0.80 | ¥80 |
| 合计 | | | **¥1130/日 ≈ ¥34k/月** |

### ② 用户分层推演（找亏损大户）

| 用户层 | 占比 | 月调用 | 月成本 | 月收入 | 毛利 |
|---|---|---|---|---|---|
| 轻度（P50） | 60% | 30 | ¥2.7 | ¥99 | ✅ |
| 中度（P90） | 30% | 300 | ¥27 | ¥99 | ✅ |
| **重度（P99）** | 9% | 3000 | **¥270** | ¥99 | ❌ 亏 |

→ 重度用户的 9% 人数可能吃掉 60% 的成本 → 必须有配额/超额计费（见 10）。

### ③ 上下文轮次推演（多轮对话的成本曲线）

```
第 1 轮：输入 1000 → 成本 ¥0.04
第 5 轮：输入 1000 + 4×800(历史) = 4200 → 成本 ¥0.14
第 10 轮：输入 8200 → 成本 ¥0.24
→ 10 轮对话 = 前几轮成本的 4-5 倍
→ 解法：历史摘要压缩、只保留最近 N 轮（见 09）
```

## 5. 计量落库（一切分析的前提）

每次调用必须记录：

```json
{
  "trace_id": "req-8f2...",
  "ts": "2026-11-05T10:23:00Z",
  "user_id": "u-123",
  "scene": "chat",
  "model": "mid@2026-01",
  "prompt_version": "chat-v1.3.0",
  "input_tokens": 3600,
  "output_tokens": 500,
  "cost": 0.0915,
  "cache_hit": false,
  "status": "ok",
  "latency_ms": { "first_token": 800, "total": 4200 }
}
```

计量要点：

| 要点 | 说明 |
|---|---|
| **以响应中的 usage 为准** | 自己估算 token 不准，读 API 返回的 usage 字段 |
| **流式也要计量** | 流结束时读 usage；客户端中断也要估算已生成部分 |
| **记录 prompt_version** | 才能回答「哪个版本的 prompt 花钱最多」 |
| **失败请求也计费** | 超时/取消后供应商可能仍计费 |
| **重试要合并** | 一次业务请求的多次重试记为一条 trace，费用累加 |

## 6. 成本归因（知道钱花在哪）

```
四个归因维度（看板必备）：
① 按场景：哪个场景最烧钱
② 按用户/租户：谁是重度用户
③ 按输入构成：系统 prompt / 检索 / 历史 / 用户输入 各占多少
④ 按模型：旗舰 vs 便宜模型的成本占比
```

输入构成分析是降本最重要的依据：

```
示例发现：检索上下文占输入的 42%
  → 优化检索（top-k 减小、分块调优）比换模型更有效
```

## 7. 预算体系

```
层级：
全局月预算 → 场景日预算 → 用户日配额 → 单请求 token 上限

控制手段（见 10 篇详述）：
① 预警：达到预算 80% 告警
② 熔断：达到 100% 降级到便宜模型 / 关闭非核心场景
③ 硬限：单用户配额用尽 → 拒绝服务（引导升级）
```

## 8. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 自己估算 token 不准 | 成本统计偏差 20-50% | 读 API usage 字段 |
| 忽略输入成本 | 只盯输出长度，检索上下文越塞越多 | 归因到输入构成 |
| 多轮对话无上下文管理 | 轮次越深成本越高 | 摘要压缩 + 轮数限制 |
| 失败请求漏统计 | 成本对不上账 | 重试合并 + 失败也记录 |
| 只看日总成本 | 找不到亏损点 | 按 场景/用户/构成 归因 |
| 测试环境用正式模型 | 无限试错烧钱 | dev 用便宜模型或 mock |
| 历史数据不留存 | 无法复盘成本变化 | 计量全量落库 |
| 无预算熔断 | 一次事故烧穿月预算 | 阈值告警 + 自动降级 |

## 9. Checklist

- [ ] 每个场景有单次成本估算（含输入构成明细）
- [ ] 做过用户分层推演，重度用户不亏损（或有配额）
- [ ] 多轮场景有上下文长度管理
- [ ] 每次调用计量落库（usage 为准、含 prompt_version、流式/失败覆盖）
- [ ] 有场景成本表与四维归因看板
- [ ] 有预算层级与预警/熔断阈值（见 10）
