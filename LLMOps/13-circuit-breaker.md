# 13 · 熔断与舱壁：把故障隔离在局部

## 1. 为什么 AI 应用更需要熔断

```
传统依赖挂了 → 快速失败
模型 API 出问题 → 往往是「变慢+部分失败」的混合状态
  → 没有熔断时：请求堆积 → 线程池耗尽 → 连锁拖垮整个服务
     （AI 调用是长请求，占住连接/线程的时间是普通 RPC 的 10-100 倍）
```

## 2. 熔断器状态机

```
        成功率<阈值
  CLOSED ───────────→ OPEN（熔断，快速失败/走降级）
     ↑                    │ 静默期到（如 30s）
     │ 成功率恢复          ▼
     └──────────── HALF-OPEN（放行少量探测请求）
                      ├─ 探测成功 → CLOSED
                      └─ 探测失败 → OPEN（重新计时）
```

### AI 场景的熔断参数（与普通 RPC 的差异）

| 参数 | 普通 RPC | AI 调用建议 |
|---|---|---|
| 统计窗口 | 10s | 30-60s（AI 波动更大） |
| 失败率阈值 | 50% | 30-50%（AI 偶发超时常见，别太敏感） |
| 最小请求数 | 10 | 5-20（低峰期别被几个请求触发） |
| 静默期 | 5-10s | 20-60s（模型恢复没那么快） |
| 半开探测数 | 1 | 2-5（避免偶发成功误判恢复） |

**关键**：按「场景 × 模型」分别设熔断器，不要全站一个（见舱壁）。

## 3. 舱壁隔离（Bulkhead）

```
问题：所有场景共享一个调用线程池/连接池
  → 长文生成占满资源 → 连轻量的分类请求也发不出去

解法：按重要性/模型/场景划分独立资源池

┌────────────────────────────┐
│ 旗舰模型池：并发 20          │ ← 长文、复杂推理
│ mini 模型池：并发 100       │ ← 分类、摘要
│ 批量任务池：并发 10         │ ← 离线任务（限流防挤占）
│ 探索/免费场景池：并发 30    │ ← 与付费隔离
└────────────────────────────┘
任一池满 → 该池排队或拒绝 → 不影响其他池
```

### 并发上限怎么定

```
供应商侧约束：你的 API 配额（RPM/TPM）
  并发上限 ≈ min(自建预算, 供应商配额可支撑的并发)
  且预留 20% 余量给突发
```

## 4. 背压（Backpressure）：满了怎么办

```
请求超过容量时的分级处理：
① 排队（有界队列）：等待但告知预计时间
② 排队超限 → 快速拒绝 + 引导稍后重试
③ 付费用户优先（分级队列）
④ 绝不做的是：无限排队 → 内存爆炸、超时雪崩
```

## 5. Resilience4j 配置示例（Java 栈直接复用 java777/44）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      llm-flagship:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 5
        failureRateThreshold: 40
        waitDurationInOpenState: 45s
        permittedNumberOfCallsInHalfOpenState: 3
      llm-mini:
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
  bulkhead:
    instances:
      llm-flagship: { maxConcurrentCalls: 20, maxWaitDuration: 2s }
      llm-mini:     { maxConcurrentCalls: 100 }
      llm-batch:    { maxConcurrentCalls: 10 }
```

## 6. 熔断与降级的联动

```
熔断触发 ≠ 拒绝服务，而是触发降级链（见 11）：

熔断器 onTransition(OPEN):
  → 切换路由到备用模型
  → 用户侧展示"快速模式"
  → 发布事件：监控告警 + 独立质量看板

熔断器 onTransition(HALF_OPEN → CLOSED):
  → 路由切回主模型（灰度比例回升）
  → 记录本次故障时长（复盘用）
```

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 全站一个熔断器 | 一个场景故障拖垮全部 | 按 场景×模型 分实例 |
| 阈值太敏感 | AI 偶发超时频繁误熔断 | 窗口加大 + 最小请求数 |
| 静默期太短 | 反复开合震荡 | 30-60s 静默期 |
| 无舱壁 | 长请求占满资源，轻请求饿死 | 分池并发 |
| 熔断后无降级动作 | 用户直接看到报错 | 联动降级链 |
| 忽略供应商配额 | 并发超限被 429 | 并发上限对齐配额 + 余量 |
| 背压 = 无限排队 | 内存堆积雪崩 | 有界队列 + 快速拒绝 |
| 半开探测失败误判 | 单次探测成功就全量放行 | 探测数 ≥ 2-5 |
