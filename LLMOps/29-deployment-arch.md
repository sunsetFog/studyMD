# 29 - 部署架构选型：API 调用 / 容器 / Serverless / 自建推理

> 先澄清一个常见误区：大多数 LLM 应用**不需要「部署模型」**——模型在供应商那里，
> 你部署的是「编排 + 检索 + 网关 + 护栏」这套胶水层。自建推理是最后才考虑的选项。

---

## 1. 四种部署形态对比

| 形态 | 你的负载 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **API 调用 + 传统容器部署** | 只是编排服务 | 最简单，复用既有后端设施 | 无模型控制权 | 绝大多数团队（默认选择） |
| **Serverless（函数）** | 编排逻辑 | 免运维、按量计费 | 冷启动伤 TTFT、长任务受限（流式/15 章异步长任务不友好） | 低流量、突发型功能 |
| **自建推理（开源模型 + GPU）** | GPU 推理服务 | 数据不出域、无 token 计费上限、可微调 | 重资产：GPU 采购/运维/容量规划，模型质量天花板 | 数据合规强制、超大调用量 |
| **混合（混合路由）** | 两者兼备 | 敏感/高频走自建，其余走 API | 复杂度最高，网关抽象必须先做好（04 章） | 成熟期优化 |

**决策流程**：默认 API 调用；出现「合规强制 / 调用量大到 API 费用 > 自建总成本 / 需要专有微调模型」任一条件才评估自建。

---

## 2. API 调用型：标准部署拓扑

```
LB → [编排服务集群] ──→ 模型网关（04 章，独立部署，集中管密钥/路由/计量）
        ├→ 向量库（托管服务或独立集群，19 章）
        ├→ 缓存层（Redis：语义缓存/配额/幂等，08/10/14 章）
        ├→ 异步队列（RocketMQ/Kafka：长任务/影子/批量，15 章）
        └→ 观测管道（OTel Collector → 计量明细/trace，21 章）
```

要点：

- **模型网关独立部署**：密钥只存在网关，业务服务不碰 API Key（05 章）；路由/熔断/计量集中收敛（04/13/21 章）。
- 编排服务无状态化：会话状态在外部（Redis/DB），随时可水平扩容。
- 队列 worker 与在线服务**分开伸缩**（15 章：长任务的负载模式与在线流量完全不同）。

### 2.1 容量估算的特殊性

LLM 应用在线服务的负载特征：

| 特征 | 对容量的影响 |
|---|---|
| 编排服务本身很轻（CPU 密集度低） | 单 Pod 可承载高 QPS，瓶颈在上游供应商而非容器 |
| 请求长耗时（10-60s） | 并发连接数远高于传统 API（同 QPS 下连接占用时长 ×20），注意 LB/网关的连接与超时配置 |
| 上游限流才是真瓶颈 | 容器再多也没用，扩容上限由供应商 RPM/TPM 决定（10 章配额对齐） |

**结论：容器副本数按「供应商配额 ÷ 单 Pod 并发」算，而不是按 CPU 利用率算。** HPA 用连接数/队列深度做指标，别用 CPU。

## 3. Serverless 的适用边界

| 适合 | 不适合 |
|---|---|
| 低频后台任务（文档解析入库，19 章管道的部分环节） | 首响敏感的对话（冷启动 +1-3s，直接毁掉 TTFT 预算） |
| 突发批处理（夜间评估流水线，25 章） | 流式输出（长连接保持受限） |
| Webhook 触发的同步功能 | Agent/长任务（15 章：步数多、总时长分钟级） |

若用函数跑 LLM 调用，务必核对平台「最大执行时长」与流式响应支持——这是最常见的踩坑点。

## 4. 自建推理（当确实需要时）

### 4.1 技术栈最小集

```
模型服务:  vLLM / SGLang / TGI（PagedAttention、continuous batching 是标配）
硬件:      A100/H100 或国产替代，按并发 × KV cache 显存估算
编排:      K8s + GPU 调度（节点池隔离，30 章）
```

### 4.2 成本与容量现实

| 项目 | 经验值 |
|---|---|
| 显存需求 | 模型权重 + KV cache，7B-13B FP16 约 15-30GB 起，长上下文需按 max_seq_len 预留 |
| 有效吞吐 | continuous batching 下单卡数 QPS 千级 tokens/s（视模型/序列长度），先压测再定容量 |
| 利用率红线 | GPU 利用率 <30% 时自建纯亏；夜间低谷大 → 考虑批量任务填谷（15 章批处理） |
| 隐性成本 | 模型运维人力（升级/压测/故障）、硬件折旧、多可用区冗余 |

**降级关系**：自建模型通常作为 11 章降级链中的「internal tier」，API 模型为主力、自建兜底（或反之）——由 04 章网关统一路由，不要两套路由逻辑。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 模型网关逻辑散在业务服务 | 密钥泄漏面大、路由策略漂移 | 网关独立部署，业务只认 tier |
| HPA 按 CPU 扩容 | 容器忙但实际瓶颈在供应商配额 | 按并发连接/队列深度扩容 |
| 长请求吃满 LB 默认超时 | 60s 请求被 LB 504 掐断 | 调 LB/网关超时分级（09/12 章） |
| Serverless 跑流式对话 | 冷启动 + 连接限制，体验崩 | 流式场景用常驻容器 |
| 过早自建推理 | 团队精力耗在 GPU 运维，产品没长大 | 达成第 1 节三条件再评估 |
| 自建与 API 两套路由 | 降级链断裂、计量分裂 | 统一网关，自建作为一个 provider |
| 异步 worker 与在线服务同池 | 夜间批量任务挤占在线容量 | 分池伸缩（13 章舱壁） |

---

## 6. Checklist

- [ ] 默认 API 调用形态，自建推理仅在三条件触发时评估
- [ ] 模型网关独立部署，密钥收敛，业务服务零 API Key
- [ ] 编排服务无状态，会话/任务状态外置
- [ ] 异步 worker 独立伸缩池
- [ ] 容量按供应商配额与并发连接数规划，HPA 指标正确
- [ ] LB/网关超时链路覆盖长请求（对照 09 章分级超时表）
- [ ] Serverless 仅用于低频后台/批处理，流式场景排除
- [ ] 若自建：压测后再定容量，夜间低谷填谷，利用率红线监控
- [ ] 自建模型接入统一网关作为独立 tier，参与降级链
