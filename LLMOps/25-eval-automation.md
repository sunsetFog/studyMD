# 25 - 离线 Evals 自动化流水线

> evals 是 AI 应用的「单元测试 + 性能基准」。没有它，17 章灰度没有通过标准、
> 18 章模型升级无法决策、24 章漂移没有基线。本篇讲评估集建设与流水线自动化。

---

## 1. 评估集建设：从哪里来

### 1.1 评估集的四类来源（按价值排序）

| 来源 | 构成 | 价值 |
|---|---|---|
| **线上 badcase** | 21 章「负反馈永久保留」的 trace，转化为用例 | 最高：真实分布 + 真实失败模式，防回归的护城河 |
| 核心场景代表样本 | 每个功能场景手工编写 20-50 条典型输入 | 保证覆盖面，CI 冒烟集的主体 |
| 边界与对抗样本 | 超长输入、空输入、注入语句、多语言混合、专业术语 | 拦截系统性缺陷 |
| 合成数据 | LLM 生成相似变体扩充 | 数量补充，**必须人工抽检**，否则污染评估集 |

**铁律：评估集本身是版本化资产**（Git 管理），变更写 changelog 说明原因。每次事故复盘产出至少 1 条新用例——评估集的增长曲线就是系统的防御史。

### 1.2 用例格式规范

```yaml
# evals/sets/support-classifier.yaml
case_id: sc-0031
scenario: support-classifier
input:
  ticket_title: "退款为什么还没到账"
  ticket_body: "订单 20261101xxx 退款一周了..."
expect:
  category: billing
  priority: P2
  must_mention: []            # 答案必须包含的要点（生成类任务用）
  must_not_mention: ["无法退款"]  # 禁止出现的内容
  citation_source: "kb#refund#p12"  # RAG 任务：必须引用的来源
judge_rubric: |
  分类正确性：category 与 priority 均正确得 1.0，仅 category 正确得 0.5
source: "线上点踩会话 s_8812 (INC-1234)"   # 历史可溯源
added_in: "2026-10"
```

## 2. 评估方法工具箱

### 2.1 按任务类型选方法

| 任务类型 | 方法 | 说明 |
|---|---|---|
| 分类/抽取（有标准答案） | **精确匹配 / 准确率** | 最便宜最可靠，能用就用 |
| 结构化输出 | **Schema 校验 + 字段断言** | JSON 合法性、字段值范围 |
| RAG 问答 | **检索命中率（recall@k / MRR）+ 引用正确性 + 忠实度** | 拆开评：检索错和生成错是两种病 |
| 生成类（无标准答案） | **LLM-as-judge + rubric** | 打分维度明确化，见 2.2 |
| 安全合规类 | 断言式（禁止内容出现即 fail） | 不容许打分模糊 |

### 2.2 LLM-as-judge 的正确用法

judge 模型可用，但必须控制偏差：

| 坑 | 对策 |
|---|---|
| 位置偏差（偏好先出现的答案） | 成对比较时随机交换顺序，双向都赢才算赢 |
| 自我偏好（偏好同家族模型输出） | judge 与被评模型用不同供应商 |
| rubric 模糊（「质量好」= 什么都行） | 打分维度拆开：正确性/完整性/简洁性，每维独立 rubric |
| 分数漂移（judge 自身被供应商更新） | judge 模型版本锁定 + 校准集定期回归（见 2.3） |

judge prompt 模板要素：任务背景 + 输入 + 待评输出 + **逐维度 rubric（含每分档示例）** + 要求输出 JSON（分数 + 理由）。judge 的理由文本是人工复核的输入。

### 2.3 校准集：让 judge 可信

拿 30-50 条**人工打过分**的样本做校准集，定期跑 judge 并对比：

```
人工分与 judge 分一致率 ≥85% → judge 可用于自动化门禁
一致率 70-85%               → judge 结果只能做趋势参考，门禁需人工复核
一致率 <70%                 → 重写 rubric 或换 judge 模型
```

## 3. 自动化流水线

### 3.1 三条流水线（不同频率、不同用途）

| 流水线 | 触发 | 范围 | 时限 | 用途 |
|---|---|---|---|---|
| **冒烟** | 每次 PR（17 章 CI） | 30-80 条核心用例 | <5 分钟 | 拦截明显退化 |
| **全量回归** | 每夜 + 发布前 | 数百~数千条 | 小时级 | 发布门禁（28 章）依据 |
| **金丝雀** | 每日定时 | 固定基准集（24 章） | <15 分钟 | 环境漂移探测 |

### 3.2 流水线执行架构

```
触发 → 用例集加载（Git 版本锁定）
     → 并发执行（限速！别把自己打出供应商限流）
       ├─ 分类/结构化：程序断言，零成本
       └─ 生成类：调用目标模型 → judge 模型评分
     → 结果落库（版本/模型/用例/分数/耗时，关联 trace）
     → 与基线对比（按场景分组，24 章 2.2 教训：不看总分）
     → 报告：通过/失败 + 差异清单 + 失败用例直接链接原始输入输出
```

### 3.3 报告的关键设计：失败可行动

```
❌ 全量回归 2026-11-05 (prompt v7 @ model-x-2026-03-01)
总体: 94.2% (基线 96.1%, -1.9pp ❌)

场景拆解:
  ticket-classifier  97.8% (基线 97.9%) ✅
  faq-answer         88.5% (基线 93.0%) ❌ -4.5pp
     失败用例 6 条，其中 4 条模式: 引用了过期政策 kb#refund (v2026-09)
     → 初判: 知识漂移（24 章），非 prompt 问题

失败用例列表（可点击查看完整输入/输出/judge 理由）...
```

**报告必须把失败聚合为「模式」而非罗列**——4 条同模式失败是一条修复线索，6 条散乱失败才是真问题。

### 3.4 成本控制

- 全量回归按 500 条 × 2 次调用（目标 + judge）≈ 每天 ¥5-20 量级，可控。
- 优化：分类类用例走程序断言（免费）；judge 用 mini 档模型；夜间跑完自动关停。
- 大变更（模型升级 18 章）评估的成本远小于上线后救火，别在这里抠。

## 4. 与其他章节的闭环

```
线上点踩/负反馈（20/21 章）→ badcase 转用例 → 评估集增长
17 章灰度发布 → evals 通过标准 = 灰度依据
18 章模型升级 → 逐场景 evals = 升级决策依据
24 章漂移检测 → 金丝雀集 = 漂移探针
28 章发布门禁 → 全量回归结果 = 门禁硬条件
```

评估集是所有质量机制的**共同底座**，它的维护优先级等同于数据库 schema。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 评估集只手工编不接 badcase | 与真实分布脱节，考不出的题线上天天错 | 负反馈自动转用例流程 |
| 合成数据不抽检 | 错误标注污染评估集 | 合成样本 100% 人工过一遍 |
| 只看总分不看场景拆解 | 结构性退化被平均分掩盖 | 报告强制按场景分组对比 |
| judge 不校准 | 门禁被 judge 偏差劫持 | 校准集定期回归（2.3） |
| 评估集混进训练/调优用过的数据 | 分数虚高，线上翻车 | 用例来源溯源（input 字段 source） |
| 并发跑 evals 打爆供应商限流 | 流水线失败且影响生产 | 限速 + 失败重试隔离 |
| 评估集从不更新基线 | 每夜全红，逐渐没人看流水线 | 基线随版本发布同步更新（留痕） |
| 生成类任务只评「看起来对」 | 无法进自动化门禁 | rubric 逐维度化 + 校准 |

## 6. Checklist

- [ ] 评估集版本化（Git），四类来源齐备，badcase 转化流程自动化
- [ ] 每次事故复盘产出 ≥1 条新用例
- [ ] 按任务类型选评估方法，能用程序断言的不用 judge
- [ ] judge 有校准集（30-50 条人工标注），一致率 ≥85% 才进门禁
- [ ] 三条流水线：冒烟（PR）/ 全量（每夜+发布前）/ 金丝雀（每日）
- [ ] 流水线限速执行，结果落库关联版本与 trace
- [ ] 报告按场景拆解 + 失败模式聚合 + 可点进原始输入输出
- [ ] 基线随版本同步更新并留痕
- [ ] 评估成本可控（程序断言优先、judge 用小模型）
- [ ] 用例来源可溯源，杜绝数据泄漏
