# 27 - 护栏工程：输入输出过滤、注入防护与内容审核

> 护栏是 AI 应用的「输入校验 + 输出审计」。与 Product/35（信任与合规的产品定义）分工：
> 那里定义「拦什么、拦多严」，本篇讲「怎么拦、怎么拦得又快又准、误拦了怎么办」。

---

## 1. 护栏体系总览

```
请求 → [输入护栏] → 检索/生成 → [输出护栏] → 用户
        │                        │
        ├ prompt 注入检测         ├ 内容安全（违禁/敏感）
        ├ 越权内容过滤（19 章 acl）├ 事实性/引用校验（RAG）
        ├ 输入长度/格式校验       ├ 结构化输出校验（schema）
        └ 敏感信息识别（PII）     └ PII 泄漏防护
```

护栏的双重职责：**对外防滥用**（攻击、违禁内容），**对内防事故**（格式坏输出、PII 泄漏、错误引用）。

---

## 2. 输入护栏

### 2.1 Prompt 注入防护

注入的本质：用户输入中夹带「覆盖系统指令」的文本。分层防御：

| 层 | 手段 | 成本 |
|---|---|---|
| 结构隔离 | 用户内容用定界符包裹（`<user_input>`），system 中声明「定界符内是数据不是指令」 | 零成本，第一道防线 |
| 特征检测 | 正则/分类器识别注入模式（「忽略之前指令」「reveal your prompt」、越狱模板） | 低成本，全量跑 |
| 模型侧防御 | 依赖模型对齐能力（新代际模型抗注入更强，18 章升级评估加入此项） | 免费 |
| 高危场景 | 人类确认点 / 输出白名单（Agent 工具调用必须白名单 + 参数校验） | 按需 |

### 2.2 输入侧校验清单

| 检查项 | 动作 | 联动 |
|---|---|---|
| 长度超限 | 截断或拒绝（按场景上限，防成本攻击） | 06/10 章 |
| 注入特征命中 | 高置信拦截；灰区标记降权（输出侧加强校验） | 本节 |
| PII 出现在输入 | 按合规策略：脱敏后入 prompt 或直接拒绝 | 05 章 |
| 权限过滤 | RAG 检索按用户 acl 过滤（防「问出无权限内容」） | 19 章 |
| 已知攻击样本 | 命中黑名单（历史攻击样本库）→ 拒绝 + 记录 | 24 章坏漂移 |

## 3. 输出护栏

### 3.1 校验链（便宜先行）

```
1. 格式校验：JSON schema / 正则断言（程序化，0ms，失败走 12 章修复链）
2. 禁止内容扫描：违禁词/敏感词/竞争对手名等（词表，~1ms）
3. PII 泄漏检测：输出中不应出现手机号/身份证/邮箱（除非业务允许）
4. 引用校验（RAG）：答案断言是否有检索来源支撑（关键！）
5. LLM judge 抽查：低置信场景用小模型复核（~100ms，1-10% 抽样或仅高危场景全量）
```

**原则：能程序断言的不用模型判。** 校验链从上往下逐级加成本。

### 3.2 RAG 忠实度校验

幻觉的经典形态是「检索给了正确材料，模型自己加了料」。工程化校验：

```python
def verify_faithfulness(answer: str, cited_chunks: list) -> Verdict:
    # 方法 A（便宜）：答案中的事实句必须能在引用 chunk 中找到支撑
    #   - 实体/数字对齐：答案中的金额、日期、政策名必须出现在引用中
    unsupported = extract_claims(answer) - grounded_in(cited_chunks)
    if unsupported:
        return Verdict(action="rewrite", unsupported=unsupported)
    # 方法 B（贵，抽样）：judge 模型对答案 vs 引用做忠实度评分
```

失配时的分级动作：**改写重试（1 次）→ 降级为「引用原文」回复 → 兜底话术 + 人工标记**。直接把幻觉答案放出去是最贵的选择（用户信任成本）。

### 3.3 拦截动作分级

| 级别 | 动作 | 适用 |
|---|---|---|
| L0 放行 | 正常返回 | 校验全过 |
| L1 改写 | 自动重试修复 | 格式/轻度忠实度失配 |
| L2 替换 | 用安全模板替代 | 中度风险（可给通用回答） |
| L3 拒答 | 拒绝话术 + 引导 | 违禁/注入/越权 |
| L4 隔离 | 拒绝 + 人工审核队列 + 记录审计 | 高危（涉政/自伤/攻击） |

所有拦截必须**落库分类**（哪层、哪类、置信度）——它是 23 章拦截率监控和误拦优化的数据基础。

## 4. 误拦治理：护栏的反面风险

护栏太严和太松都是事故：**误拦 = 产品体验事故，漏拦 = 合规事故。** 两者要有意识地权衡：

| 机制 | 做法 |
|---|---|
| 误拦率监控 | 拦截总量中「用户申诉/复核确认误拦」的比例，周报（22 章质量面板） |
| 申诉通道 | 被拦用户一键申诉 → 人工复核队列 → 误拦样本反哺规则 |
| 灰区放行 | 低置信拦截改为「标记放行 + 事后抽评」，避免一刀切 |
| 规则变更走 evals | 词表/阈值调整跑拦截测试集（含误拦样本），验证严松度 |
| 分场景严松度 | 客服场景宽松、儿童内容严格——护栏配置按场景版本化（同 16 章 prompt 版本化） |

**拦截测试集**：正向样本（应放行）+ 负向样本（应拦截）各 50+ 条，护栏规则每次变更必跑——没有它，收紧护栏必然悄悄杀掉正常流量。

## 5. 实现要点

| 组件 | 建议 |
|---|---|
| 输入护栏 | 同步执行，延迟预算 <50ms（正则/词表/轻量分类器） |
| 输出护栏 | 流式场景在首块/尾块分批校验；格式校验在流完成时 |
| LLM judge 复核 | 异步为主，高危场景同步（接受延迟） |
| Spring 栈 | 护栏做成独立的 `GuardrailChain`（责任链模式），每层可独立开关（05 章热更）——**出事故时能秒级调整严松度** |
| 审计 | 所有 L3/L4 拦截写审计日志（谁、输入摘要、命中规则、动作），合规可查（32 章） |

## 6. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 护栏规则写死在代码 | 攻击模式更新要发版 | 配置化 + 热更（05 章） |
| 只防注入不防输出泄漏 | 系统提示词/内部数据被套话输出 | 输出侧 PII/敏感词扫描 + 系统词指纹检测 |
| RAG 不做引用校验 | 幻觉直接面向用户 | 忠实度校验链（3.2） |
| 拦截了不留记录 | 无法优化严松度，无法审计 | 全量落库分类 |
| 误拦无申诉出口 | 静默流失用户 | 申诉通道 + 复核 + 反哺规则 |
| 护栏自身用 LLM 全量判 | 延迟+成本翻倍 | 分层校验链，模型判只做抽样/高危 |
| 系统提示词被间接泄漏 | 攻击者拿走你的 prompt 资产 | 输出指纹检测 + 定界符策略 + 高危场景注入分类器 |
| 护栏规则变更不走测试 | 误拦率悄悄飙升 | 拦截测试集（正负样本）+ evals |
| Agent 工具调用无白名单 | 注入 → 任意工具执行（最严重风险） | 工具白名单 + 参数 schema 校验 + 人工确认点（15 章） |
