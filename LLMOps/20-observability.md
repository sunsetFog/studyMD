# 20 - LLM 可观测性总览：看得见才修得快

> 传统 APM 解决不了 AI 应用的三个独有问题：**输出质量不可断言**（没有 exception 可抓）、
> **成本逐请求累积**（每次调用都在烧钱）、**行为随模型/输入分布漂移**。
> 本篇是 20-24 章的总纲：建立「trace → span → 会话 → 评估 → 告警 → 漂移」的分层模型。

---

## 1. LLM 应用要看什么：三类信号

| 信号类型 | 回答的问题 | 典型例子 |
|---|---|---|
| **系统信号**（传统 APM） | 服务活着吗？快吗？ | QPS、P95 延迟、错误率、CPU/内存 |
| **AI 信号**（本篇重点） | 答得好吗？烧了多少？ | 质量/满意度代理指标、token 用量、单次成本、拒答率、检索命中率 |
| **业务信号** | 用户满意吗？在用吗？ | 会话完成率、采纳率、点踩率、任务成功率 |

**核心难点：AI 信号没有天然的「断言」。** HTTP 500 一眼可见，但「模型这次回答偏保守了」只能靠代理指标 + 抽样评估。可观测性体系的设计目标：**让质量可代理、让成本可归因、让行为可对比**。

---

## 2. Trace / Span / 会话：三层观测结构

### 2.1 层次模型

```
Session（会话）            ← 用户视角：一次完整交互（可含多轮）
 └─ Trace（请求链路）      ← 一次用户请求进入系统的全链路
     ├─ span: retrieve     ← 检索（RAG：query 改写/召回/rerank）
     ├─ span: llm.generate ← 一次 LLM 调用（含 usage/模型/参数/prompt 版本）
     ├─ span: tool.call    ← Agent 场景的工具调用
     ├─ span: guardrail    ← 护栏过滤（27 章）
     └─ span: postprocess  ← 解析/格式化/重试（12 章重试在 trace 内合并）
```

为什么 LLM 应用必须建三层：

- **Session 层**：多轮对话的成本和质量必须按会话聚合（单次调用便宜、会话可能很贵——见 06 章多轮成本曲线）。
- **Trace 层**：一次回答 = 检索 + 生成 + 后处理，坏答案要能定位坏在哪一环。
- **Span 层**：LLM 调用 span 是计量与归因的最小单元，携带 06 章计量落库的全部字段。

### 2.2 AI 场景对 trace 的特殊要求

| 传统 trace | LLM trace 需要额外记录 |
|---|---|
| 方法名、耗时、状态码 | prompt_key@version、变量值（脱敏）、**渲染快照** |
| 请求/响应 body（可选） | 模型快照版本、temperature/params |
| 耗时分解 | **TTFT 与生成速率**（09 章两大延迟主轴） |
| — | usage（prompt/completion/cached tokens）→ 成本归因 |
| — | 重试次数、降级路径（11 章走了哪级降级） |
| — | 检索 span 的召回 chunk id + 分数 |
| — | 会话 ID / 用户 ID / 实验标签（17 章灰度对比的前提） |

**原则：LLM span 的 payload 必须足以完整重放这次调用**（脱敏后），否则 badcase 无法复现——这是 16 章「渲染快照」要求的落点。

### 2.3 一次会话的观测画像示例

```
session: s_8812  user: u_1024  feature: 客服助手
├─ trace t_001  cost ¥0.021  2.4s  👍
│   ├─ retrieve  320ms  top5  hit: kb#refund#p12
│   └─ llm.generate  1.9s  TTFT 410ms  1.2k in / 380 out  tier=mini  prompt v7
└─ trace t_002  cost ¥0.087  6.1s  👎 (用户反馈: 答非所问)
    ├─ retrieve  1.8s  top5  hit: 0 命中 ← 根因初判: 检索空结果
    ├─ llm.generate  3.9s  tier=flagship  prompt v7  (fallback v6 未触发)
    └─ guardrail  12ms  pass
```

坏答案的第一归因经常不在模型，而在检索——**没有 trace 分层就只能笼统地说「AI 答错了」**。

## 3. 质量的代理指标（在线侧）

离线 evals（25 章）不可能覆盖所有真实输入，线上质量靠代理指标持续观测：

| 代理指标 | 采集方式 | 信号强度 |
|---|---|---|
| 点赞/点踩率 | 显式 UI 按钮 | 强，但量少、有偏 |
| 重新生成率 | 用户点击「换一个答案」 | 强 |
| 会话放弃率 | 用户中途离开未再交互 | 中 |
| 采纳率 | 用户复制/使用生成内容 | 强（Copilot 类产品核心） |
| 人工反馈文本 | 「答案不对/过期/看不懂」选项 | 定位问题类型 |
| LLM-as-judge 抽评 | 用 judge 模型抽样打分 | 自动化覆盖面大，需校准（26 章） |
| 结构化失败率 | JSON 解析失败/schema 校验失败 | 强且免费，最优先看 |

**策略：免费结构化指标全量记，显式反馈全量收，LLM-as-judge 按 1-5% 抽样。** 三者构成漏斗：结构化异常 → 用户反馈 → 抽评定位，逐级深入。

## 4. 观测技术选型

| 方案 | 说明 | 适用 |
|---|---|---|
| **OpenTelemetry + 自建** | OTel span 落 Jaeger/Tempo + AI 属性自定义，成本/质量指标进 Prometheus | Java/Spring 团队复用既有 Micrometer/OTel 设施 |
| **LLM 观测平台** | Langfuse（可自托管）/ LangSmith / Arize Phoenix：原生 prompt 版本管理、trace 重放、评估关联 | 快速获得 AI 专属视图，Langfuse 开源可私有化 |
| **混合** | 系统信号在 APM、AI 信号在 LLM 平台，以 trace_id 关联 | 大多数团队的现实选择 |

**Spring 栈提示**：`Micrometer Observation` 天然生成 span，LLM client 封装处加 AI 属性即可无缝接入既有 OTel 链路；trace_id 透传给 Langfuse SDK 可打通两套视图。

## 5. 可观测性成熟度自评

| 级别 | 特征 | 危险信号 |
|---|---|---|
| L0 | 只有服务日志 | 出问题只能靠用户投诉发现 |
| L1 | 有 trace，LLM 调用只是一个 span | 知道「慢/报错」，不知道「为什么答错」 |
| L2 | LLM span 带 prompt 版本 + usage，成本可归因 | 能查 badcase，但发现靠运气 |
| L3 | 质量代理指标 + 看板 + 分版本对比 | 主动发现退化，灰度可量化 |
| L4 | 告警 + 漂移检测 + 评估闭环 | 变更与故障都有自动化防线 |

本篇后四章即 L3-L4 的落地：21 落库规范 → 22 看板 → 23 告警 → 24 漂移。

## 6. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| LLM 调用埋一个普通 span 就完事 | 无法回答「哪个 prompt 版本烧的钱」 | span 强制携带 AI 属性清单 |
| trace 不含渲染快照 | badcase 永远无法复现 | payload 可重放（脱敏后） |
| 按请求而非按会话看成本 | 多轮会话的隐性成本不可见 | Session 聚合层 |
| 重试在 trace 里变成独立 trace | 单次用户请求的成本/延迟被低估 | 重试在 trace 内合并（12 章） |
| 质量只看点赞点踩 | 量太少且幸存者偏差，大样本全是沉默用户 | 结构化指标全量 + judge 抽样 |
| 观测数据本身含敏感信息泄露 | 合规事故 | 落库前统一脱敏（05 章） |
| 系统信号与 AI 信号两套体系互不关联 | 排障时两边对不上 | 统一 trace_id 贯穿 |

---

## 7. Checklist

- [ ] Session / Trace / Span 三层结构落地，LLM span 携带 AI 属性（prompt 版本、usage、TTFT、降级路径）
- [ ] LLM span payload 足以重放（脱敏后），落库前统一脱敏
- [ ] 多轮成本与质量按会话聚合
- [ ] 重试、降级在 trace 内可见并正确归属成本
- [ ] 质量代理指标三层：结构化失败（全量）+ 用户反馈（全量）+ judge 抽评（1-5%）
- [ ] 检索 span 记录召回 chunk 与分数，坏答案可分环节归因
- [ ] 系统信号（APM）与 AI 信号（LLM 平台）以 trace_id 关联
- [ ] 成熟度至少达到 L2（成本可归因），并向 L3（质量可对比）推进
