# 31 - CI/CD 流水线与发布策略

> 传统流水线 + AI 专属环节（prompt CI、evals、金丝雀集）= AI 应用的完整流水线。
> 本篇整合 17 章（prompt CI/CD）与 28 章（发布门禁），给出从提交到生产的全景视图。

---

## 1. 全景流水线

```
代码/配置提交（应用代码 / prompt yaml / 护栏规则 / KB 管道）
  ↓
【CI 阶段】
  ├─ 构建 & 单测 & 静态扫描
  ├─ prompt-lint / 渲染 diff（17 章）
  ├─ 冒烟集（25 章，<5 分钟）
  ├─ 合同测试（解析层，28 章）
  └─ 镜像构建（prompt 不进镜像，30 章）
  ↓
【发布前门禁】
  ├─ 全量 evals（夜间已跑，取最新结果）
  ├─ 门禁矩阵逐项检查（28 章硬条件）
  └─ 发布单登记（灰度计划/回滚命令/观察指标）
  ↓
【部署】
  ├─ K8s 滚动/蓝绿（30 章：宽限期+摘流）
  ├─ 应用层灰度（17 章：用户维度分流）
  └─ 配置生效验证（热更项立即校验）
  ↓
【发布后观察】
  ├─ 1h/24h/1w 观察计划执行（22 章看板）
  ├─ 金丝雀集次日基准确认（24 章）
  └─ 回滚就绪：指针级回滚随时可执行
```

**关键设计：evals 与构建解耦**——全量回归每夜跑（覆盖最新 main），发布时只取门禁所需的最新结果。若 main 自夜间评估后又有变更，触发增量重跑受影响场景。

---

## 2. 多环境策略

| 环境 | 用途 | 与生产的差异边界 |
|---|---|---|
| dev | 开发自测 | 可用假模型（mock LLM）跑集成测试，省钱稳定 |
| staging | 端到端验证 | 用真实供应商 + **降档模型**，控制成本 |
| prod | 生产 | 全配置 + 灰度 |

要点：

- **mock LLM 是 CI 的标配**：单测/集成测试用录制回放（cassette）或假实现，CI 不调真实 API（慢、贵、结果随机）。真实调用的验证交给 evals 流水线（它有独立的限速与预算）。
- staging 与 prod 的差异必须显式登记（模型档位、数据规模），「staging 绿了但 prod 崩」最常见的根因就是差异没登记。
- 环境间配置差异走 05 章分层配置，代码零 if-else。

## 3. 发布节奏与变更纪律

### 3.1 节奏设计

| 变更类型 | 节奏 | 说明 |
|---|---|---|
| 应用代码 | 随时（每日多批） | 常规 CD |
| prompt/护栏/路由配置 | 独立节奏（工作日、避开高峰） | 走 17 章灰度，不等代码发版 |
| 模型/KB 大变更 | 排期制（18/19 章流程） | 周级准备 |
| 供应商相关 | 跟随公告窗口 | 18 章：避开供应商变更期发布 |

**prompt 与代码分离发布**是 16 章存储方案带来的能力：配置类变更独立走灰度，不被发版节奏绑架；同时发布单里保持关联（28 章组合变更纪律）。

### 3.2 发布窗口纪律

- 避开流量高峰（发布初期问题发现窗口与高峰期重叠会放大影响面）
- 避开节假日/周五下午（人手不足时别发布）
- 供应商有已知变更公告时，冻结非必要发布（18 章）

## 4. 流水线工程细节

### 4.1 关键配置参考

```yaml
# 发布流水线的 AI 专属 stage 示例
stages:
  - name: smoke-evals
    budget: {minutes: 5}
    steps:
      - render-diff          # 渲染快照 diff → PR 评论
      - prompt-lint
      - smoke-run            # 限速执行，失败用例自动附 trace 链接
  - name: release-gate
    steps:
      - fetch-nightly-evals  # 取最新全量结果，检查时效（<24h）
      - gate-matrix-check    # 28 章硬条件矩阵
      - deploy-manifest-gen  # 生成发布单（含回滚命令）
  - name: deploy
    steps:
      - k8s-rolling          # 30 章宽限期配置
      - config-hotreload-verify
      - canary-register      # 注册灰度实验（17 章）
```

### 4.2 流水线自身的运维指标

| 指标 | 健康标准 |
|---|---|
| 冒烟集时长 | P95 < 5 分钟（超时说明用例膨胀或供应商变慢） |
| 全量回归时长 | < 2 小时 |
| 门禁拦截率 | 5-20% 之间：0% 说明门禁形同虚设，>30% 说明上游质量失控 |
| 紧急通道占比 | < 5%（28 章纪律） |
| 流水线失败重试率 | evals 类失败区分「真退化」与「供应商抖动」重试 |

## 5. 回滚体系总装

各章回滚能力的统一视图（值班时查这张表）：

| 变更 | 回滚手段 | 速度 | 章 |
|---|---|---|---|
| prompt 版本 | 切 active 指针 | 秒级 | 17 |
| 模型/路由 | 网关 tier 切换 | 秒级 | 04 |
| 护栏严松度 | 配置热更 | 秒级 | 27 |
| 降级开关/限流 | 应急开关清单 | 秒级 | 10/11 |
| 知识库索引 | 切回旧 collection | 分钟级 | 19 |
| 应用代码 | K8s 回滚到上一版本 | 分钟级 | 30 |
| Prompt+代码组合 | 按发布单绑定的回滚序列 | 分钟级 | 16/28 |

原则：**回滚优先走配置与指针（秒级），部署级回滚（分钟级）留给代码类变更。** 所有回滚动作在发布单预写并在演练环境验证过（28 章）。

## 6. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| CI 里直调真实供应商 | 慢、贵、结果随机导致流水线闪烁 | mock/录制回放，真实验证交给 evals |
| 全量回归阻塞每次发布 | 发布小时级延迟，团队开始绕过门禁 | 夜跑解耦 + 发布取最新结果 |
| staging 与 prod 差异不登记 | 「staging 绿了 prod 崩」 | 差异显式登记，关键差异必测 |
| prompt 变更与代码发版强行捆绑 | 配置级调优被发版节奏拖慢 | 分离发布（16 章存储能力） |
| 门禁拦截率 0% 长期不变 | 门禁形同虚设 | 监控拦截率健康区间 |
| 发布单不登记灰度与回滚 | 出事时现场手忙脚乱 | manifest 生成自动化 |
| 周五/高峰期发布 | 人手不足 + 影响放大 | 发布窗口纪律 |
| 回滚方案从未演练 | 真事故时回滚也失败 | 周期性回滚演练（34 章） |
