# 09 · 延迟优化：让等待可以被接受

## 1. 延迟的构成

```
总延迟 = 网络 + 排队 + 首字生成(TTFT) + 全文生成
         │      │        │            │
     客户端↔API 限流/排队  prompt处理+首token   逐token生成

典型数值（云端 API）：
  网络 RTT           50-200ms
  排队/限流          0 - 数秒（高峰期）
  首 token（TTFT）   300ms - 2s（与输入长度正相关）
  生成速率           30-80 token/s（输出越长越慢）
  1000 token 输出    ≈ 12-30s
```

**关键认知**：
- 输入越长，TTFT 越长（处理输入要时间）——这就是为什么压缩上下文也降延迟
- 输出长度决定总时长的下限——生成 2000 token 不可能 5 秒内完成
- 所以延迟优化的两大主轴：**缩短输入** 与 **让用户感知不到等待**

## 2. 延迟预算（Latency Budget）

按场景设定目标，写进验收标准：

| 场景 | 首字 TTFT | 总时长 | 手段 |
|---|---|---|---|
| 聊天/客服 | < 1.5s | < 15s | 流式 + 上下文压缩 |
| 内联补全 | < 300ms | < 800ms | 小模型 + 极短上下文 |
| 文档摘要 | — | < 30s | 分块并行 + 进度提示 |
| 后台批处理 | — | 分钟级可接受 | 批量 API |

## 3. 感知性能优化（最重要，成本最低）

### 流式输出（Stream）

```
把「等 15 秒看全文」变成「1 秒看到开头 + 持续输出」
总时长不变，主观等待感下降 80%+

实现要点：
① SSE / WebSocket 逐 token 转发
② 前端用打字机效果渲染（Markdown 增量解析）
③ 网关透传流，并单独记录 TTFT
④ 客户端断开要停止上游请求（省钱）
```

### 过程反馈（让用户知道在干活）

```
阶段提示：「正在检索知识库…」→「正在组织答案…」→ 输出
多步任务显示进度：「第 2/4 步：分析数据…」
骨架屏占位，避免布局跳动
```

### 并行预取

```
用户还在打字时：
① 提前做检索（输入到一定长度就触发语义检索）
② 提前加载用户偏好/历史
点击发送时检索已完成 → 省 500ms-2s
```

### 乐观 UI

```
发送消息立即上屏（不等确认）
生成中的内容先展示骨架/占位
```

## 4. 实际性能优化

### ① 缩短输入

```
压缩上下文（同成本优化，见 07-③）
检索精简（top-k 减小）
系统 prompt 精简
→ 输入每减 50%，TTFT 约减 30-50%
```

### ② 缩短输出

```
限制输出长度（max_tokens + prompt 约束）
结构化输出（列表/要点比长段落 token 少）
分批返回（先给摘要，详细内容按需展开）
```

### ③ 换更快的模型

```
小模型生成速率通常是旗舰的 2-5 倍
简单场景（分类、短回答、补全）直接用小模型
这是「路由」的另一个理由（见 07-②）
```

### ④ 并行化多步任务

```
串行：检索 → 生成摘要 → 生成正文   （3 × 延迟）
并行：检索与摘要并行；正文分块并行生成后拼接
注意：并行会放大瞬时 token 消耗（成本与限流压力）
```

### ⑤ 连接与基础设施

```
① 复用 HTTP 连接（keep-alive / 连接池）——省 50-100ms/次
② 服务部署靠近模型 API 区域（减少跨区 RTT）
③ 异步任务用队列削峰，避免高峰期排队不可控
```

## 5. 超时与分级体验

```
超时分级：
  TTFT 超时（如 5s 没有首字）→ 提示重试或自动重试
  总时长超时（如 30s）→ 取消 + 转后台 + 完成后通知

分级体验：
  快路径：缓存命中 / 小模型能处理 → 立即返回
  慢路径：复杂任务 → 明确告知「需要约 30 秒，可稍后回来」
```

## 6. 监控指标

| 指标 | 定义 | 目标参考 |
|---|---|---|
| TTFT P50/P95 | 首字时间 | P95 < 2s（交互场景） |
| 总延迟 P50/P95 | 全文完成 | 按场景预算 |
| 生成速率 | token/s | 异常下降 = 供应商降速 |
| 超时率 | 超时请求占比 | < 1% |
| 中断率 | 用户中途放弃比例 | 质量体验信号 |

> 生成速率突变是供应商侧问题的早期信号（限流/降速），比错误率更敏感。

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 只优化总延迟不优化感知 | 等待依然煎熬 | 流式 + 过程反馈优先 |
| 流式输出没有打字机渲染 | 用户看不出流式价值 | 前端增量渲染 |
| 客户端断开不取消上游 | 白烧钱 | 断连取消（网关实现） |
| 输入塞太长 | TTFT 飙升 | 压缩上下文 |
| 多步任务串行 | 延迟叠加 | 识别可并行步骤 |
| 无延迟预算 | 性能问题上线才发现 | 按场景定 TTFT/总时长目标 |
| 高峰期排队不可控 | 用户体验忽快忽慢 | 削峰 + 分级体验 |
| 只看平均值 | 长尾用户一直在忍 | 看 P95/P99 |

## 8. Checklist

- [ ] 每个场景有明确的延迟预算（TTFT + 总时长）
- [ ] 交互场景全部流式输出，前端有打字机渲染
- [ ] 多步任务有过程反馈与进度提示
- [ ] 上下文长度已压缩（输入构成归因过）
- [ ] 客户端断开时取消上游请求
- [ ] 有 TTFT/总延迟/生成速率/超时率监控（P95 口径）
- [ ] 有分级体验（快路径 + 慢路径明确告知）
- [ ] 长任务异步化，支持离开后通知
