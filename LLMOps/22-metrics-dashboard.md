# 22 - 指标设计与看板：质量 / 成本 / 延迟

> 21 章落了库，本篇把数据变成可看、可对比、可行动的看板。
> 看板设计的核心原则：**每一块面板都要回答一个「要不要做动作」的问题**，回答不了的别放上屏。

---

## 1. 指标体系：先分层，再选图

### 1.1 三层指标金字塔

```
            ┌─────────────┐
            │  决策层       │  周报/月报：单位成本、毛利率、采纳率、SLA 达成
            ├─────────────┤
            │  运营层       │  日常值班：错误率、P95 延迟、单次成本、拒答率、灰度对比
            ├─────────────┤
            │  诊断层       │  排障下钻：分场景/分 tier/分 prompt 版本/分供应商明细
            └─────────────┘
```

### 1.2 核心指标清单（AI 信号部分）

| 维度 | 指标 | 计算口径 | 联动章节 |
|---|---|---|---|
| 成本 | 单次请求成本 P50/P95 | cost / 请求数 | 06 |
| 成本 | 单会话成本、会话轮均成本 | 会话维度聚合 | 06 |
| 成本 | 各功能/各 tier 成本占比 | 分维度归因 | 06 |
| 成本 | 缓存命中率（供应商前缀 + 自建） | cached_tokens 占比 | 08 |
| 成本 | 预算消耗进度 | 当日预算已用 % | 10 |
| 延迟 | TTFT P50/P95/P99 | 生成首 token 时间 | 09 |
| 延迟 | 端到端总时长 P50/P95 | 含检索/护栏 | 09 |
| 延迟 | 生成速率 tok/s | output_tokens / (total - ttft) | 09 |
| 质量 | 结构化解析失败率 | parse_ok=false 占比 | 21 |
| 质量 | 拒答率（模型拒 + 护栏拦） | 分类型拆分 | 27 |
| 质量 | 点踩率 / 重新生成率 / 会话放弃率 | 显式反馈 | 20 |
| 质量 | judge 抽评分分布 | 1-5 分样本 | 26 |
| 容量 | 错误率（分错误类型）、降级触发率 | 分级统计 | 11-13 |

系统信号（QPS/CPU/队列深度）沿用既有 APM，不在本篇重复。

## 2. 看板设计

### 2.1 主看板（运营层）布局建议

```
┌────────────────────────────────────────────────────────┐
│ 顶部健康条： 今日请求量 | 成本 | P95延迟 | 错误率 | 点踩率      │ ← 一眼判断是否异常
├──────────────────────────┬─────────────────────────────┤
│ ① 成本趋势（按天，按功能堆叠）│ ② 延迟趋势（TTFT/总时长 P95） │
├──────────────────────────┼─────────────────────────────┤
│ ③ 单次成本分布直方图        │ ④ 错误与降级率（分类型堆叠）   │
├──────────────────────────┼─────────────────────────────┤
│ ⑤ 质量代理指标趋势          │ ⑥ 模型使用占比（tier/供应商） │
├──────────────────────────┴─────────────────────────────┤
│ ⑦ Top 问题清单：点踩 Top 会话 / parse_fail Top prompt 版本  │ ← 直接可点进 trace
└────────────────────────────────────────────────────────┘
```

### 2.2 分版本对比视图（灰度专用）

17 章灰度的配套视图——**同一指标，按 prompt 版本/实验分组对比**：

```
指标：点踩率     v6(active) 0.8%   v7(testing 5%) 1.9%   ⚠️ +1.1pp
指标：单次成本   v6 ¥0.010   v7 ¥0.014              ⚠️ +40% (输出变长)
指标：解析失败率  v6 0.2%    v7 0.1%                ✅
```

没有这张图，17 章的灰度就只剩「没报错」，质量的退化完全不可见。

### 2.3 下钻路径设计

看板必须支持从异常点一路点到原始数据：

```
看板异常（成本涨 30%）
 → 按功能维度拆解（哪个功能涨的）
 → 按 prompt 版本拆解（是不是昨天发的 v7）
 → 按 tier/供应商拆解（是不是 fallback 到贵模型了）
 → 明细表：该维度 trace 列表（带成本、usage、时间）
 → 单条 trace 详情（重放 prompt）
```

**每一步都要求可在 3 次点击内完成**，做不到说明落库维度缺了（回 21 章补字段）。

## 3. 关键报表：三个必建

### 3.1 成本日报/周报（决策层）

自动生成，含同比环比：

```
日期: 2026-11-05  总成本: ¥1,204 (环比 +18%)
┌──────────────┬────────┬────────┬──────────┐
│ 功能          │ 成本    │ 环比    │ 单次成本   │
│ 客服助手      │ ¥860    │ +25% ⚠️ │ ¥0.011    │
│ 文档摘要      │ ¥344    │ +3%    │ ¥0.008    │
└──────────────┴────────┴────────┴──────────┘
异常说明: 客服助手 +25% 由 prompt v7 输出膨胀(+38% output tokens)贡献
建议: 17 章灰度面板复核 v7，或收紧 max_tokens
```

### 3.2 SLA/质量周报

- 各场景可用性（按错误率 + 降级率折算）
- 质量代理指标趋势与阈值达成
- 本周 badcase 抽样与根因分类（检索 vs prompt vs 模型 vs 上游）——这是评估集迭代的输入。

### 3.3 容量与预算看板（衔接 10 章）

预算消耗进度条（日/月）、限流触发次数、熔断事件时间线——运营层判断「钱还够不够烧」的主视图。

## 4. 实现要点

| 组件 | 建议做法 |
|---|---|
| 指标聚合 | 21 章明细表上做物化视图/定时聚合（ClickHouse rollup / Spark 定时任务），别在明细上实时聚合大范围 |
| 图表 | Grafana（接 Prometheus + ClickHouse 数据源）；LLM 平台（Langfuse）自带的 dashboard 做 trace 视图 |
| 数据新鲜度 | 运营层 1-5 分钟延迟可接受；预算熔断类指标必须准实时（<1 分钟） |
| 权限 | 成本数据默认限管理层可见；trace 明细按 05 章权限/脱敏策略控制 |
| 版本对齐 | 看板本身配置进 Git 管理，变更可回溯 |

**Spring/Java 参考**：Micrometer 打点 + Prometheus 抓取 + Grafana 展示是既有设施；AI 指标只是新增 metric series，成本类聚合建议走明细表（Prometheus 不适合做金额累计的精确统计）。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 看板堆 30 张图没人看 | 信息淹没，异常漏看 | 每块面板绑定一个动作问题 |
| 指标只有全局值没有维度拆解 | 成本涨了但查不出原因 | 强制支持按功能/版本/tier 拆解 |
| 点踩率直接当质量指标 | 反馈人群偏差（愤怒用户更爱点） | 多代理指标组合 + 抽评校准 |
| 成本看板与账单口径不一致 | 报表可信度崩塌 | 与 21 章对账机制对齐口径 |
| Prometheus 上做精确成本累计 | 浮点误差 + 重启重置 | 成本统计走明细表/OLAP |
| 看板不可下钻 | 看见异常但查不动 | 3 次点击到 trace 明细 |
| 灰度对比只有请求量没有质量 | 灰度决策瞎拍 | 分版本对比视图必建 |
| 指标口径每人一个版本 | 会上吵半天数字对不上 | 口径文档化，看板注明计算方式 |
