# 01 · LLMOps 是什么：AI 应用的运维为何不同

## 1. 一句话定义

> LLMOps = 让基于大模型的**应用**在生产环境中**可靠、可控、可持续**运行的一整套工程实践。
> 覆盖：开发 → 部署 → 监控 → 评估 → 迭代 的完整闭环。

注意：LLMOps 关注的是**应用侧**（你调用/编排模型，不训练模型），而不是模型训练侧。

## 2. DevOps / MLOps / LLMOps 的差别

| 维度 | DevOps（传统软件） | MLOps（机器学习） | **LLMOps（大模型应用）** |
|---|---|---|---|
| 核心资产 | 代码 | 代码 + 数据 + 模型 | 代码 + **Prompt + 知识库 + 模型** |
| 输出 | 确定性 | 概率性（有准确率指标） | **概率性（开放式，难以自动判对错）** |
| 变更 | 发版 | 重新训练 + 发版 | **改 prompt / 换模型 / 改检索**（高频轻量） |
| 边际成本 | ≈ 0 | 低 | **高（每次调用都要钱）** |
| 失败模式 | 报错、崩溃 | 预测不准 | 报错 + **质量悄悄退化 / 幻觉 / 成本失控** |
| 测试 | 单元测试 | 测试集 + 指标 | **evals（需 LLM 或人工判定）** |
| 迭代速度 | 周-月 | 周-月 | 天-小时 |
| 退化风险 | 一般不退化 | 模型固定可复现 | **供应商静默更新，行为会漂移** |

结论：传统 DevOps 的工具（监控/CI/CD/告警）照用，但**必须加一层专属能力**。

## 3. LLMOps 的五大专属挑战

| 挑战 | 表现 | 对应篇目 |
|---|---|---|
| ① 成本可控 | 一个死循环 prompt 烧掉几百块；免费用户越多亏越多 | 06-10 |
| ② 输出概率性 | 同一请求结果不同；格式偶发不合法 | 11-15、27 |
| ③ 行为漂移 | 供应商更新模型后质量/风格突变 | 24、28 |
| ④ Prompt 即资产 | prompt 改动影响巨大，但常散落各处、无版本无回滚 | 16-18 |
| ⑤ 质量难自动判定 | 「回答得好不好」多数场景无法用断言判断 | 25-26 |

## 4. LLMOps 生命周期全景

```
      ┌────────────── 开发期 ──────────────┐
      │  需求 → spike → prompt 原型        │
      │    → evals 集构建 → 离线评估        │
      └──────────────┬────────────────────┘
                     ↓
      ┌────────────── 发布期 ──────────────┐
      │  CI 跑 evals → 发布门禁            │
      │    → 影子流量 → 小流量灰度 → 全量   │
      └──────────────┬────────────────────┘
                     ↓
      ┌────────────── 运行期 ──────────────┐
      │  网关（路由/限流/熔断/缓存）        │
      │    → 可观测（trace/指标/日志）      │
      │    → 成本控制（预算/配额）          │
      │    → 漂移检测 + 线上 eval           │
      └──────────────┬────────────────────┘
                     ↓
              反馈（bad case → evals 集）→ 回到开发期
```

**闭环的关键机制**：线上 bad case 持续流入 evals 集；每次 prompt/模型改动必须跑回归。

## 5. 一张图看懂 LLMOps 的技术栈分层

```
┌─────────────────────────────────────────────┐
│ 应用层：业务功能（客服/写作/摘要…）           │
├─────────────────────────────────────────────┤
│ 编排层：Prompt 模板、RAG 检索、多步工作流、Agent │
├─────────────────────────────────────────────┤
│ 质量层：evals、护栏、审核、降级兜底            │
├─────────────────────────────────────────────┤
│ 网关层：路由、限流、熔断、缓存、重试、日志      │
├─────────────────────────────────────────────┤
│ 模型层：供应商 API（OpenAI/Anthropic/国产）或自建推理 │
└─────────────────────────────────────────────┘
```

传统运维（K8s、CI/CD、日志监控）照用；**网关层、质量层是 LLMOps 新增的**。

## 6. 成熟度模型（判断你在哪一档）

| 级别 | 特征 | 风险 |
|---|---|---|
| L0 手工 | prompt 写死在代码里，无监控，出问题靠用户投诉 | 爆炸半径极大 |
| L1 基础 | 有日志、有重试、prompt 外置配置 | 成本与质量仍不可控 |
| L2 规范 | 网关统一、限流熔断、成本告警、请求全量落库 | 换模型仍靠胆量 |
| L3 闭环 | evals 进 CI、灰度发布、bad case 回流、漂移检测 | ★ 目标档位 |
| L4 自动化 | 自动评估+自动回滚、自适应路由、A/B 常态化 | 少数大团队 |

**建议路径**：个人/小团队直接做到 L2（一周可达成），逐步演进到 L3。

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 用传统运维思维做 AI | 只监控 5xx，不管质量 | 质量指标进监控（采纳率/👎率） |
| prompt 硬编码 | 改一次发一次版，无法回滚 | 外置 + 版本化（见 16） |
| 无成本意识 | 月底账单爆炸 | 预算熔断 + 告警（见 10） |
| 单点依赖一个供应商 | 涨价/下线/限流就停摆 | 模型网关抽象（见 04） |
| 无 evals | 改 prompt 全靠感觉 | 先建 50 条测试集（见 25） |
| 日志不留存 | 无法复现线上问题 | 请求/响应全量记录 + 脱敏（见 21） |
