# 32 - 安全与合规运维：密钥、数据与审计

> Product/35 定义了信任与合规的产品策略，本篇讲工程落地。AI 应用相比传统后端新增的
> 攻击面：密钥直接对应「烧钱通道」、prompt 与用户对话是敏感数据资产、模型输出可能成为泄漏出口。

---

## 1. 密钥安全（最高频事故源）

### 1.1 API Key 的特殊风险

API Key 泄漏的后果是**直接资金损失**：捡到 key 的人可以无限刷你的额度（不是传统 API 的「数据泄漏」而是「烧钱泄漏」）。GitHub 上每天都有从公开仓库扫到的 key 被盗刷的案例。

### 1.2 密钥管理清单（05 章的落地细化）

| 要求 | 做法 |
|---|---|
| 存储 | 密钥管理服务（KMS/Secrets Manager/Vault），禁止：代码、配置文件、环境变量明文、聊天记录、工单 |
| 分发 | 只注入模型网关（04 章），业务服务零密钥 |
| 权限最小化 | 按供应商/项目分 key，禁用组织级全权 key；可设限额的 key 一律设限额 |
| 轮换 | 季度例行 + 事件驱动；双 key 过渡（新旧并存期验证） |
| 扫描 | CI 密钥扫描（gitleaks 等）+ 仓库历史扫描（泄漏过的 key 必须轮换，删除提交没用） |
| 监控 | 供应商侧用量告警（异常消耗即报警，10 章预算体系的外围） |

### 1.3 泄漏应急 SOP

```
发现泄漏（扫描告警/账单异常/外部通报）
 1. 立即吊销该 key（分钟级，供应商控制台）——先止血再排查
 2. 网关切换备用 key（双 key 过渡的价值时刻）
 3. 核账：泄漏窗口内的异常消耗清单，联系供应商申请争议处理
 4. 溯源：怎么漏的（提交/日志/第三方服务）→ 修复渠道
 5. 复盘：扫描规则与流程改进
```

## 2. 数据安全

### 2.1 AI 应用的数据流与敏感点

```
用户输入 ──> 编排/日志/trace ──> 供应商 API ──> 模型输出
   │              │                │              │
 PII 采集      明文落库风险      第三方数据边界    输出泄漏
```

| 敏感点 | 风险 | 控制措施 |
|---|---|---|
| 用户输入中的 PII | 落库/出域合规风险 | 入口脱敏管道（05 章）；确需原文的场景显式声明 + 最短保留期 |
| prompt 中的内部数据 | 系统提示词泄漏（27 章输出指纹防护） | 分级：公开知识可进 prompt，机密内容走运行时检索（RAG）而非硬编码 |
| 输出引用 | 越权内容经 RAG 泄漏 | 检索 acl 过滤（19 章）+ 输出侧 PII 扫描（27 章） |
| trace/日志 | 观测数据成为敏感数据池 | 分级存储 + 权限控制（21 章），trace 明细默认限内部访问 |
| 供应商数据边界 | 合同约定 vs 实际使用 | 核对供应商数据处理条款（是否训练用你的数据、保留期、驻留区域），登记到合规台账 |

### 2.2 数据保留与删除

| 数据 | 默认保留 | 删除机制 |
|---|---|---|
| 计量明细（无敏感字段） | ≥180 天 | 到期自动清理 |
| trace/prompt 快照 | 30-90 天 | 到期清理；badcase 永久保留项定期复核脱敏状态 |
| 用户对话原文 | 按产品策略（如 30 天） | **用户删除请求必须级联清除**：会话、trace、向量库 chunk、备份——建立「按用户 ID 删除」的幂等作业（14 章幂等） |
| 供应商侧 | 合同约定 | 调用供应商删除 API 的（如 OpenAI 数据控制端点）纳入 SOP |

## 3. 访问控制与审计

### 3.1 内部访问分级

| 对象 | 权限 |
|---|---|
| 值班工程师 | 看板、告警、trace 摘要（脱敏）、应急开关 |
| 平台团队 | 全量 trace（按需申请 + 操作留痕）、密钥管理 |
| 产品/运营 | 质量看板、评估报告；trace 明细默认不可见 |

### 3.2 审计事件清单（必须留痕的操作）

```
- 密钥：创建/轮换/吊销/配置变更
- prompt：版本发布/回滚/紧急修改（16 章变更审计）
- 配置：降级开关/限流/护栏严松度热更（10/27 章）
- 知识库：内容删除/权限变更（19 章）
- 访问：trace 明细查看、数据导出
- 拦截：L3/L4 护栏动作（27 章）
```

审计日志本身**只增不改、独立存储、保留 ≥1 年**——它是合规检查与事故溯源的最后一道防线。

## 4. 合规要点（中国场景常见项）

> 以下为工程侧需要配合的常见合规要求，具体条款以法务/合规团队判断为准。

| 要求 | 工程配合点 |
|---|---|
| 生成内容标识 | AI 生成内容添加显式/隐式标识（水印/元数据），接口层统一注入 |
| 内容安全 | 输入输出审核（27 章护栏）+ 拦截审计留痕 |
| 用户投诉与申诉 | 27 章申诉通道 + 工单闭环记录 |
| 数据驻留 | 选择数据驻留区域匹配的供应商部署（如Azure/AWS 中国区或本地化版本） |
| 评估与备案材料 | 25 章评估报告、27 章拦截记录、32 章审计日志是备案/年审的现成材料 |

**设计建议**：合规所需的记录（审核日志、标识、申诉记录）在架构期就纳入落库设计——事后补记录的成本远高于顺路记录。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| Key 放环境变量/配置文件 | 一次泄漏 = 无限烧钱通道 | KMS + 网关收敛 + 限额 |
| 泄漏后只删提交不换 key | 历史 commit 里照样能扫到 | 吊销 + 轮换 + 全历史扫描 |
| 供应商数据条款没核对 | 用户数据被用于供应商训练，合规爆雷 | 合规台账登记各供应商条款 |
| trace 存储人人可看 | 敏感对话被内部滥用 | 访问分级 + 查看留痕 |
| 用户删除请求只删会话表 | trace/向量库/备份里还在 | 级联删除幂等作业 |
| 系统提示词硬编码内部机密 | 越狱后被完整吐出 | 机密走 RAG 运行时检索 |
| 审计日志可被修改 | 违规操作无据可查 | append-only 独立存储 |
| 合规材料平时不收集 | 备案/检查时现补，成本巨大 | 评估/拦截/审计记录顺路落库 |

## 6. Checklist

- [ ] API Key 全部走 KMS，仅网关持有，按供应商分 key 且设限额
- [ ] CI + 历史 + 日志三处密钥扫描，泄漏 key 吊销（而非删除）
- [ ] 泄漏应急 SOP 成文（吊销→切备用→核账→溯源→复盘）
- [ ] 数据流敏感点登记：PII 脱敏、prompt 分级、输出 PII 扫描、acl 过滤
- [ ] 各供应商数据条款（训练使用/保留期/驻留）登记合规台账
- [ ] 用户级删除 = 级联清除幂等作业（会话/trace/向量/备份）
- [ ] 内部访问分级 + 敏感操作留痕
- [ ] 审计事件清单落地，append-only 独立存储 ≥1 年
- [ ] 生成内容标识在接口层统一注入
- [ ] 合规所需记录（评估/拦截/审计）在架构期纳入落库设计
