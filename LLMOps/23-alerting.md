# 23 - 告警规则、分级与值班响应

> 看板解决「人主动看」，告警解决「异常来找人」。AI 应用的告警难点：
> 质量类异常没有二值信号，容易做成「永远不响」或「天天乱响」两个极端。
> 本篇给出可落地的规则分级与值班 SOP。

---

## 1. 告警设计原则

1. **每条告警必须有：触发条件、严重级别、预期动作、负责人。** 四要素缺一即不算告警，只能算日志。
2. **宁可漏掉轻微异常，不可天天误报。** 误报的代价是狼来了效应——真正的事故发生时没人看了。
3. 质量类告警用「相对基线」而非绝对阈值：上线第一个月绝对值都是拍的，基线漂移才是信号。
4. 告警分级与响应义务绑定（见第 3 节）：P0 睡觉叫醒，P4 只写周报。

---

## 2. 告警规则清单（按信号类型）

### 2.1 系统与可用性类（成熟模式，直接复用）

| 规则 | 条件示例 | 级别 |
|---|---|---|
| 服务不可用 | 健康 check 失败 / 5xx > 5% 持续 5 分钟 | P0 |
| 延迟劣化 | 端到端 P95 > 预算 1.5 倍持续 15 分钟 | P2 |
| 队列积压 | 异步任务队列深度 > 容量 80% | P2 |

### 2.2 AI 专属：可用性类

| 规则 | 条件示例 | 级别 | 对应章节 |
|---|---|---|---|
| 供应商大面积失败 | 某供应商错误率 >10% 持续 10 分钟 | P1 | 04 |
| 降级链用尽 | L3/L4 级降级（11 章）被触发 | P1 | 11 |
| 熔断打开 | 主 tier 熔断器 open 持续 >5 分钟 | P1 | 13 |
| 预算熔断 | 日预算 100% 触发（服务实际受限） | P0 | 10 |
| 预算告急 | 日/月预算 80% | P3 | 10 |
| 解析失败率飙升 | parse_fail > 基线 5 倍持续 15 分钟 | P1 | 12/21 |
| 生成速率异常 | tok/s < 历史均值 50%（模型 Hang） | P2 | 09 |

### 2.3 AI 专属：质量类（相对基线）

| 规则 | 条件示例 | 级别 |
|---|---|---|
| 金丝雀集掉分 | 每日基准分数周环比 -2% 以上 | P2 |
| 点踩率上升 | 周滑动均值 +30% 相对基线 | P3 |
| 拒答率异常 | 拒答率 +50% 相对基线（模型/护栏行为变化） | P3 |
| 成本漂移 | 单次成本周环比 +20%（且排除流量结构变化） | P3 |
| 输出长度漂移 | 平均 output tokens 周环比 +30% | P3 |

质量类统一说明：用**周滑动基线 + 相对变化率**，避免绝对阈值过期；置信样本不足（日请求 <500）时降级为周报而非告警。

### 2.4 数据与合规类

| 规则 | 条件示例 | 级别 |
|---|---|---|
| 知识库同步失败 | 19 章同步报告失败 >0 持续 2 个周期 | P2 |
| 护栏拦截激增 | 27 章拦截率突增 5 倍（可能是攻击） | P1 |
| 计费对账差异 | 21 章与账单差异 >2% | P2 |
| 密钥即将过期/泄漏扫描命中 | 05 章密钥管理事件 | P1 |

## 3. 分级与值班响应

### 3.1 级别定义与响应义务

| 级别 | 定义 | 通知方式 | 响应时限 |
|---|---|---|---|
| **P0** | 用户全面受影响 / 服务实际停摆 / 预算熔断生效 / 合规事故 | 电话 + 短信 + 群 | 立即（值班睡醒也要处理） |
| **P1** | 功能降级运行 / 单供应商失效 / 疑似攻击 | 短信 + 群 | 15 分钟内认领 |
| **P2** | 明显劣化但可用 / 质量掉分 / 同步失败 | 群通知 | 当日处理 |
| **P3** | 漂移类预警 / 预算告急 | 群通知 | 3 个工作日 |
| **P4** | 趋势观察项 | 周报汇总 | 下个迭代窗口 |

### 3.2 值班 SOP（P0/P1 通用动作）

```
1. 认领与通报（5 分钟内）：谁在处理、初步影响面
2. 止血优先于查因：
   - 可用性问题 → 11 章降级链 / 04 章切供应商
   - 成本失控 → 10 章应急开关（按优先级保护清单裁撤）
   - 质量事故疑似新发布导致 → 17 章秒级回滚
   - 护栏/合规 → 停用该功能（L4 兜底）
3. 确认止血生效（看板回归正常）
4. 查因与修复
5. 复盘（48h 内）：时间线、根因、改进项，落入 Checklist 与冒烟集
```

**AI 场景特别提醒：止血动作基本都是「配置热更」（05 章）可达的**——降级、回滚、熔断、预算收紧都不需要发版。值班手册的第一页应该是应急开关清单（10 章）。

## 4. 告警工程实现

### 4.1 从 21 章数据到告警的管道

```
计量明细/事件日志 → 规则引擎（Prometheus Alertmanager / 自研定时查询）
                  → 分级路由（P0 电话 / P1 短信 / P2-P4 群）
                  → 静默、聚合、升级机制
```

### 4.2 必备工程细节

| 机制 | 说明 |
|---|---|
| 持续时间条件 | 所有规则带 `for 5-15 分钟`，单点毛刺不告警 |
| 分组聚合 | 同一供应商/场景的 N 条相关告警合并成 1 条通知 |
| 静默窗口 | 发布窗口/演练期间主动静默（排期进告警系统） |
| 自动升级 | P1 认领超时 15 分钟 → 升级 P0 通知下一责任人 |
| 夜间抑制 | P3/P4 类不进夜间通道（狼来了主要来源） |
| 告警回顾 | 每周统计：误报率、平均认领时长、静默滥用 |

### 4.3 规则示例（Alertmanager 风格）

```yaml
- alert: ProviderErrorRateHigh
  expr: sum(rate(llm_requests_total{status="error",provider="a"}[5m]))
        / sum(rate(llm_requests_total{provider="a"}[5m])) > 0.10
  for: 10m
  labels: {severity: P1, team: ai-platform}
  annotations:
    summary: "供应商 A 错误率 >10%"
    action: "检查 04 网关健康探测与 tier 路由切换；观察 fallback 流量占比"
    runbook: "https://wiki/llmops/runbook/provider-failure"
```

每条告警的 `action` 与 `runbook` 链接是强制的——**半夜 3 点收到告警的人不该需要现场推理**。

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 质量告警用拍的绝对阈值 | 上线三个月后全部失真 | 相对基线 + 定期校准 |
| P2/P3 也打电话 | 一周两次后全员屏蔽 | 通知渠道与级别严格绑定 |
| 告警没有 action 指引 | 值班临时推理，动作变形 | 强制 annotations.action + runbook |
| 无静默机制 | 每次发布告警轰炸 | 发布排期联动静默 |
| 只告警不回顾误报 | 告警系统慢性死亡 | 每周误报率统计与规则调优 |
| 多供应商失败各自告警 | 同源问题连环轰炸 | 按根因维度分组聚合 |
| 止血动作需要发版 | MTTR 拉长数倍 | 应急动作全部配置化（05/10/17 章） |
| 复盘改进项不落地 | 同类事故反复发生 | 改进项进 Checklist / 冒烟集 / runbook |

## 6. Checklist

- [ ] 告警四要素齐全（条件/级别/动作/负责人），action 与 runbook 强制
- [ ] 系统类、AI 可用性类、质量类、数据合规类规则清单成文
- [ ] 质量告警用周滑动基线 + 相对变化率，小流量场景自动降级为周报
- [ ] P0-P4 与通知渠道、响应时限绑定，夜间通道只进 P0/P1
- [ ] P1 认领超时自动升级
- [ ] 分组聚合与静默窗口机制上线，发布排期联动
- [ ] 每周告警回顾：误报率、认领时长、规则调优
- [ ] 止血动作全部为配置热更操作，runbook 第一页 = 应急开关清单
- [ ] 每次 P0/P1 事故 48h 内复盘，改进项落回冒烟集与 Checklist
