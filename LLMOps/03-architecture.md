# 03 · 典型架构：AI 应用的标准组件

## 1. 全景架构图

```
客户端（Web/App/API）
      │
      ▼
┌──────────────────────────────┐
│ 应用服务（BFF/API）           │  鉴权、会话、业务逻辑
└──────────┬───────────────────┘
           ▼
┌──────────────────────────────┐
│ AI 编排层（Orchestrator）      │  Prompt 模板、RAG、工作流、Agent
└──┬────────┬────────┬─────────┘
   ▼        ▼        ▼
┌──────┐ ┌──────┐ ┌─────────┐
│检索服务│ │缓存层 │ │模型网关  │──── 模型 A / B / C（多供应商）
└──────┘ └──────┘ └────┬────┘
   │                    │
┌──▼───────────┐  ┌────▼──────────┐
│ 向量库 + 原文库│  │ 观测层：日志/trace/指标/eval │
└──────────────┘  └───────────────┘

旁路：异步队列（长任务）｜ 审核服务 ｜ 计量计费
```

## 2. 各组件职责

| 组件 | 职责 | 关键设计点 | 篇目 |
|---|---|---|---|
| 应用服务 | 鉴权、会话管理、业务编排 | 会话与上下文管理、用户态 | — |
| 编排层 | 组装 prompt、检索、多步流程 | 模板变量、流程可配置 | 16、19 |
| 模型网关 | 统一调用模型的唯一入口 | 路由/重试/熔断/日志/计量 | 04 |
| 检索服务 | 向量/关键词检索 | 索引更新、权限过滤 | 19 |
| 缓存层 | 相同/相似请求复用 | 缓存键设计、失效策略 | 08 |
| 观测层 | 记录每次请求全过程 | 脱敏、可检索、成本计量 | 20-22 |
| 异步队列 | 长任务异步化 | 状态机、回调、幂等 | 15 |
| 审核服务 | 内容安全过滤 | 输入输出双向 | 27 |

## 3. 最小可行架构（个人/小团队）

```
客户端 → API 服务 → SDK 直调模型（带重试）
                │
                └→ SQLite/文件 存日志
```

**判断标准**：日调用 < 1 万、单一模型、单人维护 → 先别上复杂架构。要补的三件事：

1. 重试 + 超时（12）
2. 日志落库（21）
3. 日成本告警（23）

## 4. 标准架构（中团队，日调用 1 万-100 万）

```
+ 模型网关（自建或 LiteLLM/One API）
+ Redis 精确缓存
+ 向量库（pgvector / Milvus）
+ 消息队列（异步长任务）
+ 观测平台（LangFuse / 自建）
+ 多模型路由（便宜模型处理简单请求）
```

## 5. 大规模架构（日调用 > 100 万）

```
+ 网关集群（限流、熔断、舱壁）
+ 分级路由（意图分类 → 模型选择）
+ 语义缓存（向量相似度命中）
+ 异步批处理（离线任务走批量 API）
+ 多区域多供应商容灾
+ 自动降级编排（熔断触发自动切换）
+ 全链路 trace + 成本归因（按用户/场景/模型）
```

## 6. 同步 vs 异步：按延迟需求分派

| 场景 | 模式 | 方案 |
|---|---|---|
| 聊天、补全 | 同步流式 | SSE/WebSocket，直调 |
| 文档摘要、批量处理 | 异步 | 队列 + 状态轮询/回调 |
| 批量生成、离线分析 | 批量 API | 半价，延迟换成本 |
| Agent 多步任务 | 异步任务 | 任务表 + 步骤记录 + 可中断 |

## 7. 数据流与状态设计

```
会话状态：
  session_id → 历史消息（截断/摘要策略）
  ★ 上下文窗口管理：超长时做「摘要压缩 + 保留最近 N 轮」

任务状态机（异步）：
  PENDING → RUNNING → SUCCEEDED / FAILED / CANCELLED / TIMEOUT
  每次状态变更落库 + 时间戳，便于排查

计量数据：
  每次调用记录：user_id、scene、model、prompt_version、
  input_tokens、output_tokens、cost、latency、status
```

## 8. 与 Spring/Java 栈的衔接（Java 开发者）

| 组件 | Java 生态方案 |
|---|---|
| 模型 SDK | Spring AI、LangChain4j |
| 网关 | Spring Cloud Gateway + 自定义过滤器（限流/计量/日志） |
| 重试/熔断 | Resilience4j（java777/44 篇直接复用） |
| 异步 | 消息队列（RocketMQ/Kafka，java777/35-36） |
| 向量库 | pgvector（PostgreSQL）或 Milvus Java SDK |
| 观测 | Micrometer（java777/59）+ 自定义 LLM 指标 |

> 结论：你已有的 Spring 后端能力 80% 可复用，新增的是**模型网关语义**（计量、路由、降级）。

## 9. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 架构过度设计 | 3 个用户就上 K8s+网关+队列 | 按调用量分档演进 |
| 网关缺位 | 每个服务直调模型，日志散乱、无处限流 | 统一网关入口 |
| 无计量 | 不知道钱花在谁身上 | 每次调用带 user_id/scene 落库 |
| 会话上下文无限增长 | token 爆炸、成本飙升 | 摘要压缩 + 截断策略 |
| 同步做长任务 | 网关超时、用户重复提交 | 异步化 + 状态机 |
| 检索无权限过滤 | 用户看到他人数据 | 检索必须带权限（见 27） |
| 审核放在最后 | 违规内容已展示给用户 | 输入输出双向拦截 |
