# 05 · 环境与配置：把可变的东西管起来

## 1. AI 应用比传统应用多出的「可变项」

| 类别 | 传统应用 | AI 应用新增 |
|---|---|---|
| 密钥 | 数据库密码 | **模型 API Key（多供应商、多账号）** |
| 配置 | 端口、连接串 | **路由表、prompt 版本、模型参数、成本阈值** |
| 资产 | 静态资源 | **prompt、知识库数据、evals 集** |
| 参数 | 业务开关 | **温度、max_tokens、超时、降级开关** |

原则：**一切可能要改的东西都不进代码**——prompt、路由表、模型版本、阈值全部外置。

## 2. 配置分层

```
① 环境配置：dev / staging / prod（连接串、密钥引用、域名）
② 业务配置：路由表、模型版本锁定、成本阈值、限流配额
③ Prompt 资产：模板 + 示例 + 参数（版本化管理，见 16）
④ 知识库资产：文档、切分参数、embedding 模型（见 19）
```

### 配置优先级（高 → 低）

```
命令行参数 > 环境变量 > 配置中心 > 本地配置文件 > 代码默认值
```

### 环境矩阵

| 环境 | 用途 | 模型 | 数据 |
|---|---|---|---|
| dev | 本地开发 | 便宜模型 / mock | 假数据 |
| staging | 预发验证 | 与 prod 相同 | 脱敏数据 |
| prod | 生产 | 正式模型 | 真实数据 |

> 关键：**staging 的模型与 prod 保持一致**，否则 eval 结果不可信。

## 3. 密钥管理（最容易出事故的地方）

### 铁律

```
① API Key 绝不进代码仓库（包括注释、测试代码、历史提交）
② 不硬编码在前端/客户端（前端可见 = 公开）
③ 每个环境用独立 Key（dev 泄漏不影响 prod）
④ 按用途拆分 Key（不同业务不同 Key，便于限流与封禁定位）
⑤ 可轮换：换 Key 不需要改代码
```

### 存放方案（按成熟度）

| 方案 | 做法 | 适用 |
|---|---|---|
| 本地 .env | `.env` 文件 + `.gitignore`，永不提交 | 个人开发 |
| 环境变量 | 部署平台注入（CI/CD secrets） | 小团队 |
| 密钥管理服务 | 云 KMS / Vault / 飞书密码本 | 正式生产 |

### 轮换流程

```
① 新 Key 创建 → ② 配置中心更新（灰度生效） → ③ 验证调用正常
④ 旧 Key 观察期 → ⑤ 吊销旧 Key
```

### 泄漏应急（发生后的 10 分钟）

```
① 立即在供应商控制台吊销泄漏的 Key
② 检查账单与调用日志（有无异常消耗）
③ 换新 Key 上线
④ 排查泄漏源（git 历史？日志打印？前端暴露？）
⑤ 清理：git 历史中的 Key 也算泄漏（要轮换，不能只删文件）
```

## 4. 配置的代码化与审计

```yaml
# ai-config.yaml（进 Git，变更走 Code Review）
routes:
  summary:   { tier: cheap,    model: mini-latest, timeout_ms: 10000 }
  chat:      { tier: balanced, model: mid@2026-01, timeout_ms: 30000 }
  long-form: { tier: premium,  model: flagship@2026-01, timeout_ms: 60000 }
limits:
  per_user_daily_calls: 200
  daily_budget_cny: 500
degradation:
  enable_fallback: true
  fallback_chain:
    premium: [flagship-b, mini-latest, static-template]
```

好处：

- 变更有 diff、有评审、可回滚
- 新环境一眼看清全部行为
- 审计（谁在什么时候把降级关了）

> 注意：密钥不进这个文件（用 `${ENV_VAR}` 占位符引用）。

## 5. 动态配置与热更新

| 配置项 | 更新方式 | 为什么 |
|---|---|---|
| 路由表、降级开关 | **热更新**（配置中心） | 故障时秒级切换 |
| 成本阈值、限流配额 | **热更新** | 应急需要 |
| prompt | 热更新 + 灰度（见 17） | 高频迭代 |
| 模型版本 | 走变更流程（可热更新但需审批） | 见 18 |
| 代码 | 发版 | — |

**降级开关必须做到秒级生效**——线上事故时，最快的止血手段往往就是「切模型/开兜底」。

## 6. 敏感数据处理（配置层面的延伸）

```
① 用户输入进日志前脱敏（手机号/身份证/密钥模式识别替换）
② 发送给模型 API 的内容 = 数据出境（国内场景需评估合规，见 32）
③ 不把内部系统密钥/数据库连接串放进 prompt 或上下文（会被日志与模型看到）
④ RAG 索引中的敏感文档要有权限标记（见 19）
```

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| Key 提交进 Git | 泄漏被刷爆账单 | .gitignore + 历史清理 + 轮换 |
| 前端调用模型 API | Key 暴露给全世界 | 后端代理 |
| 所有环境共用一个 Key | 出事无法定位、无法单独封禁 | 按环境/业务拆 Key |
| 降级开关要发版才能改 | 事故时止血慢 | 配置中心热更新 |
| staging 用便宜模型 | eval 结果与 prod 不符 | staging 与 prod 同模型 |
| prompt 硬编码 | 无法灰度无法回滚 | 外置 + 版本化（16） |
| 配置无审计 | 出了问题不知道谁改的 | 配置变更记录 + Review |
| 日志打印完整请求含密钥 | 日志系统泄漏 | 脱敏 + 禁止打印 Header |

## 8. Checklist

- [ ] API Key 不在任何代码仓库中（含 git 历史）
- [ ] 按环境与业务拆分 Key，可独立吊销
- [ ] 密钥通过环境变量或密钥服务注入，可轮换
- [ ] 路由表/模型版本/成本阈值/降级开关外置且可热更新
- [ ] staging 与 prod 使用相同模型
- [ ] 配置变更有评审与审计记录
- [ ] 日志输出有脱敏规则，不打印密钥
- [ ] 有 Key 泄漏应急预案（10 分钟内可吊销换新）
