# 28 - 回归测试与发布门禁

> 前四章各自解决了单点验证，本篇把它们串成一道「门禁」：
> 任何影响系统行为的变更（prompt / 模型 / 管道 / 护栏 / 应用代码）上线前必须过闸。
> 门禁的目标：**变更可预期——过了门禁的变更，效果在预测范围内；超出范围的变更，进不来。**

---

## 1. 变更类型与门禁矩阵

不同变更的风险面不同，门禁要求分级：

| 变更类型 | 必过项 | 示例 |
|---|---|---|
| 应用代码（不含 prompt/模型） | 单测 + 集成测试 + 合同测试（解析层） | 常规后端发布 |
| Prompt 变更（轻微） | 冒烟集 + 渲染 diff | 错别字修正 |
| Prompt 变更（普通/重大） | 冒烟集 + 全量 evals + 灰度 | 17 章分级 |
| 模型升级/切换 | 全量 evals（逐场景）+ 回放/影子 + 灰度 | 18 章七步法 |
| 切分/检索配置变更 | 检索评测集 + 回放 | 19 章 pipeline_version |
| 护栏规则变更 | 拦截测试集（正负样本） | 27 章 |
| 知识库大版本发布 | 标准查询集 + 抽样人工核查 | 19 章 |
| 组合变更（代码 + prompt） | 各自门禁 + 联合回归 | 最易漏，见 16 章「回滚绑定」原则 |

**没有例外通道**——「紧急修复所以跳过门禁」是事故的第二来源。紧急通道也存在，但见第 4 节的代价设计。

---

## 2. 发布门禁清单（硬条件）

一次普通 prompt 版本发布的门禁闸机：

```
Gate 1  构建/静态检查        ci/prompt-lint 全绿
Gate 2  渲染快照 diff        reviewer 确认无意外差异
Gate 3  冒烟集              通过率 ≥ 基线（无倒退）
Gate 4  全量 evals          按场景达标，总分 ≥ 基线 - ε
Gate 5  影子/回放（可选）     成本/延迟副作用在预算内
Gate 6  灰度计划已登记       分流比例、观察指标、回滚预案（17 章）
Gate 7  变更说明完整         changelog + 审计事件
```

每道闸机的结果**自动归档并关联发布单**——事后审计（32 章）与复盘的依据。门禁失败的变更不销毁，标记 `blocked` 留档，防止被原样重提。

### 2.1 门禁阈值的设定纪律

- **ε（可接受噪声带）要按指标分别设定**：解析失败率 ε≈0.1pp（严格）、judge 分 ε≈0.05（宽松）、成本 ε≈+5%。
- 阈值来自**历史分布**而非拍脑袋：取近 30 天正常发布后的分数波动 P95 作为噪声带。
- 门禁失败≠变更错误：先看失败模式是否为新问题（见 25 章「失败可行动」），有时是评估集该更新——但更新评估集**本身也走门禁**（留痕 + review），不能当后门用。

## 3. 联合回归：组合变更的防线

### 3.1 为什么单独过闸不够

```
变更 A: prompt v7 输出新增字段 tags        （单独过闸 ✅）
变更 B: 解析层升级支持 tags                 （单独过闸 ✅）
组合问题: v6 与新解析层不兼容？B 先发 A 没发 → 生产 30% 流量还是 v6
```

组合变更的门禁要点：

1. **发布顺序声明**：变更单写明依赖关系与发布顺序（先解析层兼容，再切 prompt）。
2. **兼容窗口验证**：新旧输出格式并存期间的解析兼容性必须显式测试（16 章解析层宽容原则）。
3. **联合冒烟**：组合后的完整链路跑一次冒烟集（不是各跑各的）。
4. **回滚预案绑定**：任一组件回滚时声明对同伴的影响（16 章「回滚绑定」）。

### 3.2 合同测试（解析层的专属防线）

模型输出与解析代码之间的「合同」独立成测试资产：

```
合同测试集：用 17/18 章历史版本的真实输出样本（含畸形输出）
断言：解析层对每份历史样本的处理行为（接受/宽容降级/明确报错）
触发：解析层代码变更、prompt 输出结构变更、模型升级——三者都要跑
```

它防的是「解析层悄悄拒绝了一种它本该容忍的输出」这类静默故障。

## 4. 紧急发布通道

真实事故中需要「跳过程序」，但通道本身要有约束：

| 约束 | 内容 |
|---|---|
| 只限止血类变更 | 回滚、降级开关、护栏收紧、限流调整（**这些本就该是配置热更，不走发布**） |
| 最小范围 | 只动引发事故的单一版本/配置，不捎带其他待发布内容 |
| 事后补闸 | 24 小时内补跑全量回归与复盘，缺一不可 |
| 计数公开 | 紧急通道使用次数进月报——频繁使用说明常规门禁太慢，要优化流水线而非绕过它 |

**止血动作配置化（05/10/17 章）的最大价值就在这里**：绝大多数「紧急」不需要新发布，回滚/降级/熔断都是秒级配置操作，紧急发布通道本应是低频路径。

## 5. 发布检查单（Checklist 式门禁的最后一关）

自动门禁之外，发布人手工确认（模拟 34 章 runbook 风格）：

```
[ ] 本次变更影响面清单已列出（功能/场景/下游解析）
[ ] 灰度比例与观察指标已登记，回滚命令已写在发布单上
[ ] 相关方已通知（值班、客服团队——他们可能收到用户反馈）
[ ] 发布窗口避开流量高峰与节假日
[ ] 供应商公告已检查（18 章：避开供应商变更窗口）
[ ] 观察计划：发布后 1h / 24h / 1 周各看一次什么指标
[ ] 预算影响已评估（新版本成本变化）
```

「回滚命令写在发布单上」是强制项：**发布时刻写的回滚方案远比事故时刻现场想出来的可靠。**

## 6. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 门禁只有冒烟集 | 评估覆盖不足，结构性退化漏过 | 硬条件矩阵（第 1 节）按变更类型强制 |
| 评估集当后门改 | 分数达标了、线上翻车了 | 评估集变更自身走门禁 + 留痕 |
| 组合变更各自过闸 | 发布顺序/兼容窗口出事故 | 发布顺序声明 + 联合冒烟 + 合同测试 |
| 紧急通道常态化 | 门禁形同虚设 | 紧急通道计数公开，止血配置化 |
| 发布单不写回滚方案 | 事故时现场 improvisation | 强制预写回滚命令 |
| 门禁结果不留档 | 无法审计、复盘无据 | 自动归档关联发布单 |
| 阈值拍脑袋 | 误拦正常变更或放进退化 | 阈值取历史波动 P95 |
| 灰度观察指标没定 | 灰度变成「跑两天看感觉」 | 发布单登记观察指标与通过标准 |
| 只验新版本不验回滚路径 | 回滚命令从未被验证过 | 演练环境周期性验证回滚（34 章应急演练） |

## 7. Checklist

- [ ] 变更类型 × 门禁要求矩阵成文，无例外通道
- [ ] 门禁闸机自动化（构建/冒烟/全量/灰度登记），结果归档关联发布单
- [ ] 阈值基于历史波动分布设定，分指标差异化
- [ ] 评估集变更自身走门禁留痕
- [ ] 组合变更有发布顺序声明 + 联合冒烟 + 兼容窗口验证
- [ ] 合同测试集覆盖历史版本真实输出（含畸形样本），三触发条件齐备
- [ ] 紧急通道仅限止血类、最小范围、24h 补闸、计数公开
- [ ] 止血动作配置化，紧急发布保持低频
- [ ] 发布检查单含回滚命令强制项与观察计划
- [ ] 回滚路径周期性演练验证
