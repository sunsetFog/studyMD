# 10 · 限流、配额与预算熔断：防止失控的三道闸

## 1. 为什么要三道闸

```
AI 应用的成本是「活」的：
  ① 用户的 bug 循环调用 → 一夜烧穿预算
  ② 恶意刷量（薅免费额度）→ 账单爆炸
  ③ 某个场景上线即爆量 → 供应商限流，全站不可用
  ④ 重度用户无限使用 → 亏损

三道闸（从内到外）：
  第一道：单请求限制（token/费用上限）
  第二道：用户配额（频次/日额度）
  第三道：全局预算熔断（日/月预算，超了自动降级）
```

## 2. 第一道闸：单请求限制

```
① 输入长度上限：用户输入 max_chars（如 5000 字）
② 上下文上限：拼装后的总输入 token 上限（如 32k）
③ 输出上限：max_tokens 按场景配置
④ 单次费用估算：调用前预估费用 > 阈值 → 拒绝或降级
⑤ 循环检测：同一用户短时间内完全相同的请求 → 拦截（防 bug 循环）
```

预估费用示例：

```python
def estimate_cost(messages, max_tokens, model_price):
    input_tokens = count_tokens(messages)          # 本地 tokenizer 估算
    est = input_tokens / 1e6 * model_price.input \
        + max_tokens  / 1e6 * model_price.output
    return est   # 调用前检查 est 是否超过单次费用上限
```

## 3. 第二道闸：用户配额

### 配额维度

| 维度 | 示例 | 目的 |
|---|---|---|
| 频次限流 | 10 次/分钟 | 防刷、削峰 |
| 日调用数 | 免费用户 50 次/日 | 控制单用户成本 |
| 日 token/金额 | 免费 ¥0.5/日，付费 ¥5/日 | 直接对齐成本 |
| 并发数 | 免费并发 1，付费并发 3 | 保护后端 |

### 分层配额（与商业模式对齐）

```
免费用户：日 50 次，并发 1，走便宜模型
标准付费：日 500 次，并发 3
重度付费：日 5000 次，超额部分按次计费
企业客户：单独配额池 + SLA
```

### 实现要点

```
① 限流算法：令牌桶/滑动窗口（Redis + Lua 保证分布式一致）
② 计数粒度：user_id 为主键，scene 可细分
③ 拒绝体验：清晰告知「今日额度已用完，明日恢复/升级解锁」
④ 额度预警：用到 80% 提前提示
⑤ 豁免机制：内部测试账号、VIP 白名单
```

Redis 滑动窗口示意：

```
ZADD user:{id}:{date} ts req_id          # 记录每次请求
ZREMRANGEBYSCORE user:{id}:{date} 0 ts-86400   # 清理过期
ZCARD user:{id}:{date}                   # 当前计数 → 超过配额则拒绝
```

## 4. 第三道闸：全局预算熔断

### 预算层级与动作

```
月预算 ¥30,000（示例）
  ├─ 80%：告警（值班群通知）
  ├─ 95%：非核心场景降级（旗舰→mini、关闭探索功能）
  ├─ 100%：进入「保命模式」
  │        ① 仅保留核心场景
  │        ② 全部走便宜模型 + 缓存
  │        ③ 或只读模式（禁止新调用）
  └─ 恢复：次月自动恢复 / 人工调高预算
```

### 熔断的分级设计（不要一刀切）

```
优先级保护清单（熔断时保谁）：
  P0 付费用户核心场景    → 最后才限
  P1 免费用户核心场景    → 降模型限频
  P2 免费探索功能        → 先关
  P3 内部分析/非关键任务 → 直接停
```

### 防刷（与配额配套）

```
① 注册门槛：手机号/邮箱验证，防批量注册
② 行为检测：新账号高频调用、固定 pattern → 风控拦截
③ 指纹/设备维度限流（防单人多号）
④ 免费额度按「成功产出」而非「调用次数」消耗更稳（可选）
⑤ 异常告警：单用户 1 小时消耗超历史 P99 × 10 → 自动暂停该用户
```

## 5. 应急开关清单（值班必备）

```
可热更新的开关（见 05 篇配置中心）：
① global_model_tier: premium → mini     （全局降级）
② scene_off: ["explore", "batch"]        （关闭非核心场景）
③ free_daily_quota: 50 → 20              （收紧免费额度）
④ cache_only_mode: on                    （仅缓存可答）
⑤ maintenance_mode: on                   （只读/维护页）
```

> 事故演练：定期（每月）实际演练一次「预算熔断」与「全局降级」，确保开关真的有效。

## 6. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 只限频次不限金额 | 每次都塞超长上下文照样烧钱 | token/金额维度配额 |
| 免费额度无注册门槛 | 被批量注册薅穿 | 验证 + 风控 |
| 熔断一刀切 | 全站不可用，付费用户流失 | 分级保护清单 |
| 配额计数不准 | 分布式下多实例绕过 | Redis 原子操作（Lua） |
| 拒绝体验差 | 「请求过于频繁」没有下一步 | 说明原因 + 恢复时间 + 升级路径 |
| 循环调用无检测 | 用户端 bug 一夜烧钱 | 相同请求短窗拦截 + 单用户异常告警 |
| 开关没演练过 | 事故时发现降级开关失效 | 定期演练 |
| 预算只看月 | 月内发现时已超支 | 日预算双保险 |

## 7. Checklist

- [ ] 单请求有输入/输出/费用上限与循环检测
- [ ] 用户配额按层级（免费/付费/企业）配置且分布式一致
- [ ] 额度用尽的提示有清晰文案与升级路径
- [ ] 全局预算有 80% 告警、95% 降级、100% 保命模式三级动作
- [ ] 有分级保护清单（熔断时保核心）
- [ ] 防刷机制：注册门槛 + 行为检测 + 异常自动暂停
- [ ] 应急开关全部可热更新，且演练过
- [ ] 有按用户维度的异常消耗告警
