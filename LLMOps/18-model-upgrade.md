# 18 - 模型升级：迁移、评估与兼容处理

> Prompt 版本是你能控制的，**模型版本是供应商替你控制的**——这是 AI 应用最特殊的运维风险：
> 供应商悄悄更新模型，你的系统行为就变了。本篇覆盖主动升级与被动漂移两类场景。

---

## 1. 模型变更的四种来源

| 来源 | 触发方式 | 控制权 | 风险 |
|---|---|---|---|
| 主动升级 | 你决定换新模型/新版本 | 完全可控 | 可提前评估 |
| 供应商废弃（deprecation） | 官方宣布旧模型下线日期 | 只能被迫迁移 | 有截止时间压力 |
| 供应商静默更新 | 同名模型权重更新（如 `gpt-x-2026-03` 快照变更） | 不可控 | 最危险，无预兆 |
| 定价调整 | API 价格变化 | 不可控 | 成本模型失效 |

**防御基本盘**：

1. **版本锁定**：调用时始终带完整版本参数（如 `claude-xxx-2026xxxx`、`model_version`），不要用别名端点。除非刻意吃新特性，否则锁定快照。
2. **订阅供应商公告**（changelog / 邮件 / RSS），deprecation 公告一般提前 3-6 个月。
3. 24 章漂移检测兜底：即使静默更新，质量/成本/延迟的异常也能被监控发现。

---

## 2. 主动升级的标准流程

### 2.1 七步迁移法

```
1. 盘点依赖     → 哪些场景用旧模型？各自对 prompt/参数/输出格式的依赖是什么？
2. 行为对比评估 → 新旧模型跑全量 evals，逐场景对比（不是只看总分！）
3. prompt 迁移  → 旧 prompt 在新模型上往往需要重写（见 2.3）
4. 成本延迟测算 → 新模型 token 单价 × 实测 token 用量，注意「输出变长」
5. 灰度上线     → 复用 17 章灰度框架，按用户分流对比
6. 全量切换     → 指标稳定后切换，旧模型保留为降级路径（11 章）
7. 归档结论     → 迁移报告：改动点、指标变化、踩坑记录
```

### 2.2 逐场景对比：总分掩盖一切

全量 evals 的汇总分数会掩盖结构性差异。必须**按场景/类别拆开看**：

```
场景           旧模型    新模型    差异
─────────────────────────────────────────
工单分类        96.2%     97.8%    ✅ +1.6
长文摘要        91.0%     88.5%    ⚠️ -2.5  ← 新模型倾向漏掉末尾要点
JSON 严格输出    99.1%     94.3%    ❌ -4.8  ← 新模型爱加解释性文字
拒答边界        合规       3例越界   ❌      ← 安全行为变化，必须人工核查
```

**结论示例**：分类场景可以立即升级；摘要场景需要配合 prompt 调整或暂缓；JSON 输出需要加「只输出 JSON」强化指令或改用结构化输出 API。

### 2.3 Prompt 迁移：不是换个模型名就行

不同代际模型的「性格」不同，旧 prompt 常见失效模式：

| 旧 prompt 模式 | 在新模型上的问题 | 处理 |
|---|---|---|
| 大量 fewshot 撑行为 | 新模型指令跟随更强，fewshot 冗余 → 输出变长、成本涨 | 精简到 2-3 个，改用规则描述 |
| 负向指令堆砌（「不要…不要…」） | 可能被过度执行，正常能力被抑制 | 改为正向指令（「只输出 JSON」） |
| 手工格式约定（「用---分隔」） | 新模型支持结构化输出/JSON mode | 迁移到原生结构化输出，删约定 |
| 复杂 CoT 手工步骤 | 新模型自带推理能力 | 简化或删除显式 CoT，实测对比 |
| 依赖特定模型的习惯性措辞 | 触发不预期的拒答或风格漂移 | 重写并重跑该场景 evals |

**实操建议**：迁移时以 evals 失败 case 为线索改 prompt，而不是推倒重来。旧 prompt 中「为什么这么写」的注释（16 章 changelog）此时最值钱。

### 2.4 成本测算的陷阱

新模型更便宜 ≠ 总成本下降：

```
旧模型:  $3/M in + $15/M out, 平均输出 800 tok  → 单次 $0.0132
新模型:  $1/M in + $4/M  out, 平均输出 1500 tok → 单次 $0.0078   ✅ 降 41%
但若新模型输出膨胀到 4000 tok（啰嗦）→ $0.0176  ❌ 反涨 33%
```

测算必须用**实测 token 用量**（灰度期从 trace 统计），不能拿官方示例脑补。同时检查新模型是否引入新的计费项（缓存费、推理 token 费——o 系/思维链模型输出含隐藏推理 token，可能数倍于可见输出）。

## 3. 被动漂移：静默更新怎么办

### 3.1 发现手段（详见 24 章）

| 信号 | 监控方式 |
|---|---|
| 质量缓慢下滑 | 每日金丝雀集（固定 50 条基准 case）打分，周环比 >2% 告警 |
| 输出分布变化 | 输出长度分布、拒答率、语言/格式分布的统计监控 |
| token 用量突变 | 同类请求的平均 token 周环比异常（模型变啰嗦） |
| 延迟变化 | P50/P95 趋势，模型换底层基础设施常伴随延迟变化 |

**金丝雀集是 drift 检测的核心资产**：一组固定输入 + 人工确认过的标准答案，每天定时跑，不依赖线上流量。它的分数下降 = 环境/模型变了（你的代码没变）。

### 3.2 应对决策

发现漂移后按影响分级：

| 影响程度 | 动作 |
|---|---|
| 轻微（金丝雀掉 2-5%，无用户投诉） | 记录观察，下个迭代窗口内安排 prompt 微调 |
| 中等（badcase 上升/成本涨 >10%） | 决策：锁定到更旧的快照版本（若可选）or 紧急 prompt 修正 |
| 严重（合规行为变化/功能不可用） | 切换到备用供应商（04 网关 tier 路由），事后复盘 |

## 4. 多模型并存与退役

### 4.1 让新旧模型长期共存一段时间

升级期间不要「非黑即白」：

```
tier 路由（04 章）:
  tier: flagship  → 新模型（主）
  tier: flagship-legacy → 旧模型（保留 30-90 天，作为降级路径）
```

好处：新模型出问题时秒级切回旧模型；也有真实流量的对照组用于持续对比。

### 4.2 退役清单（deprecation 响应 SOP）

供应商宣布废弃时：

- [ ] 确认最后可用日期，倒排迁移计划（一般预留 4-8 周缓冲）
- [ ] 盘点该模型的所有引用点（网关配置、代码、实验配置）
- [ ] 按 2.1 流程完成迁移评估，重点确认 deprecation 通常是「被迫提前」，评估时间只有平时一半
- [ ] 更新降级链（别让降级目标指向即将下线的模型！——经典事故）
- [ ] 下线前最后一天全量跑金丝雀集，留下基线记录
- [ ] 归档该模型的 trace/计量数据口径说明

## 5. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 使用模型别名/最新标签 | 供应商更新即行为漂移，且无法归因 | 锁定快照版本号 |
| 只看 evals 总分做升级决策 | 个别场景暴跌被平均分掩盖 | 逐场景对比 + 差异清单 |
| 沿用旧 prompt 直接切新模型 | fewshot/负向指令失效，质量下降 | 按 2.3 重构并重跑评估 |
| 成本测算用假设 token 量 | 输出膨胀导致成本反涨 | 灰度期实测统计 |
| 降级链指向待退役模型 | 主备同时失效 | 退役 SOP 中强制检查降级配置 |
| 没有金丝雀集 | 静默更新几个月后才被用户发现 | 建立每日基准测试 |
| 升级后立刻删除旧模型配置 | 无法回滚 | 旧版本保留 30-90 天 |
| 思维链模型按可见输出估成本 | 实际计费含隐藏推理 token，账单翻数倍 | 上线前用小流量实测 usage |

## 6. Checklist

- [ ] 所有模型调用锁定快照版本，不使用别名端点
- [ ] 订阅所有在用供应商的 changelog，deprecation 有跟踪表（模型/替代品/截止日期/负责人）
- [ ] 升级流程 = 七步法，逐场景对比 evals（非总分）
- [ ] prompt 迁移有专门环节，以失败 case 为线索重构
- [ ] 成本测算基于实测 token 用量，含隐藏计费项检查
- [ ] 灰度框架复用 17 章，用户维度分流对比
- [ ] 旧模型保留 30-90 天作为降级路径
- [ ] 每日金丝雀集 + 输出分布监控，周环比异常告警
- [ ] 退役 SOP：降级链检查、下线前基线归档
- [ ] 每次升级/退役产出迁移报告归档
