# 08 · 缓存策略：命中即免费

## 1. AI 应用中缓存的三层

```
① 请求结果缓存：相同/相似输入 → 直接返回缓存答案（省一次模型调用）
② 供应商侧前缀缓存：prompt 前缀重复部分，供应商打折计费
③ 基础设施缓存：embedding 结果、检索结果、会话上下文
```

本篇重点是 ①（对成本影响最大）与 ②（容易被忽略）。

## 2. 精确缓存（Exact Cache）

### 缓存键设计（核心难点）

```
键 = hash(场景 + 模型版本 + prompt版本 + 完整输入 + 关键参数)
        │      │          │           │          │
      不同场景答案不同  换模型要失效   改prompt要失效  参数影响输出
```

```python
def cache_key(scene, model, prompt_ver, messages, params):
    payload = json.dumps({
        "scene": scene,
        "model": model,
        "prompt_version": prompt_ver,
        "messages": messages,
        "params": params,
    }, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode()).hexdigest()
```

### 失效策略

| 触发条件 | 处理 |
|---|---|
| prompt 版本变更 | 按版本前缀批量失效 |
| 模型版本变更 | 同上 |
| 知识库更新 | 带知识库版本号进键，或按知识分区失效 |
| TTL 过期 | FAQ 类 24h-7d，实时类不缓存 |
| 主动清除 | 内容纠错时定向清除 |

> 关键设计：**把 prompt 版本、模型版本、知识库版本编进缓存键**，升级资产时天然失效，不会返回旧答案。

### TTL 与容量

```
TTL 选择：
  FAQ/静态知识：24h - 7d
  个性化内容：不缓存或极短
  生成类创作：不缓存（用户期望多样性）

容量：LRU 淘汰，保留高频键
```

## 3. 语义缓存（Semantic Cache）

### 原理

```
精确缓存：输入完全相同才命中 → 命中率低
语义缓存：输入向量化后相似度 > 阈值 → 视为同一问题

"怎么退货" ≈ "退货流程是什么" → 语义上应命中
```

### 实现

```
① 用户输入 → embedding
② 在向量库中检索历史问题（过滤同场景）
③ 相似度 ≥ 阈值（如 0.92）→ 返回该问题的缓存答案
④ 未命中 → 正常调用 → 结果写入语义缓存
```

### 阈值的权衡（最重要的参数）

| 阈值 | 效果 | 风险 |
|---|---|---|
| 太高（0.98） | 几乎不命中，浪费 | 无 |
| 太低（0.85） | 命中率高 | **答非所问**（「苹果手机多少钱」命中「苹果多少钱一斤」） |

```
建议：
① 起步 0.93-0.95，观察误命中样本再调
② 相似度区间 0.90-0.93 的「灰区」可以让 LLM 快速判定是否同义
③ 按场景分别设阈值（客服 FAQ 可低些，医法金要极高或不做）
④ 必须有「不命中」反馈通道：用户点「不是我想问的」→ 清除该缓存
```

### 语义缓存的风险边界

```
不适合语义缓存的场景：
① 个性化输出（含用户名/订单号的答案）
② 时间敏感（价格、库存、日程）
③ 创意生成（用户期待多样性）
④ 高风险领域（医疗/法律，措辞差异即含义差异）
```

## 4. 供应商前缀缓存（Prompt Cache）

```
原理：多家供应商对「重复的 prompt 前缀」打折计费（通常 5-9 折）

用法：
① 系统提示放最前、保持稳定（不要每次带时间戳等变化内容！）
② 知识库文档、few-shot 示例放中间稳定区
③ 用户输入放最后

反模式（破坏前缀缓存）：
  系统提示里拼接当前时间、随机数、用户ID → 前缀每次都变 → 无折扣
```

## 5. 其他基础设施缓存

| 对象 | 缓存内容 | 收益 |
|---|---|---|
| embedding | 文本 → 向量 | 重复文本不再调用 embedding API |
| 检索结果 | 查询 → top-k 分块 | 省检索延迟 |
| 分块 | 文档 → 切片结果 | 知识库处理 |
| 分类/审核 | 输入 → 判定结果 | 省小模型调用 |

## 6. 缓存的观测（必须做）

```
指标：
  命中率（精确/语义分开统计）
  节省成本 = 命中次数 × 对应模型单次成本
  误命中投诉数（语义缓存质量红线）

告警：
  命中率突然下降 → 可能是缓存键设计变更或流量变化
  误命中反馈上升 → 阈值过松，收紧
```

## 7. 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 键里漏了 prompt/模型版本 | 升级后返回旧答案 | 版本号进键 |
| 缓存个性化内容 | 用户看到别人的答案 | 个性化内容不缓存或键含 user_id |
| 系统提示带动态内容 | 前缀缓存失效 | 动态信息移到末尾 |
| 语义阈值太松 | 答非所问 | 0.93 起步 + 灰区判定 + 反馈通道 |
| 缓存无监控 | 不知道省了多少 | 命中率与节省成本进看板 |
| 创意场景也缓存 | 用户觉得「每次都一样」 | 按 scene 配置是否启用缓存 |
| 知识库更新不清缓存 | 旧知识持续返回 | 知识版本进键 |

## 8. Checklist

- [ ] 缓存键包含场景/模型/prompt/知识库版本与关键参数
- [ ] 按 scene 配置缓存开关与 TTL
- [ ] 个性化、时间敏感、创意类内容不缓存
- [ ] 语义缓存有阈值策略与「误命中」反馈清除机制
- [ ] 系统提示保持稳定（前缀缓存友好），动态内容在末尾
- [ ] embedding/检索结果有缓存
- [ ] 命中率、节省成本、误命中数进监控看板
