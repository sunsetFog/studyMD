# 19 - 知识库运维：数据管道、增量更新与重建索引

> RAG 应用中，模型只是引擎，**知识库的质量决定答案的上限**。
> 知识库不是「建完就完」的一次性工程，它是一套持续运转的数据管道，本篇讲它的日常运维。

---

## 1. 知识库生命周期总览

```
数据源 ──> 抽取/清洗 ──> 切分 ──> 向量化 ──> 入库 ──> 检索质量验证 ──> 上线
   ▲                                                            │
   └────────── 源数据变更 → 增量更新 / 全量重建 <────────────────┘
                    （版本发布、元数据管理贯穿全程）
```

知识库运维的四个日常问题：

1. 源数据变了，索引怎么跟着变？
2. 答案引用了过期内容，怎么发现和修复？
3. 换 embedding 模型 / 切分策略，怎么安全重建？
4. 知识库本身的质量，怎么持续监控？

---

## 2. 数据管道设计

### 2.1 分层管道

| 阶段 | 内容 | 关键产出 |
|---|---|---|
| 抽取 | 从 Markdown/PDF/Confluence/DB 拉取原始内容 | 原始文档（附来源 URL、版本、抓取时间） |
| 清洗 | 去页眉页脚、去导航噪音、规范格式、去重 | 清洗后文档 + 清洗报告（删了什么） |
| 切分 | 按语义结构切 chunk（标题/段落优先，再按 token 上限） | chunk + 元数据 |
| 富化 | 附加元数据：所属产品/章节路径/生效日期/权限标签 | 带元数据的 chunk |
| 向量化 | embedding 模型批量生成向量 | 向量 + 模型版本标记 |
| 入库 | 写入向量库（原子替换，见 2.3） | 可检索索引 |

### 2.2 元数据是检索质量的一半

每个 chunk 必须携带：

```json
{
  "chunk_id": "kb-prod-manual#refund#p12#c3",
  "source_url": "https://wiki.example.com/manual/refund",
  "source_version": "2026-10-28T09:00:00Z",   // 源文档最后修改时间
  "ingested_at": "2026-11-01T03:00:00Z",       // 本次入库时间
  "pipeline_version": "v4",                    // 管道策略版本（切分/清洗规则）
  "embedding_model": "bge-m3-v1.5",            // 向量模型版本
  "namespace": "product-manual",               // 业务域
  "acl_tags": ["public"],                      // 权限标签（配合检索过滤）
  "effective_from": "2026-10-01",              // 内容生效期（政策类文档关键！）
  "effective_to": null,
  "token_count": 412
}
```

为什么重要：

- **答案过期排查**：出问题时能定位「这条内容来自哪份文档的哪个版本」。
- **混合重建**：能精确筛出「哪些 chunk 需要重新处理」（见 4.2）。
- **权限过滤**：检索时按用户权限过滤 namespace/acl，防止越权内容被引用。

### 2.3 增量更新：内容寻址

不要每次全量重算。以**源文档内容哈希**为变更依据：

```python
def sync_source(doc):
    new_hash = sha256(doc.cleaned_content)
    existing = kb.get_by_source(doc.source_url)
    if existing and existing.content_hash == new_hash:
        return "unchanged"          # 跳过，省下全部下游成本
    delete_chunks_of(doc.source_url)   # 先删旧 chunk（按 source_url 索引）
    chunks = chunk(doc.cleaned_content, strategy=PIPELINE.current)
    kb.insert_batch(chunks, metadata=...)  # 原子批量写入
    return "updated"
```

要点：

- **按 source_url 整体替换**，不要试图做「chunk 级 diff 合并」——局部更新极易留下孤儿 chunk 和编号错乱。
- 先删后写要保证原子性（事务或带 staging 标记再切换），否则删除成功、写入失败会造成知识缺口。
- **删除源文档时也要删除其全部 chunk**——「源没了索引还在」是 RAG 幻觉的经典来源（模型引用一篇已删除的文章）。

### 2.4 同步频率与触发方式

| 源类型 | 触发 | 频率 |
|---|---|---|
| Wiki / 产品文档 | Webhook 或定时 diff | 每小时~每日 |
| 数据库类知识（价格、库存口径） | 变更事件驱动 | 准实时 |
| PDF / 外部资料 | 人工上传触发 | 按需 |
| 政策/合同类 | 人工触发 + 双人确认 | 随业务变更 |

定时同步任务要有**同步报告**：本次扫描 N 篇，新增 x、更新 y、删除 z、失败 w。失败项进入重试队列并告警，静默失败 = 知识悄悄过期。

## 3. 切分与向量化策略的运维视角

### 3.1 切分策略是版本化的资产

切分规则（chunk 大小、重叠、标题感知、表格处理）和 prompt 一样要**版本化**（存为 `pipeline_version`）：

| 版本要素 | 记录内容 |
|---|---|
| chunk 大小 / overlap | 如 512 tok / 64 tok |
| 结构感知规则 | 按标题层级切？表格不切断？代码块整体保留？ |
| 清洗规则 | 去除了哪些 pattern |

调整切分策略必然要求**重建受影响索引**（新旧 chunk 无法混用对比），走第 4 节的重建流程。

### 3.2 Embedding 模型变更 = 必须全量重建

**不同 embedding 模型的向量空间不兼容，绝不允许混存。** 换模型时：

```
1. 新模型在抽样集上对比检索质量（召回率/MRR，见 25 章 RAG evals）
2. 双写过渡：新字段/新 collection 用新模型写入，检索仍走旧
3. 新 collection 全量完成后，金丝雀验证 → 切换检索目标
4. 保留旧 collection 7-30 天，确认无回滚需求后删除
```

注意 embedding 成本：全量重建 = 全量重新计费，提前用文档总量 × 单价估算，量大时选批量 API。

### 3.3 检索配置也是运维对象

| 配置 | 常见事故 | 运维手段 |
|---|---|---|
| top_k | 调大到 20 无人察觉，上下文爆炸、成本涨 | 配置热更 + token 预算校验 |
| 相似度阈值 | 阈值过低拉进无关内容 → 幻觉 | 与 RAG evals 联动调参 |
| rerank 开关 | 关闭 rerank 后精度下降无感知 | 作为 pipeline_version 的一部分 |
| 混合检索权重 | 关键词权重调飞，专名类查询失效 | 变更走 evals 验证 |

## 4. 索引重建流程

### 4.1 何时需要重建

| 触发 | 范围 |
|---|---|
| 换 embedding 模型 | 全量 |
| 换切分/清洗策略（pipeline_version 升级） | 全量 |
| 源文档批量变更（大版本发布） | 受影响文档 |
| 索引损坏 / 检索质量异常且无法定位 | 全量（最后手段） |

### 4.2 安全重建五步法

```
1. 快照统计：当前文档数/chunk 数/存储用量留档（重建后必须能对账）
2. 构建新 collection（或新 version 字段），不影响线上检索
3. 批量处理：分批抽取→切分→向量化→写入，限速执行，失败可断点续跑
4. 对账 + 质量验证：
   - 对账：chunk 总数 ≈ 预期（文档数 × 平均 chunk 数，偏差需解释）
   - 抽样人工核查：随机 50 个 chunk 检查切分边界、元数据完整
   - 跑 RAG 检索评测集：召回率/MRR/引用正确性达标
5. 切换与保留：原子切换检索目标 → 旧索引保留 7-30 天 → 清理
```

**对账清单**（重建最容易翻车的环节）：

- 文档数：源 N 篇 → 入库 N 篇（失败的逐条列出原因）
- chunk 数：每篇文档 chunk 数合理（空文档/超长文档单独列出）
- 元数据完整率：source_version / pipeline_version 覆盖率 100%
- 向量维度与模型一致性检查

### 4.3 检索质量验证集（知识库的「冒烟集」）

与 17 章 prompt 冒烟集同理，建立 **20-100 条标准查询**：

```
query: "退款到账需要多久"
expect:
  must_cite: ["kb-prod-manual#refund"]       # 必须命中该来源
  answer_should_say: "3-5 个工作日"           # 期望要点
forbidden:
  - "kb-prod-manual#promotion"               # 不应引用促销文案回答政策问题
```

每次数据同步、配置变更、重建后自动跑一遍。这是知识库质量持续可见的唯一手段。

## 5. 日常监控

| 监控项 | 指标 | 告警条件示例 |
|---|---|---|
| 同步健康 | 每次同步的成功/失败数 | 失败 >0 即告警 |
| 新鲜度 | 最老未同步源的滞留时长 | > SLA（如 24h）告警 |
| 索引规模 | chunk 总数趋势 | 突然暴跌（删库/管道 bug）或暴涨 |
| 检索空结果率 | 检索返回 0 条的比例 | >5% 告警（可能索引损坏/过滤条件错误） |
| 引用过期率 | 答案引用的 source_version 与最新版差距 | 抽样监控 + 用户「内容过期」反馈入口 |
| 向量化成本 | 批量 embedding 花费 | 超月预算 80% 告警（衔接 06 章） |

**给用户一个「这条答案过期了」的反馈按钮**：它是发现知识过期最便宜的渠道，反馈直接生成同步任务工单。

## 6. 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 删除源文档不删 chunk | 模型引用已删除内容，幻觉式回答 | 删除联动清理 + 定期对账 |
| 换 embedding 模型只增量处理 | 新旧向量混存，检索质量莫名下降 | 强制全量重建 + collection 隔离 |
| chunk 级 diff 局部更新 | 孤儿 chunk、顺序错乱 | 按 source_url 整体替换 |
| 无 pipeline_version 标记 | 策略变更后无法区分新旧 chunk，无法定向重建 | 元数据强制携带 |
| 同步任务静默失败 | 知识悄悄过期数周 | 失败重试 + 同步报告 + 告警 |
| top_k/阈值随手调 | 上下文爆炸成本涨、无关内容引入幻觉 | 配置版本化 + evals 验证 |
| 重建不跑检索评测集 | 新索引质量不如旧的无从发现 | 标准查询集自动验证后才切换 |
| 政策类文档无生效期元数据 | 回答已废止政策 | effective_from/to 字段 + 检索时过滤 |
| 旧索引立即删除 | 出问题无法回滚 | 保留 7-30 天 |

## 7. Checklist

- [ ] 数据管道分层（抽取/清洗/切分/富化/向量化/入库），各阶段有报告
- [ ] chunk 元数据完整：source_url/version/ingested_at/pipeline_version/embedding_model/acl/effective 期
- [ ] 增量同步基于内容哈希，按源文档整体替换，删除联动
- [ ] 同步失败重试 + 告警，新鲜度有 SLA 监控
- [ ] 切分策略与检索配置版本化，变更走 evals
- [ ] embedding 模型变更走双写→验证→切换流程，绝不混存
- [ ] 重建五步法：快照→新库→分批→对账+评测→切换保留
- [ ] 维护 20-100 条标准查询验证集，每次变更后自动执行
- [ ] 监控：空结果率、chunk 规模趋势、引用过期率、embedding 成本
- [ ] 提供用户端「答案过期」反馈通道并接入工单
