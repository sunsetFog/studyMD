# 15 - 支付

## 1. 需求背景与目标

- **背景**：支付是资金入口，正确性 > 体验；需对接多支付渠道并处理超时、重复、对账。
- **目标**：支付成功率 ≥99.3%（渠道侧故障除外）；对账差错 T+1 清零。
- **非目标**：不做分期/信用支付（P2）；不做国际卡（P2）。

## 2. 用户故事

- 作为买家，我想要用熟悉的支付方式付款（余额/第三方支付），以便顺畅完成交易。
- 作为买家，我想要支付超时自动关单，以便资金不被长期占用。
- 作为财务，我想要每日自动对账，以便资金差错即时暴露。

## 3. 功能需求

### 3.1 支付方式（P0）

| 渠道 | 说明 |
|---|---|
| 平台余额 | 07 钱包；大额需实名 |
| 第三方支付 A/B/C | 聚合对接（支付网关抽象多渠道，可路由降级） |
| 银行卡快捷支付 | P1，四要素签约 |

### 3.2 核心规则

| 条目 | 规则 | 优先级 |
|---|---|---|
| 15-3-1 | 支付超时关单：CREATED 订单 15 分钟未支付自动关闭（秒杀订单 5 分钟，26），释放预占库存（18），通知用户（40） | P0 |
| 15-3-2 | 幂等支付：同一订单重复支付请求 → 返回进行中/已支付态，不重复扣款；渠道回调幂等（49） | P0 |
| 15-3-3 | 渠道降级：主渠道失败率 >10%（5 分钟窗）自动切换备用渠道（46 熔断） | P1 |
| 15-3-4 | 支付限额：单笔/单日限额按渠道配置；触发 41 风控的支付需二次验证 | P0 |
| 15-3-5 | 支付结果异步通知：回调 + 主动查询兜底（每 30s 查一次，共 10 次） | P0 |
| 15-3-6 | 支付成功页：展示订单摘要 + 「查看订单」；失败页给出原因与重试 | P0 |

## 4. 流程与状态

```
收银台 → 用户选渠道 → 发起支付（幂等键=订单号+渠道）
 → 渠道处理 → 回调/查询确认 → 更新订单 PAID（16）
 → 若渠道回调成功但订单关单已执行（并发）→ 自动退款路径：
   渠道扣款成功 + 订单已关 → 创建系统退款单 → 原路退回 → 通知
```

**关单与支付的竞态处理**是本篇最重要规则：一切以「渠道最终态 + 订单状态机 + 幂等」为准，宁可多退款不可多扣款。

## 5. 对账（P0）

| 任务 | 频率 | 差错处理 |
|---|---|---|
| 渠道流水 vs 平台支付单 | T+1 | 差异生成差错工单：长款（渠道有平台无）→ 挂账核查；短款 → 补单 |
| 退款流水对账 | T+1 | 同上，退款失败自动重试 3 次 → 人工 |
| 结算资金对账 | T+1（35） | — |

## 6. 异常与边界

| 场景 | 处理 |
|---|---|
| 用户重复点击支付 | 幂等，展示「支付处理中」 |
| 回调丢失 | 主动查询兜底（15-3-5）；30 分钟仍未确认 → 差错工单 |
| 渠道故障 | 降级切渠道（15-3-3）；全渠道故障 → 收银台置维护态（46） |
| 支付中订单改价/优惠过期 | 价格快照已锁（14），不受影响 |
| 部分支付成功幻觉（渠道超时未回） | 状态「处理中」，禁止重复发起；查询确认后终态化 |

## 7. 数据与埋点

- 事件：`checkout_view(order_no)` / `pay_attempt(channel)` / `pay_success(channel, duration)` / `pay_fail(reason)`
- 指标：支付成功率（按渠道）、平均支付时长、超时关单率、渠道降级次数、对账差错数。

## 8. 依赖与接口

- 依赖：订单（16 状态机）、钱包（07 余额）、风控（41）、渠道侧。
- 提供：`发起支付`、`支付状态查询`、`退款发起`（20/21/22 调用）。
