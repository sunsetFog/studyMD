# 17 - 订单取消与修改

## 1. 需求背景与目标

- **背景**：取消/修改地址是高频操作，难点在于与商家发货的竞态（拦不拦得住）。
- **目标**：取消响应 ≤1s；发货拦截成功率 ≥95%（未出仓前）。
- **非目标**：不做改 SKU/改数量（P2，通过取消重下实现）；不做改价。

## 2. 用户故事

- 作为买家，我想要在商家发货前取消订单，以便买错了及时止损。
- 作为买家，我想要在发货前修改收货地址，以便换地址收货。
- 作为商家，我想要在打包完成前得知买家取消，以便拦截拣货。

## 3. 功能需求

### 3.1 取消订单（P0）

| 条目 | 规则 |
|---|---|
| 17-3-1 | 可取消窗口：CREATED（免费取消）；PAID 且商家未发货（买家原因取消，若商家已开始拣货可拒）；SHIPPED 后不可取消（走退货退款 21） |
| 17-3-2 | 取消原因必选（不想要了/拍错了/价格原因/其他+描述），用于 45 分析 |
| 17-3-3 | 已支付订单取消：全额原路退款（15），优惠券返还（25 有效期内）、积分扣回（06） |
| 17-3-4 | 商家拒取消（已打包）：订单继续，买家可走 20 仅退款；或等待收货后退货 |
| 17-3-5 | 取消幂等：重复取消返回已取消态（49） |
| 17-3-6 | 取消后商品在「已关闭」列表保留 6 个月可查 |

### 3.2 修改地址（P0）

| 条目 | 规则 |
|---|---|
| 17-3-7 | 可改窗口：PAID 且未发货；SHIPPED 后不可改（联系物流或拒收） |
| 17-3-8 | 修改校验：新地址服务可用性（38 配送范围）、运费重算（37 模板）——运费变化需用户确认差额 |
| 17-3-9 | 修改通知：同步商家（34 端）与物流（37） |
| 17-3-10 | 修改次数限制：每订单 ≤3 次（防风控滥用） |

### 3.3 发货拦截（P0，与 34 联动）

```
买家取消/改址请求 → 状态机校验 → 向商家侧推送拦截指令（34 打单系统）
 → 商家 WMS 回执：拦截成功（未出库）→ 允许操作
                              → 拦截失败（已出库/已揽收）→ 阻断买家操作，提示联系商家
 → 兜底：商家 30 分钟未回执 → 视为可拦截（业务权衡，避免用户无限等待）
```

## 4. 流程：已支付取消

```
买家发起 → 拦截校验（3.3）→ 商家确认/超时视同同意 → 订单 CLOSED
 → 触发退款单（15 原路退）→ 优惠券返还 + 积分扣回（06）→ 全程通知（40）
 → 取消数据入 45 报表（按原因/时段分析）
```

## 5. 异常与边界

| 场景 | 处理 |
|---|---|
| 取消与发货同时发生 | 以拦截回执为准：回执成功→取消成功；失败→订单继续，提示用户 |
| 退款中买家再次操作 | 退款处理中锁定订单操作（49 串行化） |
| 修改地址与发货竞态 | 同拦截机制；改址成功后发货单自动更新（34） |
| 取消超时（系统故障） | 兜底任务每 5 分钟扫描「取消申请中超 1h」订单，强制终态并退款 |
| 优惠券已过期返还 | 过期券返还后仍过期（不可再使用，25 规则，需在取消文案中提示） |

## 6. 数据与埋点

- 事件：`cancel_apply(reason)` / `cancel_success|rejected` / `address_modify` / `intercept_result`
- 指标：取消率（按状态/原因）、拦截成功率、改址次数分布、取消→重购转化（45 。

## 7. 依赖与接口

- 依赖：15（退款）、18（回补）、25（券返还）、34（拦截回执）、37（运费重算/物流）、40（通知）。
- 提供：`取消订单`、`修改地址`、`拦截指令下发`。
