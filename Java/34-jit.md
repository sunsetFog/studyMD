# 34 · JIT 即时编译与运行时优化

## 一、解释执行与即时编译

```
字节码 → 解释器逐条执行（启动快，慢）
       → 热点代码被 JIT 编译为本地机器码（缓存起来，快）

热点探测：
- 方法调用计数器（调用次数超阈值）
- 回边计数器（循环次数）→ OSR 栈上替换（循环热身中途换编译版）
```

## 二、分层编译（Tiered Compilation）

```
Tier 0  解释执行
Tier 1-3  C1 客户端编译（快编译，轻优化）
Tier 4  C2 服务端编译（慢编译，深度优化）—— 稳态性能主力
```

```bash
-XX:TieredStopAtLevel=1    # 只用 C1：启动快，适合 Serverless/CLI
-XX:+NeverActAsServerClassMachine
```

## 三、JIT 深度优化手段（面试原理级）

### 1. 方法内联（最重要）

```java
int add(int a, int b) { return a + b; }
// 调用 add(1,2) 被编译器直接替换为 3 的计算 —— 消除调用开销
// 小方法（<35 字节码默认）内联价值最大
// → 这就是「小方法更有利性能」的底层原因
```

### 2. 逃逸分析 + 栈上分配/标量替换/锁消除

```java
public int sum() {
    Point p = new Point(1, 2);      // p 未逃逸出方法
    return p.x + p.y;
}
// 逃逸分析判定 p 不逃逸 →
//   标量替换：p 拆成两个局部变量，对象根本不创建（省 GC）
//   栈上分配（理论）/同步省略：
synchronized (new Object()) { }     // 锁对象不逃逸 → 锁消除
```

**验证**：`-XX:+DoEscapeAnalysis`（默认开）关闭后对比 GC 次数差异。

### 3. 循环优化

```
- 循环展开/合并
- 循环不变量外提
- 数组边界检查消除（如明确循环范围安全）
```

### 4. 其他

```
- 去虚拟化：类型分析 → 单实现接口调用去虚化 + 内联
- 常量折叠、空检查消除
- SIMD 自动向量化（Vector API 的动机）
```

## 四、编译阈值与预热

```bash
-XX:CompileThreshold=10000      # 解释调用次数阈值（C2，分层下由自适应控制）
```

**预热问题**：服务重启后前几分钟 JIT 未完成 → 性能低于稳态。手段：
```
- 流量预热（网关权重渐增）
- 压测热身脚本
- AOT（JDK Native Image / CRAF）与 GraalVM（衔接 SpringBoot 34 篇）
```

## 五、JIT 与反优化（deoptimization）

```
乐观假设失效 → 回退解释执行：
- 分支预测路径变更（if 走了罕见分支）
- 类型图谱变化（新实现加入破坏单态假设）
- 常见现象：压测稳态后 P99 偶发抖动
```

## 六、代码如何配合 JIT（微优化素养）

| 写法 | 原因 |
|---|---|
| 方法保持小而单一 | 内联友好 |
| 热路径避免多态分支狂切换 | 利于去虚化 |
| 避免在热循环中 new 大量短命对象 | 逃逸分析有时救不了，直接省 GC |
| final/不变字段 | 优化器敢于假设 |
| 别手写「聪明的」位运算替代可读逻辑 | JIT 比你强，可读性优先 |

**微基准测试**：手写 while 循环计时必然被 JIT 优化骗 → 用 JMH（38 篇）。

## 七、观测 JIT

```bash
-XX:+PrintCompilation                 # 编译事件流
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining   # 内联详情
-XX:+LogCompilation                   # XML 日志（JITWatch 分析）
perf / async-profiler --jit           # 火焰图区分 JIT 编译线程
```

## 常见坑

- **坑 1**：手写微基准得出「A 比 B 快」→ 无 JMH 必错
- **坑 2**：把逃逸分析当万能 → 只对不逃逸对象生效
- **坑 3**：过度微优化牺牲可读性 → JIT 时代热路径优化交给编译器
- **坑 4**：忽略预热期性能 → 上线即高峰流量打爆
- **坑 5**：盲信 volatile/synchronized 全零成本 → 各有内存屏障成本，但 JIT 会消除冗余
