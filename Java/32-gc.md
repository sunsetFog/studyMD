# 32 · 垃圾回收

## 一、GC 判定：对象死了吗

```
引用计数法：循环引用失效 → JVM 不采用
可达性分析（JVM 采用）：从 GC Roots 出发，不可达 = 可回收

GC Roots：
- 虚拟机栈中引用的对象（局部变量）
- 静态变量引用、常量引用
- JNI 引用、活跃线程、同步锁持有的对象
```

**引用强度**：强引用（永不回收）> 软引用（内存不足才回收，缓存）> 弱引用（下次 GC 回收，WeakHashMap）> 虚引用（回收通知，堆外内存管理）。

## 二、回收算法

| 算法 | 思路 | 用在哪 |
|---|---|---|
| 标记-清除 | 标记可达，清除其余 | CMS 老年代；碎片问题 |
| **标记-复制** | 存活对象复制到另一半 | 新生代（Eden+S 区） |
| 标记-整理 | 存活对象向一端移动 | 老年代；无碎片 |

## 三、分代收集与 GC 类型

```
新生代：Eden(8) + Survivor×2(1+1)
- 新对象进 Eden → Minor GC 存活者复制到 S 区 → 年龄达标晋升老年代
Minor GC：只回收新生代，STW 短（毫秒级），频繁

老年代：长期存活对象
Major/Full GC：STW 长（百 ms-秒级），触发原因：老年代满/空间担保失败/System.gc()
```

**晋升要懂**：大对象直接老年代、动态年龄判定（S 区同龄对象 > 一半空间则晋升）、空间担保（老年代可容纳新生代全部对象才敢 Minor GC）。

## 四、垃圾收集器演进

| 收集器 | 特点 | 现状 |
|---|---|---|
| Serial | 单线程 STW | 客户端小内存 |
| Parallel | 吞吐优先（JDK8 默认） | 批处理 |
| CMS | 低停顿并发 | Java 9 弃用 |
| **G1** | Region 化、可预测停顿 | **JDK 9+ 默认，主流** |
| **ZGC** | 停顿 <1ms，TB 级堆 | JDK 15+ 生产，大内存低延迟 |
| Shenandoah | 类似 ZGC | RedHat 系 |

### G1 核心机制

```
堆划分为 ~2048 个等大 Region（1-32MB），每个动态标记 E/O/H
- 可预测停顿：-XX:MaxGCPauseMillis=200 → 优先回收垃圾最多 Region（Garbage First 之名）
- 回收步骤：初始标记(STW) → 并发标记 → 最终标记(STW) → 筛选回收(STW 复制)
- Humongous 对象：> Region 一半，直接连续分配
```

### ZGC

```
染色指针 + 读屏障 → 并发整理
停顿亚毫秒级且与堆大小无关 → 服务延迟敏感/大堆场景
```

## 五、GC 日志解读

```bash
-XX:+PrintGCDetails -Xlog:gc*        # 统一日志（9+）
```

```
[gc] GC(12) Pause Young (Normal) (G1 Evacuation Pause) 1024M->256M(2048M) 25.123ms
     ↑次数        新生代回收           原因              回收前后堆占用    停顿时长
[gc] GC(15) Pause Full (G1 Compaction Pause) 1800M->900M(2048M) 890ms
     ↑ Full GC 出现 = 重点排查（通常意味着晋升压力/泄漏）
```

**关键健康指标**：Minor GC 频率与时长、老年代增长斜率（平稳=健康；锯齿持续上移=泄漏）、Full GC 频率（应为 0 或极低）。

## 六、常用 GC 参数

```bash
-XX:+UseG1GC                         # 选收集器
-XX:MaxGCPauseMillis=200             # G1 停顿目标
-Xms4g -Xmx4g                        # 堆固定
-XX:InitiatingHeapOccupancyPercent=45   # G1 并发标记启动阈值
-XX:+UseZGC -XX:+ZGenerational       # ZGC（17+/21 分代）
```

## 七、GC 调优思路（衔接 33 篇）

```
1. 先测后调：GC 日志 + 监控基线
2. 目标分解：吞吐优先（Parallel）vs 延迟优先（G1/ZGC）
3. 常见手段：
   - 停顿过长 → 收集器升级（CMS→G1→ZGC）
   - Minor GC 频繁 → 增大新生代
   - 晋升过快/大对象多 → 排查缓存设计/批量对象
   - Full GC → 优先查泄漏（35 篇），其次调老年代
4. 别调出玄学：参数越少越好，JVM 自适应已经很强
```

## 常见坑

- **坑 1**：以为 GC 完全自动无需理解 → Full GC 洪峰线上事故无从下手
- **坑 2**：System.gc() 散落代码 → 强制 Full GC
- **坑 3**：finalize 想清理资源 → 已废弃；用 try-with-resources/Cleaner
- **坑 4**：缓存用强引用 → 泄漏；用 Caffeine（容量+过期）或 WeakHashMap
- **坑 5**：JDK8 默认 Parallel 却期待低延迟 → 换 G1/ZGC
