# 17 - 消息队列考点

## 1. MQ 三问（为什么用/损失了什么）

| 收益 | 代价 |
|---|---|
| 异步（响应时间↓） | 系统复杂度↑ |
| 解耦（生产者不知道消费者） | 一致性问题（最终一致） |
| 削峰（流量缓冲） | 可用性依赖 MQ、可能重复消息 |

## 2. Kafka vs RabbitMQ vs RocketMQ（选型题）

| 维度 | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|
| 吞吐 | 极高（百万/s） | 万级 | 十万级 |
| 延迟 | ms 级 | μs~ms 级 | ms 级 |
| 模型 | 分区+消费组、pull | exchange 路由、push | topic+queue |
| 事务消息 | 无原生 | 无 | **有** |
| 延迟消息 | 无原生 | 插件 | 支持 |
| 场景 | 日志/大数据流 | 中小业务、复杂路由 | 电商交易 |

## 3. 消息可靠性三环节（必考⭐⭐）

```
生产端不丢：发送确认（publisher confirm/acks=all）+ 重试 + 本地消息表兜底
存储不丢：刷盘策略 / 副本（min.insync.replicas ≥ 2）
消费端不丢：关闭自动 ack，业务完成再 ACK；失败重试 + 死信队列
```

- 死信队列 DLQ：重试 N 次失败的落死信 → 人工/定时处理
- RabbitMQ：confirm + mandatory + 持久化（exchange/queue/message 三者都要）

## 4. 重复消费与幂等（必考⭐）

> MQ 保证"至少一次"，幂等由业务保证。

| 方案 | 实现 |
|---|---|
| 唯一约束 | 消费落库走唯一索引，冲突忽略 |
| 去重表 | msgId 做主键，insert 成功才处理 |
| 状态机 | 只允许合法状态迁移（已支付→已发货） |
| 版本号 | 乐观锁条件更新 |

## 5. 顺序消息（高频）

- 分区保序：同一业务键（orderId）路由到同一分区/队列，单线程消费
- Kafka：key 相同进同 partition；RocketMQ：MessageQueueSelector
- 全局顺序代价极高（单分区单线程），通常业务上只需要**局部顺序**

## 6. 消息积压处理（实战题）

1. 排查：消费速度 vs 生产速度，消费者线程/实例数
2. 扩容消费者（≤分区数；不够则临时加分区或"跳板"topic）
3. 降级：批量消费、跳过非关键消息（带 offset 记录）
4. 长期：消费逻辑异步化、分片并行、预估容量

## 7. 事务消息（RocketMQ 模型）

```
1. 发送半消息（对消费者不可见）
2. 执行本地事务
3. 提交/回滚半消息
4. Broker 定时回查本地事务状态（反查接口）
```

对比本地消息表：事务消息省去本地表，但要求 MQ 支持；本地消息表更通用可靠。

## 8. Spring 集成要点

```java
// Kafka
@KafkaListener(topics = "order", groupId = "g1")
public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
    handle(record.value());
    ack.acknowledge();                     // 手动提交 offset
}
// 配置：enable.auto.commit=false, max.poll.records, 重试模板
```

## 常见追问

1. 消息丢失全景图：生产确认→刷盘/副本→手动 ACK，三段各给手段
2. offset 提交时机与重复消费的 trade-off：先处理后提交（可能重复，幂等兜底）vs 先提交（可能丢失）
3. 延迟队列实现：RocketMQ 延迟等级/RabbitMQ 插件+死信/ZSet 轮询
