# 18 - 分布式核心考点

## 1. CAP 与 BASE（开场必考）

- CAP：一致性/可用性/分区容错——网络分区必然存在，只能 CP 或 AP 二选一
  - CP：ZooKeeper/etcd（分区时拒绝服务保一致）
  - AP：Eureka/Redis 主从（可用优先，数据短暂不一致）
- BASE：基本可用 + 软状态 + 最终一致——互联网架构默认哲学

## 2. 分布式锁（对比题⭐⭐）

| 实现 | 原理 | 优缺点 |
|---|---|---|
| Redis（Redisson） | SET NX PX + Lua + 看门狗续期 | 高性能；AP，极端下锁丢失 |
| ZooKeeper | 临时顺序节点 + watch 前驱 | CP 可靠；性能低、运维重 |
| 数据库 | 唯一约束/for update | 简单；性能差，仅低并发 |

细节追问：锁的可重入（hash 结构记持有者+计数）、续期看门狗、误删他人锁（value 校验）、Redis 主从切换锁丢失的应对（业务幂等兜底）。

## 3. 分布式 ID（必考⭐）

| 方案 | 特点 |
|---|---|
| UUID | 无序，做主键页分裂，弃用 |
| 雪花 Snowflake | 64bit：时间戳+机器位+序列；趋势递增；**时钟回拨**要处理 |
| 号段模式 | DB 批量取段（Leaf），DB 依赖但简单 |
| Redis INCR | 性能好，持久化依赖 |

## 4. 分布式事务（必考⭐⭐）

| 方案 | 一致性 | 复杂度 | 场景 |
|---|---|---|---|
| 2PC/XA | 强 | 低（中间件） | 传统数据库跨库 |
| TCC | 强（业务级） | 高（Try/Confirm/Cancel 三接口） | 资金类 |
| SAGA | 最终 | 中（状态机+补偿） | 长流程 |
| **本地消息表/事务消息** | 最终 | 低 | 互联网主流 |

答题重点：互联网大多数场景**避免强一致**——用本地消息表 + MQ + 幂等消费 + 对账修复，最终一致。

## 5. 限流（必考⭐）

| 算法 | 特点 |
|---|---|
| 计数器固定窗口 | 简单，窗口边界突刺 |
| 滑动窗口 | 平滑 |
| 漏桶 | 恒定速率流出 |
| **令牌桶** | 允许突发，主流（Guava RateLimiter） |

- 单机 vs 分布式：Redis+Lua 滑动窗口；网关层限流（Nginx limit_req / Sentinel）
- 层级：接入层（Nginx/网关）→ 应用层（Sentinel 注解）→ 依赖层（连接池上限）

## 6. 熔断降级（必考⭐）

- **雪崩链路**：下游慢 → 线程池/连接占满 → 上游拖垮 → 全局雪崩
- 熔断三态：Closed →（错误率/慢调用超阈值）→ Open（快速失败）→ Half-Open（试探恢复）
- 降级预案：返回默认值/缓存旧值/简化逻辑/排队
- Sentinel：QPS/线程数流控、熔断规则、热点参数限流；对比 Hystrix（线程池隔离，已停更）
- 超时设置原则：全链路预算（前端超时 > 网关 > 服务 > DB），超时必须配

## 7. 服务注册与发现

- 注册中心模式：服务上线注册 + 心跳续约 + 客户端拉取缓存
- Nacos（AP/CP 可切换，配置中心一体）vs Eureka（AP，已停维护）vs Consul/etcd（CP）
- 配置中心：动态刷新（长轮询）、灰度发布

## 8. 微服务拆分与治理（开放题）

- 拆分依据：业务边界（DDD 限界上下文）、团队规模（康威定律）、数据独立
- 拆分陷阱：分布式事务激增、循环依赖、跨服务 JOIN → 领域事件/数据冗余
- 链路追踪：traceId 全链路透传（MDC/OpenTelemetry）
- 网关职责：路由、鉴权、限流、日志（Spring Cloud Gateway）

## 常见追问

1. TCC 的空回滚/悬挂？——Try 未到达 Cancel 先到（空回滚需记录事务表）；Cancel 后 Try 才到（悬挂需拒绝）
2. 最终一致的"最终"多久？——重试+对账双通道，SLA 分钟级
3. 服务雪崩实时案例怎么讲？——超时缺失 + 无熔断 + 线程池耗尽链条
